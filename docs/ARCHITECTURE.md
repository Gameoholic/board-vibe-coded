## Guiding stance

Build this as if it were a SaaS maintained by a large team, not a personal script: reused components, one source of truth per concept, careful modelling over fast hacks, security as a first-class concern. The owner cannot audit every line and is learning this codebase — clarity and consistency are features.

Two principles override convenience everywhere:

1. **Never hardcode the owner's board.** Sections, tasks, task types, and their config are *data over generic primitives*, editable through the UI — never `if (task.name === …)`, never a `WorkoutStreak` class. Details in `CONVENTIONS.md`; it's repeated there because it's the prime directive.
2. **History is sacred — this is a data silo.** We keep everything, forever: when a task was created, completed, edited, and *what it was edited from and to*; the exact points a completion was worth *at the time*. If we ever want a metric, we should already have the raw data and never need a backfill or a guess. This is the target model — see below for where current reality falls short.

## Data & history model

### Where we're going (the target)

A prior attempt reasoned this out carefully and the owner has re-committed to it. The reasoning is captured below (folded in from that attempt's ADRs) so it lives here and isn't re-litigated:

- **Append-only event log.** Nothing is mutated in place, nothing is hard-deleted. Every meaningful action (task created, completed, uncompleted, tier selected, edited, deleted) is an event with a timestamp. Current state is a *projection* derived from the log, cached for speed but always fully recomputable from zero.
- **Frozen values, live classification** (the subtle one — read the reasoning below twice before touching point-recalculation). The points a completion earned are written onto its event and never recomputed, so changing a task's worth later leaves past completions alone. Classification-type attributes (tags, type, the private flag) are read from the task *as it is now*. Both are recorded so an "as it was then" view stays possible.
- **Points as integer thousandths of a percent:** `1% === 1000`. Floats are banned once persistence lands — float addition isn't associative and the rebuild-parity check would fail randomly forever. `%` stays the only unit the user sees.
- **Backend is the only authority on points and time.** The client may compute optimistically for instant UI (it does today), but the server recomputes from its own config and its own clock. Time is always passed into pure logic, never read from a global clock inside it.
- **Persistence lives on the backend** (Postgres on the owner's VPS is the intended target). Everything is server-stored *except* genuine client-only display settings, which may live in `localStorage` (see "Client vs server state" below).

#### The reasoning, in full (why, not just what)

**1 — Append-only, because rebalancing must be non-destructive.** The owner rebalanced the economy repeatedly on the physical board and expects to keep doing it, and asked explicitly to store *everything*: when a task was completed and for how many points *at that time*, when something was deleted, when anything changed. A conventional mutable schema (`tasks.value`, `wallet.balance`) makes rebalancing destructive — change a task's value and every historical completion silently re-prices itself, so last year's good week becomes a different number. So: `events` is append-only, each scoring event freezing its resolved values, every multiplier applied, and the config version in force; definitions (tasks, types, filters, …) are versioned, edits write a new version, events reference the version live at the time; deletes are soft (`deleted_at`, `deleted_reason`) and are themselves events; current state is a projection with a CI parity check. *Good:* rebalances can be simulated against real history before committing; unanticipated analytics stay answerable; undo is honest (it records the reversal, doesn't erase the action). *Costs:* more rows and machinery than CRUD, every read path needs a projection — the owner waived storage as a concern. *Requires:* integer arithmetic (next), and idempotency keys on every write so a retry can't double-count.

**2 — Integer thousandths, because the rebuild must be exact.** Projections rebuilt from the log must equal the cached values *exactly*, and CI asserts it. Float addition isn't associative — `(0.1+0.2)+0.3 = 0.6000000000000001` vs `0.1+(0.2+0.3) = 0.6` — and a rebuild sums thousands of rows in whatever order the query returns; any index change, `WHERE` clause, or parallel aggregate changes that order and the check goes flaky. Separately, affordability (once a shop exists) is an equality test that floats break. So every point value is an integer number of thousandths of a percent (`1% === 1000`); multipliers compose into one factor, applied once, rounded once, half-up; the display layer divides by 1000 at the very edge. (Hundredths aren't enough — a 0.15% task at ×1.3 has nowhere to land and becomes a permanent overpayment. Postgres `numeric` is exact but node-postgres returns it as a string, forcing decimal.js everywhere for no gain.)

**3 — Frozen values vs. live classification, because two requirements pull opposite ways.** Requirement A: every scoring event freezes what applied at that instant, so changing what a task is worth in 2027 leaves the completions already logged untouched — the whole reason the log exists. Requirement B: a saved filter is reused — "change what counts as a workout in one place and every streak/counter/chart updates." Now retag a task that's been `stretch` for three months to also be `workout`: if the event froze its tags, the workout counter ignores those three months forever with no fix short of editing history (forbidden); if the filter reads tags *as they are now*, the counter jumps on its own. The resolution: **scoring values are frozen on the event** (`xp`/`coins`/`minutes`/`tier`, day classification, the resolved multipliers and composed factor, the definition version) and **never recomputed**; **classification is resolved live** from the task's current definition every time a filter runs (`tags`, type, behaviour, effort, `isPrivate`). The frozen snapshot still records `tagsAtTheTime` etc., so nothing is lost and a future "as it was then" mode needs no migration. Consequences worth stating in the UI: retagging changes what past events match (intended — the tag editor should say so), and marking a task private hides its whole history at once (what you want from a privacy flag; the alternative leaks).

### Where we actually are (current reality — be honest about this)

The append-only log is **built and persisted**. `apps/api/src/db.ts` opens a SQLite database (`apps/api/data/board.db`) via Node's built-in `node:sqlite` `DatabaseSync` — one table, `events`, append-only (`INSERT` only, never `UPDATE`/`DELETE`), each row an `id`, `type`, JSON `payload`, `occurred_at`, and a `UNIQUE idempotency_key`. Every event is validated with `BoardEvent.parse` on the way *out* of the row, so a corrupted payload fails loudly instead of poisoning the rebuild.

**Backups (`apps/api/src/backup.ts`).** The API snapshots the database into `backups/` beside it (`apps/api/data/backups/`, gitignored with the rest of `data/`) — a new one once the newest is `Settings.backup.everyHours` old (default 48), keeping the newest `keep` (default 5), the oldest deleted to make room; `enabled: false` takes none. `startBackups(events, () => settings.backup)` checks on boot, every 10 minutes and after any `PATCH /api/settings` that carries `backup` (so a new pace or a switch back on takes effect at once), so a server that was down when one fell due catches up at start. Lowering `keep` deletes nothing until the next backup is taken (the list marks those "goes at the next backup"). It returns `Backups { check, list, preview }` for the routes: `list` is the slots newest first (`BackupSlot { name, takenAt, bytes }`, `takenAt` the file's mtime) and `nextAt`; `preview(name)` reads a backup with `readSnapshot` (`db.ts`: opened read-only, read whole and **closed at once** — an open handle would stop the rotation deleting it on Windows — served as an `EventStore` whose writes throw) and folds it with the same `BoardStore` as the live board: its sections, tasks, streaks (counted as of when it was taken, or its last event if later — a debug-clock board stamps ahead) and `pointsAvailable()`. Only a name the folder holds is read (404 otherwise), so no path is ever built from the request. The snapshot is SQLite's `VACUUM INTO` (`EventStore.backupTo`), consistent even mid-write, written to a `.tmp` name and renamed so a crash can't leave a half file posing as the newest. Filenames are ISO timestamps (`:`→`-` for Windows), so name order is age order; "is one due" reads the newest file's mtime off the **real** clock, never the debug clock. A failed backup is logged, never fatal. Reset (`clearAll`) doesn't touch backups — they're the undo for it. Covered by `apps/api/test/backup.test.mjs` (`pnpm --filter api test`). Same disk as the DB, so they guard against a bad reset or corruption, not losing the host.

`apps/api/src/projection.ts` (`BoardStore`) folds the whole log into current state on boot (`readAll()` → `apply` per event) and keeps that projection in memory for reads. Writes go through *command* methods that build an event, `append` it (idempotency-key aware — a matched key returns the existing event and is **not** re-applied), then `apply` it to the live projection. `apps/api/src/seed.ts` seeds a default board only when the log is empty (`seedIfEmpty`), plus non-destructive migrations for existing DBs (`ensureStreaksTab`; `ensureRegistryTypes`, which sets the Registry tab's allowed types to exactly `{tiered, repeatable}` — older boards were tiered-only, or, older still, had picked up a stray `checkbox`); and `ensureSectionPeriods`, which backfills `Section.period` (`"day"`/`"week"`) onto pre-existing Daily/Weekly tabs so scheduled-box cadence is inferred from the tab). (There was also an `ensureWeeklyAllowsCount` migration; it was removed when the `count` task type folded into `checkbox` — a checkbox now carries an optional box count, so Weekly needs no extra allowed type. Legacy `count`-type events and boards whose Weekly lists both types normalise to `checkbox` on read; see the task-type note below.) Transport is a thin layer in `apps/api/src/routes.ts`; `index.ts` just wires store → seed → router.

**What the target model still lacks:** frozen point values per scoring event (points are still recomputed live from current config), versioned definitions, soft-delete events (`deleteTask` appends a `TaskDeleted` event but there's no `deleted_reason`/tombstone read model yet), and integer-thousandths points. The owner earns back to those feature-by-feature — **do not silently backfill them into unrelated feature work; each is a deliberate, reviewed change.**

### Auth surface (`apps/api/src/authRoutes.ts`)

- `GET  /api/auth/status` — `{ configured, authenticated }`, unauthenticated. `configured` is false until `pnpm set-password` has ever been run.
- `POST /api/auth/login` — `{ password }`; wrong password → 401, right password → 204 and sets the session cookie.
- Everything below is gated by `requireAuth` (a missing/invalid session cookie → 401 `{ error: "not authenticated" }`).

### Current API surface (`apps/api/src/routes.ts`)

- `GET  /api/sections` — list sections (tabs), in display order.
- `PATCH /api/sections/reorder` — `{ orderedIds }`, must cover all section ids exactly.
- `PATCH /api/sections/:id` — recolor a section (`{ color }` only; name/allowedTypes are seed-authored, not editable via this route).
- `DELETE /api/sections/:id` — **405 by design**; tabs are fixed once created (see `PRODUCT.md`).
- `PATCH /api/sections/:id/reorder` — reorder a section's tasks; `{ orderedIds }` must match that section's task ids exactly. Grouped tasks move as a block, so the client always sends an order that keeps each group's members contiguous (see Groups).
- `GET  /api/tasks?sectionId=` — all tasks, or one section's.
- `POST /api/tasks` — create; validates `type` against the section's `allowedTypes`, requires `points` for checkbox (with optional `count`, `estimateMinutes`, `estimateEffortIndex`, and `pointsSource`), `tiers` for tiered (each tier may carry its own `minutes`/`effortIndex`/`pointsSource`).
- `PATCH /api/tasks/:id` — a bundle of independent edits; each present field (`done`, `activeTier`, `progress`, `text`/`points`/`estimate`/`estimateMinutes`/`estimateEffortIndex`/`pointsSource`/`description`/`tiers`/`count`, `timer`, `pruned` — see "Prune" under Core types, `status` + `blocker` — see "Status", `parentId` — tuck into a task / take a piece out, see "Break down") is applied as its own command/event (`estimate`/`estimateMinutes`/`estimateEffortIndex`/`description` accept `null` to clear).
- `POST /api/points-formula/preview` — `{ formula }`; a **dry run** returning `{ willUpdate[], wontUpdateCount }` (which builder values would move `old→new`, and how many stay put). No writes.
- `POST /api/points-formula/apply` — `{ formula, rebalance }`; saves the formula (a `SettingsChanged` snapshot) and, when `rebalance`, recomputes every builder value's points via `TaskEdited`. Returns `{ settings, tasks }`.
- `POST /api/tasks/:id/duplicate` — the row menu's **Duplicate**: a new task with the source's *definition* (never its progress — done, tier, ticked boxes, timer), appended as a `TaskCreated` carrying `duplicatedFrom` (history only; the fold ignores it), then placed right after the source (`TasksReordered`) and into its group (`GroupMembersAdded`) in the same command, so the copy never exists anywhere but beside its source. The placement events only follow a copy that was really created (a key-matched retry just returns it). Returns the copy. `taskDefinition(t)` in `projection.ts` is the one list of definition fields — shared with reset-keep-board, so a new definition field is added in one place. A piece's copy is placed among its task's pieces instead (`PiecesReordered`), and a broken-down task's copy comes with copies of its pieces (the web reads those back, since only the server knows their ids).
- `POST /api/tasks/:id/pieces` — `{ texts }` (1–100 names): **Break down** — creates those pieces inside the task (see "Break down" under Core types) and returns the task, then all its pieces. `PATCH /api/tasks/:id/pieces/reorder` — `{ orderedIds }`, exactly that task's pieces (appends `PiecesReordered`).
- `DELETE /api/tasks/:id` — appends a `TaskDeleted` event; the task drops from the projection. A broken-down task's pieces are deleted first, each with its own `TaskDeleted`.
- `GET  /api/groups?sectionId=` / `POST /api/groups` (`{ sectionId, label, itemIds }`) / `PATCH /api/groups/:id` (`{ label?, addItemIds?, removeItemIds? }`) / `DELETE /api/groups/:id` — labeled bundles of a list's contiguous items, generic over item kind: `sectionId` may be a board tab (its tasks) or a shop tab (its rewards) — see Groups. Create validates the members are in that section and ungrouped (the fold gathers them into one run — see Groups); delete ungroups them (items stay). `GET` lists the board's groups; a shop tab's ship with `GET /api/shop`.
- `GET  /api/streaks?sectionId=` — list streak views (definition + computed `count`/`active`), in display order.
- `POST /api/streaks` — create a streak (only in a `kind: "streaks"` section).
- `PATCH /api/streaks/reorder` — `{ sectionId, orderedIds }`. **Registered before `/streaks/:id`** so "reorder" isn't captured as an id.
- `PATCH /api/streaks/:id` — bundle of edits (`name`, `type`, `mode`, `since`, `matcher`).
- `DELETE /api/streaks/:id` — appends a `StreakDeleted` event.
- `GET  /api/shop` — the whole shop in one payload: `{ sections, rewards, groups, spent }` (shop tabs, rewards with a derived `redeemed` count and their list `order`/`groupId`, the shop tabs' groups, and the total of every purchase's frozen `pointsSpent`). See "Shop" below.
- `POST /api/shop/sections` (`{ name, color }`) / `PATCH /api/shop/sections/:id` (`{ name?, color? }`) / `DELETE /api/shop/sections/:id` — shop tabs. Unlike board tabs these are user-created and deletable; delete removes the tab's rewards and groups too (past spending stays).
- `PATCH /api/shop/sections/:id/reorder` — `{ orderedIds }`, exactly that shop tab's reward ids (the reward counterpart of `/sections/:id/reorder`; appends `RewardsReordered`).
- `POST /api/shop/rewards` (`{ shopSectionId, name, emoji, cost, note? }`) / `PATCH /api/shop/rewards/:id` (`name`/`emoji`/`cost`/`note`, `note: null` clears) / `DELETE /api/shop/rewards/:id` — rewards. `cost` is integer thousandths and must be > 0.
- `POST /api/shop/rewards/:id/purchase` — buy: **400 `not enough points`** unless the board's live total − `spent` ≥ the cost (checked server-side, never trusted from the client); else appends `RewardPurchased` with the cost frozen and returns the updated shop.
- `GET  /api/settings` — the board's `Settings` (timezone, day-start, week-start). `PATCH /api/settings` — partial patch, logs a full `SettingsChanged` snapshot.
- `GET/POST /api/debug/clock` — the debug clock (see "Debug clock" below). `GET` returns `{ now, real }` (`now` = pinned instant or `null`, `real` = the true clock); `POST { at }` pins the server's `now` to an ISO instant or clears it with `null`. In-memory only.
- `GET  /api/periods/status` — for `day` and `week`: `{ openKey, currentKey, due }` (due = the open period differs from the one `now` falls in), plus `banked` (points kept from tasks the rolls unchecked).
- `POST /api/periods/roll` — `{ kind }`; closes the open period (freezing a snapshot), unchecks that cadence's tabs (banking their points) and opens the current one, returning `{ recap, streaks, week? }` — a week close also rolls the new week's Bounties, in `recap.bounties` (see "Weekly Bounty"). The web only ever sends `day`: ending a day ends its week too once that's over, and the week's recap comes back as `week`.
- `GET  /api/backups` — `BackupList { slots, nextAt }`: the saved backups newest first and when the next falls due (`null` while they're off), real clock. `GET /api/backups/:name` — `BackupPreview { takenAt, sections, tasks, streaks, points }`, that backup's board as saved (404 for a name the folder doesn't hold). See "Backups".
- `GET  /api/bounty` — `BountyStatus { bounties, rerollsLeft }`: the open week's Bounties still to win (each a `RolledBounty`) and the rerolls left.
- `POST /api/bounty/reroll` — `{ taskId }`; rerolls that Bounty onto another candidate (400 when it isn't one of this week's, once it's won, with no rerolls left, or with nothing else to roll); returns the new `RolledBounty`.
- `POST /api/reset` — **destructive**: wipes the event log to an **empty board** (`clearAll()` → `initializeInfra` — settings only, **no placeholder tabs/tasks/streaks and no started period**, so the board then prompts you to start your first day/week). `POST /api/reset/keep-board` — wipes all history/progress but **rebuilds the current tabs/tasks/streaks and shop tabs/rewards** (`reseedFromCurrent`: re-emits their creation events with ids preserved, so streak links survive; done/progress/tier/timer/periods and **purchases** drop, so `spent` restarts at zero alongside the points). Both are the only places the append-only log is cleared; settings actions, confirmed in the UI. (Boot uses `initializeBoard`, which additionally seeds the demo content on a truly fresh DB.)

Every body is parsed through a contract Zod schema before the command layer runs (a `ZodError` becomes a 400 via the error middleware) — that's the trust boundary. Writes accept an optional `Idempotency-Key` header, namespaced per operation, so a retried request is a no-op rather than a duplicate event.

### Core types (`packages/contracts`, re-exported by `apps/web/src/types.ts`)

The contracts package is the single source of truth; the web `types.ts` just re-exports the inferred types. `Section { id, name, color, allowedTypes[], kind, period? }` where `kind: "tasks" | "streaks"` (defaults `"tasks"`) and `period?: "day" | "week"` is the seed-authored recurrence cadence (drives scheduled-box daily/weekly — see below — and which period roll unchecks the tab's tasks: Daily + Registry are `"day"`, Weekly `"week"`, Tasks has none and never resets; see "Settings & period close"), `Task { id, sectionId, type, text, done, order?, groupId?, points?, estimate?, estimateMinutes?, description?, tiers?, activeTier?, count?, progress?, schedule?, timer?, pruned?, status?, statusSince?, blocker?, parentId? }`, `TaskType = "checkbox" | "tiered" | "repeatable" | "once"`. `estimateMinutes` is an optional estimated duration in minutes for a **checkbox** task, derived from its points builder (a duration was picked); a **tiered** task instead stores its estimate **per tier** (`TierDef.minutes`), since each tier has its own duration. Both are captured from the shared `PointsBuilder` (its optional `onBuilderChange`), persisted like any definition field, and feed the tier timer + the per-tab time display/sort. Alongside them each builder value carries **`estimateEffortIndex`** (which effort preset it used) and **`pointsSource: "builder" | "manual"`** — see the points-formula section below. `order` is the server-derived position in its section; `groupId` is set when the task is bundled into a group (see Groups). `description` is an optional free-text note (revealed behind an inline info affordance on the row); it mirrors `estimate` end-to-end — set on create, edited via PATCH (nullable there to clear it), frozen on `TaskCreated`/`TaskEdited` like any other definition field. Streak types are below.

- **Task-type behaviour registry (`packages/contracts/src/taskKinds.ts`).** Every task type shares one shape — *a row of boxes*: `boxes` of them, `filled` currently ticked, a point `valueAt(filled)`. Each type is one `TaskBehavior` entry (`behaviorOf(task)`); consumers read board state through it instead of switching on `task.type`, so **adding a type is one entry here, not edits scattered across the UI** (capability flags like `prunable` and `breaksDown` say which row actions a type gets) (the row render, the running total, the sort orders and the streak counting all pick it up for free). **A checkbox and a "count" (do-it-N-times) task are the same type** — a `checkbox` with an optional `count` box count (default 1); `valueAt = points × filled`, `supportsQuantity: true`. Tiered is one box per tier (`valueAt` = that tier's points, `supportsTimer: true`). **`repeatable`** is the whiteboard tally: a single box completed again and again, storing its completion count in `progress`, worth `points` per completion (`valueAt = points × progress`). It takes an **optional `count` cap** (chosen at creation — blank ≡ unlimited): uncapped it climbs forever and is never `isDone` (the `unbounded: true` flag lets `setProgress` accept any level *unless* a `count` is present, which re-clamps it to `count`); capped it stops at `count`, counts as `isDone` once reached, and `maxValue = points × count`. **Left-click adds one** (`levelOnClick = min(progress+1, count ?? ∞)`, ignoring the box index); **right-clicking the box removes one** (down to 0) to fix a mis-click — that gesture replaced the old "Times done" edit field, which is gone. It's `renderKind: "counter"` — a number-bearing box + an "N" badge — and seed-allowed in the Registry tab alongside `tiered`. **`once`** is the Tasks tab's kind: a task done exactly once and then gone (reschedule the dentist, call grandma). It's `TASK_BEHAVIORS.once = { ...checkbox, supportsQuantity: false, retiresWhenDone: true }` — it scores exactly like a plain 1-box checkbox (same native toggle), but the add/edit forms never offer a box count or scheduled times for it (`supportsQuantity: false`; `CreateTaskBody` also rejects either on a `once` task), and a finished one **leaves its list** (`retiresWhenDone` → `isRetired(task)`). **Retired ≠ deleted:** the task stays in state, still `done`, still worth its points in the live total — it's just not listed. Two derived fold rules in `BoardStore` (`settleDoneChange`/`settleRetired`, run after `TaskCreated`/`TaskCompleted`/`TaskUncompleted`/`TaskTypeChanged`/`TasksReordered`) keep the list base working around hidden tasks: a task that retires **drops out of its group** (a hidden member would split the group's run), and a section's retired tasks **always trail its order** (a stable partition) — so the listed tasks are one contiguous run that `ItemList` can reorder and group without a hidden task stranded inside, and the server's contiguity check never trips on one. They're fold rules, not events, so a rebuild lands in the same place. The client mirrors both optimistically (`App.setLevel`/`addTask` via `listOps.withTrailing`), `SectionCard` filters retired tasks out and appends their ids when posting a reorder (the server wants the whole tab), and `TaskItem` holds a local `retiring` flag so the leaving row (which keeps rendering its last, unchecked props) shows checked + hatched through a short delayed exit (`ItemRow`'s `exitDelay`, `RETIRE_EXIT_DELAY`) before it's tossed off. A tab that allows a retiring type gets a **"Completed tasks"** Display toggle (off by default) — a flat, read-mostly look-back (no drag/group while it's on) where finished tasks show hatched at the end and can be unchecked; unchecking one rejoins the listed run at its end. **Type changes:** `TaskTypeChanged { taskId, taskType, previousType }` is its own event (the type is structural — it decides which fields mean anything — so it isn't a `TaskEdited` field), emitted only by migrations via `BoardStore.changeTaskType`, which refuses a type the section doesn't allow or one that can't hold the task's data (a box count/schedule on a no-quantity type). `ensureTasksTabOnceType` (`seed.ts`) sets the Tasks tab's `allowedTypes` to `[once]` and converts its existing plain checkboxes to `once` (a checkbox with a box count or schedule is left alone rather than losing data). **Known consequence:** reset-progress-keep-board re-creates every task undone, so finished one-time tasks come back. The three render shapes are the one place the row branches: `renderKind(task)` returns `"checkbox"` (native input, count 1), `"boxes"` (a strip — count>1 or tiered), or `"counter"` (repeatable). Because a 1-box checkbox must keep its native `<input>` + `done` toggle while a multi-box one renders as boxes and stores its level in `progress`, **`rendersAsBoxes(task)` and `patchForLevel(task, level)` take the task** (not a constant) and branch on count: count 1 ⇒ native checkbox, `done`/`TaskCompleted`; count > 1 ⇒ box strip, `progress`/`TaskProgressSet`. `levelOnClick(task, i)` maps a box click to a target *filled level* — so `App`'s single `setLevel` handler and `TaskItem` never branch on type. Points live in this shared contract because the **server is the sole scorer**: the projection and the web counter compute from the same functions and so agree by construction.
- **Scheduled boxes (`schedule`)** — a "do this box at a certain hour" gate, duck-typed onto **any checkbox task** (1-box or multi-box), never a task type of its own. `Task.schedule` is an optional array indexed by box, each slot `{ minutes?, dayOfWeek? } | null` with **at least one field set** (`packages/contracts/src/period.ts` → `BoxSchedule` refine; `minutes` = minutes past local midnight, `dayOfWeek` 0–6). Two shapes, two cadences: a **daily gate carries only `minutes`** (no weekday — unlocks at that time every day); a **weekly gate carries a `dayOfWeek`** and *optionally* `minutes` (unlocks on that weekday within the board's week, at the time if given, else from the start of that day — "Friday, any time"). So teeth-plates (count 2) is box 0 → Friday, box 1 → Saturday. So teeth-plates lives in the Weekly tab. The daily/weekly cadence is **inferred from the section's `period`** — `"week"` → weekly scheduling (weekday + optional time), anything else → daily (time only) — so it's read off the *tab*, never a per-task option and never section-name matching. `Section.period` is a **generic seed-authored primitive** (`SectionPeriod` in `domain.ts`, like `kind`): the seed sets Daily→`"day"`, Weekly→`"week"`; a `SectionPeriodSet` event + `ensureSectionPeriods` migration backfill it onto pre-existing Daily/Weekly tabs (name-keyed, which is fine in seed/migration code — cf. `ensureRegistryTieredOnly`). The `SectionCard`/`AddTaskPopover`/`TaskItem` read `section.period` into a `scheduleCadence` prop; the shared `ScheduleEditor` takes that cadence, it isn't chosen in the form. (There's still no daily/weekly *task* type — Daily/Weekly/Registry remain seeded section names, everything non-registry is a `checkbox`, and the period-close system stays global; `Section.period` only informs scheduling today.) `isBoxLocked(entry, now, settings)` is a **pure** function (pure civil arithmetic: minute-of-day for daily, position-within-week for weekly — no timezone-aware instant construction) and a **display/interaction gate only** — the server never rejects an early tick, so it isn't a scoring concern. Persisted like any definition field: sent on create/edit, frozen on `TaskCreated`/`TaskEdited`, and **normalised on read/apply so an all-`null` array collapses to "no schedule"** (`.some(Boolean)`). Applies to `checkbox` only (`supportsQuantity`); meaningless for tiered ladders. Frontend: a locked box (dot, or the single checkbox wrapped in `.checkbox-cell` to stay one grid child) shows a `LockIcon` badge + an "Unlocks …" hint via the reusable **`Tooltip`** component (dark-bubble style shared with the tier-dot label; the box uses `aria-disabled` + a click guard rather than the `disabled` attribute so it still takes hover/focus to reveal the tooltip); an already-ticked box never shows a lock. **Any scheduled box carries the hover tip, not just locked ones** — an already-open timed box reads "For 08:00" so several timed boxes on a row stay distinguishable (`boxTip`). The board's effective `now` + `Settings` reach `TaskItem` through a **`BoardClockProvider`/`useBoardClock`** context (not prop-drilled through `SectionCard`/`GroupBlock`), and `App` re-stamps `realNow` on a **60s interval** so a box unlocks when its time arrives without a manual reload (a debug-pinned time still wins). The add/edit forms share one `ScheduleEditor` (a Daily/Weekly pill toggle + per-box time input, plus a weekday select in weekly mode). **ponytail:** a pathological schedule where a lower box unlocks *later* than a higher one can be filled past via the higher box's cumulative click — acceptable for a personal board; add per-box click clamping if it ever bites.
- **Multi-box checkbox tasks** (`count` 2–100) carry `progress` (0–`count` ticked). Each ticked box is a completion worth `points`; the task is "done" only when `progress ≥ count`. Editing `count` down clamps `progress` in the projection so state stays valid. Set via the `TaskProgressSet` event (`{ taskId, progress, pointsAwarded }`, `pointsAwarded = points × progress`). **`count` was named `target` before the checkbox/count merge**; old `TaskCreated`/`TaskEdited` events (and a retired `count` task type) are normalised on read — `taskType: "count" → "checkbox"`, `target → count` (`count ?? target`) — like the streak `period → type` alias, no backfill.
- **Prune (`Task.pruned`)** — "not this cycle" for a daily/weekly task. `TaskPruned { taskId, periodKey }` records the open period of the task's tab (`Section.period`); `TaskUnpruned` undoes it. The projection keeps them in a side map (`prunedIn`, like the timers) and `readTask` derives `pruned` as *that period is still the tab's open one* — so the roll that opens the next day/week ends it with **no event of its own**, and a rebuild lands in the same place. Eligibility is one rule, `canPrune(task, section)` in `taskKinds.ts`: the behaviour's `prunable` flag (plain `checkbox` only — tiered, tally and one-time tasks aren't) **and** a tab that recurs; never a tab name. `setPruned` refuses anything else, and refuses before any day/week has started. It changes nothing else — done, progress, points and streak counting are untouched (pruning isn't doing). Web: `SectionCard` hides pruned tasks unless the tab's **Pruned tasks** Display toggle is on (then they list dimmed at the bottom as a flat, no-drag look-back, like Completed tasks); the row menu offers Prune / Unprune and names the streaks pruning would break (`streaksBrokenByPruning` in `pruning.ts`: an unmet daily/weekly condition on the task, in an all-mode or single-condition streak; a weekly streak on a daily task is exempt, since the task is back tomorrow). **Trap:** pruned tasks are the first hidden rows that sit *inside* the listed run (retired ones always trail), so a reorder, an eject, or a new/extended group must keep them in place — `withUnlistedKept` (`listOps.ts`) rebuilds the tab's full order from a list's reorder (see "Status" for the rule, which the bands share), and `runBetween` pulls a hidden task lying inside a new group's span into the group. Pruned styling dims the row's *cells*, never the row — framer owns the row's `opacity` for its enter/exit.
- **Status (`Task.status`, `statusSince`, `blocker`)** — which band of its tab a task sits in: `TaskStatus = "in-progress" | "backlog" | "blocked"` (absent ≡ backlog; the words the owner sees are display labels in `taskStatus.ts`, never these ids). Organisation only: it never touches points, progress or **the tab's order** (priority *is* the Backlog's order; there's no priority field). `TaskStatusSet { taskId, status, previousStatus, note?, blockedBy? }` is the one event — only the owner's own choices are events. The shared pure rules live in `packages/contracts/src/taskStatus.ts` and both sides fold through them: `statusChange` (what a move sets: `statusSince` only when the band really changes; a blocker `{ note?, taskId?, resume }` whose `resume` is the band it goes back to — kept when a blocked task's reason is re-said) and `releasedFrom`. **A task blocked on another is released by a fold rule, not derived at read** (`BoardStore.releaseDependents`, run after `TaskCompleted`/`TaskTierSet`/`TaskProgressSet`/`TaskEdited` once the blocker `isDone`, and on its `TaskDeleted`): it goes back to `resume` for good. Deriving "blocked while the blocker is open" on read looked simpler but is wrong — a *daily* blocker is unchecked again by its day's reset and would re-block it. `setStatus` refuses a blocker that is the task itself, missing, or already done. Reset-keep-board drops statuses (they're state, not definition); Duplicate's copy starts in the backlog. Covered, with rebuild parity and the group-gathering rule, by `apps/api/test/status.test.mjs`.
  - **The bands (web):** the tab's **Status** Display toggle (`SectionCard`; `defaultOn` where the tab allows a type that retires when done — a to-do list, never a tab name) renders `StatusBand`s — In progress (tinted, "in hand N d" from a task's second day there — none on the day it started, its band says it — and a nudge above `IN_PROGRESS_NUDGE_ABOVE`), Backlog, Blocked (folded; only while non-empty) and, with Completed tasks on, a trailing Completed look-back. **Each band is the same `ItemList` over its own tasks** (sorting, reorder, groups — a group whose tasks sit in two bands shows in both), and they share **one grid**: `.status-bands` carries the list tracks (`--list-tracks` in `:root`, the one home also used by `.item-list`) and every band and band list is a `subgrid`, so the `[%]` column lines up across bands. A band's box reaches 8px past the list (`margin: 0 -8px; padding: 0 8px` — a subgrid's margin and padding net to 0 on its edge tracks) so a group's rail sits inside the tint. An empty list's line spans the row (`.item-list > .empty`) — in column 1 it would widen that track for the shared grid. A row moves between bands by the hover `StatusPill` (icons with the tier-dot label bubble — words hid the name on a narrow tab; the name's end fades under it), the menu's Status choices (`statusActions`, `RowAction.checked` radio items), or dragging onto another band (`ItemList`'s `dropOutside` — below). Blocked opens `BlockForm` (note + the shared pick-whip) on the row; the tab holds which row's form is open, since a drop on Blocked opens it too. `App.setTaskStatus` is optimistic through `statusChange` and adopts the server's stamp; `App.setLevel`/`removeTask` mirror the release (`releasedFrom`) so the waiting task moves in the same render.
  - **Trap — keeping the rest of the tab in place.** A band's list sees only its own tasks, but a reorder must post the whole tab. `withUnlistedKept(oldOrder, listedOrder, inList, moved)` merges: an unlisted task inside its group's run rides with the group; any other stays beside the neighbours the drag *didn't* move (after the nearest one before it, else before the nearest one after it). It needs `moved` from the list (`ItemList` tracks what its drag moves — a row, or a group block's members — and passes it with `onReorder`): framer reorders one adjacent swap at a time, and a swap alone can't say which side moved — anchoring to the old predecessor (the first version) let a dragged row carry the folded Blocked task after it, and guessing the moved side from the orders still drifted by a slot. Checked in the e2e: a Backlog drag leaves the Blocked task exactly where it was.
  - **Trap — one group, two lists.** A group can now render in two lists of one tab, so nothing may find a group by a page-wide `[data-group-id]` lookup: `ItemList` and `GroupBlock` find their list/block from the dragged row (`closest(".item-list" / ".group-block")`), which stays in its list for the whole drag.
- **Weekly Bounty (`Task.bounty`, `Task.boost`)** — every week close rolls open tasks (`Settings.bounty.max` at a time) each worth a multiplier until the next close. The shared rules are `packages/contracts/src/bounty.ts`: `canBounty` (an open task of a type that's done once, in a tab with no `period`, not Blocked, not a piece), `bountyWeight` (days on the board + 1), `pickWeighted`, `rerollSource` (the week's free rerolls first, then bought ones), and `boostOf` (its own Bounty's multiplier, else its parent's — a broken-down task's Bounty pays its remaining pieces). `Settings.bounty` is `{ enabled, max, multiplier, rerolls, rollOnWin }`.
  - **Record the roll, never recompute it.** `rollPeriod("week")` on a real close (not a first start), while Bounties are `enabled`, runs `startWeekBounties`: it grants the week's free rerolls, then rolls up to `max` Bounties, each picked with the store's `random` (a constructor parameter — tests inject one; a rebuild never calls it) from candidates that aren't already one, and committed as `BountyRolled { taskId, periodKey, multiplier, reroll?, replaces?, rerollFrom? }` — the multiplier is `Settings.bounty.multiplier` at the time. Any roll (a reroll, one after a win) also skips every task the week has already had (`bountiedIn`, folded from the week's `BountyRolled`s, cleared with its slots on `PeriodStarted`) while another candidate is left — otherwise a second reroll could just bring the first one back. The fold keeps each week's Bounties in the order rolled (`bounties`): a reroll swaps the one it `replaces` (an old reroll without `replaces` swaps the week's only one), any other roll adds one. A week's `PeriodStarted` starts its Bounties and free rerolls afresh — the debug clock can reopen a week, and an earlier run's ended when that run closed (keeping them stacked a second Bounty onto a reopened week). `readTask` stamps `bounty` while its week is the open one and Bounties are enabled, so the next close (or switching them off) ends it with no event (like Prune). `rerollBounty(taskId)` refuses a task that isn't one of this week's, a won one, no rerolls left, or nothing else to roll. The recap, `GET /api/bounty` and a reroll return `RolledBounty`s (the task, multiplier, rerolls left, and other candidates' names for the reel — display only, most avoided first).
  - **Rerolls are a ledger, so they can be bought later.** `BountyRerollsGranted { count, source: "week" | "purchase", periodKey }`: a week close grants that week's free ones (`Settings.bounty.rerolls` frozen then, so changing the setting mid-week leaves the week alone); `purchase` is the shop's way in (not built yet — see BACKLOG), banked until used, whatever the week. A reroll spends free ones first (`rerollSource`), and the pool it spent is frozen on its `BountyRolled` as `rerollFrom`. `rerollsLeft` = the open week's grant less what it spent (a week from before grants were recorded falls back to the setting) + what's banked.
  - **Winning one may roll another.** With `rollOnWin` on, `setDone` follows a win (fewer Bounties left to win than before the command) with `rollAfterWin`: more `BountyRolled`s, up to `max` still to win — a command-level follow-up, recorded like any roll. Counting "still to win" before and after is what stops an untick-and-retick farming new ones.
  - **Freeze the multiplier on the completion.** `BoardStore.completion(task)` builds every `TaskCompleted` (a tick, the fan-out, `settleParent`) with `pointsAwarded = boosted(points, boost)` and the `boost`; the fold keeps `task.boost` while it's done (cleared on untick and by a period reset), and `taskPointValue` multiplies by it — so the live total, the server's `pointsAvailable` and the web counter all keep a won Bounty's ×2 after it ends, and a rebuild agrees. `boosted` (`points.ts`) is the one rounding: once, half-up, to whole thousandths. Covered by `apps/api/test/bounty.test.mjs` (rebuild with a random that throws) and `packages/contracts/test/bounty.test.mjs`.
  - **Web.** `App.withLevel` mirrors the boost (kept if already ticked); `setLevel` takes a tick's gain as the board total after it less before (so boosts and a finished task's own points need no separate sums), and plays the `finale` flyer for winning the Bounty too. `SectionCard` pins the open Bounty above the rest of its list as a single-row, non-draggable `ItemList` — never by moving it in the tab's order — with both lists on one grid (`.list-stack`, or the band's subgrid); `PointsBracket`'s `multiplier` makes it show what a completion pays — `boosted` values, marked `.points-boosted` (`TaskItem`'s `multiplier`: its frozen boost once ticked, else `boostOf`; Break down's drafts take their task's `boostOf` too); `.bounty-stamp` beside the name carries the factor. A Bounty still to win gets "Reroll Bounty" in its menu (`TaskItem`'s `reroll`, from `App.bountyStatus` — `GET /api/bounty`). The reel is `BountyRoll` (`BountyRoll.tsx`): it cycles every candidate, the winner too (so a board with one or two open tasks still spins, and the winner isn't the one new name), driven by a motion value — animated (once fonts are in) to just past the winner, then sprung back onto it, re-measured so it lands exactly centred (a swapped-in font re-lays the names mid-spin); its velocity drives a motion blur, and a listener on it lights the name under the pointer and flicks the pointer as each passes (DOM classes, no re-render). Landing adds CSS rays and framer sparks (clipped close in `.bounty-burst`, so they never scroll the page), a shake and the stamped multiplier; `spin`/`onLanded` let several roll one after another (`BountiesPage`, the recap's last page). Keyed by the winner, so a reroll spins again. **Mid-week reveal:** `BountyReveal` shows one on its reel in a card — after a row's Reroll (`App.rerollRevealed`), or a win that rolled another (`App.revealRolledAfterWin` finds the Bounty that wasn't on before, and queues it in `revealNext` until no flyer is in the air, so it never cuts the win's own celebration short); the board reads its tasks back when it closes, so the new one isn't given away early.
- **Break down (`Task.parentId`)** — a one-time task split into pieces that sit inside it, one level deep. Only a type whose behaviour `breaksDown` (`once`) can, and never a piece (`canBreakDown`); pieces are tasks of that same type. The shared rules are `packages/contracts/src/pieces.ts`: `newPiecePoints` (the task's own points split evenly across the new pieces by `splitPoints` — on hundredths, remainder to the first pieces, so they always sum exactly; once its own points are all in pieces, a new piece is worth an average existing one) and `doneFromPieces`.
  - **Events.** A piece born by Break down is a `TaskCreated` carrying `parentId`; `breakDown` also moves the task's own points into them with a `TaskEdited { points: 0, pointsSource: "manual" }` (manual, so a formula rebalance never hands its old value back on top of the pieces'). Tucking a task in, or taking a piece out ("Make it its own task"), is `TaskParentSet { taskId, parentId | null, previousParentId }`; reordering pieces is `PiecesReordered`. `setParent` refuses a parent that is a piece, finished, in another tab, the task itself, or full (`PIECES_MAX`), and a task that has pieces of its own.
  - **Order: a task is a list of its pieces.** Pieces aren't items of their tab's list — they're ordered in `itemOrder` under their task's id (`listOf(t) = t.parentId ?? t.sectionId`), so the tab's order, `reorderTasks`' permutation, groups (`sectionItems` leaves pieces out; a tucked task leaves its group) and the retire/gather rules never see them. Taken out, a piece lands right after the task it left, then the tab's rules settle (`settleGroups`, `settleRetired`).
  - **Done follows the pieces — as events.** `settleParent` runs after every command that changes a piece (tick, untick, delete, tuck, take out, a piece's copy) and commits the task's own `TaskCompleted` (its own points frozen on it, like any completion) / `TaskUncompleted` when `doneFromPieces` disagrees with it — so the task retires, releases what waits on it and counts for streaks through the ordinary rules. A command-level follow-up rather than a fold rule because it's a scoring moment. The task's own box is all its pieces at once: `setDone` on a task with pieces ticks (or unticks) each piece instead, then settles. Reset-keep-board re-creates each task's pieces right after it (from its piece order). Covered by `apps/api/test/pieces.test.mjs` (rebuild parity included) and `packages/contracts/test/pieces.test.mjs`.
  - **Web.** `SectionCard` lists only the tab's own tasks (`topTasks`) and hands each one that can break down a `RowPieces` (its pieces, fold state, callbacks); `Pieces.tsx` draws the strip, the "1 of 4 · Next: …" line (the next open piece that isn't blocked, plus "· N blocked"), the pieces (a `Reorder.Group` of ordinary `TaskItem`s inside the task's row, a second grid row on the same four tracks — not a subgrid, whose indent would widen the tab's first column) and the Break down entry (typed pieces wait there with `newPiecePoints` shown, created together on Esc / empty Enter / a click elsewhere; its pick-whip tucks a task in). A piece's menu has Make it its own task and `pieceStatusActions` (Blocked / Unblock — a piece has no band). `App.setLevel` fans a task's own tick out to its pieces and `settleParents` mirrors `settleParent`; the tick that finishes a task spawns a `finale` flyer (see Flying points) whose bracket shows everything that tick won. Which tasks' pieces are folded is a per-device tab pref (`TabPrefs.collapsed`). Ticking the task's own box in the UI doesn't send the fan-out: `TaskItem` ticks its open pieces one by one, `PIECE_CASCADE_MS` apart (timers read the row's latest state through a ref, and stop if it unmounts), so each pays and flies on its own. Whichever tick finishes the task sets its `retiring` to `"finale"`: the `.finishing` animation (the rail fills up, the box pops with a ring) and a longer `FINALE_EXIT_DELAY`; the leaving row renders its pieces ticked, since its frozen props are from before the last tick.
  - **Trap — rows inside a row.** A piece is an `ItemRow` inside its task's `ItemRow`, so a right-click, a hold and `:hover` all reach both. `ItemRow` ignores a right-click or hold that started in a nested row (`fromNestedRow`), and the row hover rules match only the innermost hovered row (`.item-row:hover:not(:has(.item-row:hover))`, with `>` to the row's own handles, trash and pill).

### Points formula & rebalancing (`packages/contracts/src/pointsFormula.ts`)

The builder turns a task's time into a `%`: **`% = hours × ratePercentPerHour × effortMult`**, rounded to 2 decimals. Both the rate and the effort presets live in **`Settings.pointsFormula`** (`{ ratePercentPerHour: 2.5, effortLevels: [{Normal ×1},{Challenging ×1.5}] }`, all editable), so the formula is board-wide server truth, not a builder constant. `pointsFromMinutes(minutes, effortMult, formula)` is the one scorer — the projection and the web builder both call it, so they agree by construction (same rule as `taskKinds`).

- **Provenance per value.** Each builder value (a checkbox task, or each `TierDef`) stores **`pointsSource: "builder" | "manual"`** plus the inputs that produced it — `estimateMinutes`/`minutes` and `estimateEffortIndex`/`effortIndex` (an index into `effortLevels`). `pointsSource` is the builder's own report: `"builder"` while the current `%` still equals what its duration+effort produce at the live formula, `"manual"` the moment you type a different `%` (or pick no duration). It's **stored, never re-derived from the current formula** — otherwise declining a bulk rebalance (or a rate change) would silently flip an untouched value's provenance. `resolvePointsSource` returns the stored flag if present, else derives **once against the historic default formula** (2.5%/hr) — the only formula pre-feature values were ever created under; `readTask` fills this so the API always returns a concrete source. (This is how the pre-feature Daily/Weekly tasks whose `estimateMinutes` was backfilled read as `builder`.)
- **Rebalance.** Changing the formula in Settings → `previewFormula(formula)` (dry run) → the **`RebalanceConfirm`** card (soft scrim, a scrollable capped-height `old→new` list + a *will-update* / *won't-update* count). **Yes** → `applyFormula(formula, true)`: recompute every `builder` value's points from its stored `minutes`+`effortIndex` at the new formula, via `TaskEdited` (each re-stamped `pointsSource:"builder"`). **No** → save the formula for future tasks only. **Cancel** → nothing. `manual` values and estimate-less values are never touched.
- **History stays honest.** Rebalancing edits a task's *current* points only; completion/tier/progress events already froze their `pointsAwarded`, so a future "% ever earned" tally reads those frozen values — old completions keep the points they earned. This is why storing frozen awards on the scoring events (already done) matters even though the live total still recomputes from current config.
- **Effort presets are editable and rebalanced too** (index-based): editing the "Challenging" multiplier and applying rebalances every value that used that preset, exactly like a rate change. **ponytail:** effort presets are edit-in-place (label + mult), not add/remove; a value stores its preset *index*, so reordering/removing presets would need index remapping.

### Groups (labeled bundles of a list's contiguous items)

A **group** bundles a contiguous run of a section's items under one label — the generic primitive behind "group my tasks" (morning / meds / evening …), never a hardcoded group. It's **list structure, not task structure**: the same groups work over a board tab's tasks, a streaks tab's streaks, and a shop tab's rewards (`sectionId` is whichever tab it's in). `Group { id, sectionId, label }`; it carries no scoring and has **no position of its own** — its place is wherever its members sit. Membership lives on the items (`task.groupId` / `streak.groupId` / `reward.groupId`).

- **Order.** The projection keeps `itemOrder: Map<sectionId, string[]>` — each section's item id order (and each broken-down task's piece order, under the task's id — see "Break down") (board, streaks, and shop tabs alike; ids are distinct), the single source of order (`TaskCreated`/`StreakCreated`/`RewardCreated` append, `TasksReordered`/`StreaksReordered`/`RewardsReordered` replace it). Each read item is stamped with an `order` index; the web sorts by it and builds the render rows. (Streaks joined this in the same change that gave them groups — before it, `StreaksReordered` spliced the `streaks` array directly; now it's list structure like everything else, ordered the same way tasks and rewards are.)
- **Written once over any item kind.** `BoardStore.sectionItems(sectionId)` returns the live items a section lists (its tasks, its streaks, or its rewards — branching on the board section's `kind`) and `allItems()` every groupable item (tasks + streaks + rewards); the group commands validate against the former and the fold tags/untags over the latter — no per-kind copy.
- **Contiguous by construction.** After anything that can change a list's order or a membership (`TasksReordered`/`StreaksReordered`/`RewardsReordered`, `GroupCreated`, `GroupMembersAdded`), the fold gathers each group's members into one run at its first member's place (`BoardStore.settleGroups` over the pure `gatherGroups` in `packages/contracts/src/listOrder.ts`; the web mirrors it with `listOps.withGathered` in `App`'s reorder/group updates). This replaced a contiguity *check* on create: with Status bands, a run the owner groups in one band can have another band's tasks between its members in the tab's full order, and they're simply gathered out of the way. Consequence: `duplicateTask` adds the copy to its group **before** placing it beside its source — placed first, an ungrouped copy beside a middle member would split the run and be pushed past the group's end.
- **Membership on the items.** `GroupCreated { groupId, sectionId, label, itemIds }` tags each member's `groupId` (validated on create: members exist, are in the section, and are ungrouped). `GroupMembersAdded/Removed { addedItemIds / removedItemIds }` extend/shrink it. `GroupEdited` relabels (carries `previousLabel`, self-describing like `TaskEdited`). `GroupDeleted` clears `groupId` on its members — deleting a group **ungroups** its items, it doesn't remove them; a group left with no members is pruned on item delete (`dropGroupIfEmpty`), and a deleted shop tab drops its groups.
- **Member-id rename (history).** The member fields were `taskIds` / `addedTaskIds` / `removedTaskIds` when only tasks could be grouped. New events write the `item` names; the old ones stay optional in the schema so logged events still parse, and the fold resolves `itemIds ?? taskIds` — the same pattern as the streak `streakType ?? period` rename. Never drop the old fields.
- **Born with a value.** Created with label `"Group name"` (shown uppercased by CSS), edited in place; no empty state — clearing the field reverts.
- **Frontend** (the list base, `ItemList.tsx` + `GroupBlock.tsx` — see "Shared bases"): the list scans the ordered items and collapses each consecutive same-`groupId` run into a `GroupBlock` row (ungrouped items are lone rows). A `GroupBlock` is one framer `Reorder.Item` in the list's outer `Reorder.Group`, so the group **moves as a block**; a nested `Reorder.Group` inside it reorders members without letting them leave. It's drawn as a left rail with a gray small-caps label. Groups show only in **manual** sort; other sorts flatten and hide them (a sort would scramble the run). A reorder always posts the flat item order (members kept contiguous). Reset-progress-keep-board re-emits `GroupCreated` after all items exist so grouping survives. Client plumbing (the `/api/groups` calls + the pure order/membership updates) lives once in `listOps.ts`, used by `App` (tasks and streaks) and `useShop` (rewards).
- **Gestures** (all in `ItemList`): each ungrouped top-level row shows a **group handle** (⌗) beside its drag handle; pressing and dragging it down the list range-selects a contiguous run (`startGroupDrag`, imperative `.group-selecting` highlight via `elementFromPoint` + `data-item-id`), and release creates (or extends) the group. Dragging an ungrouped row over a group block adds it (only a group *in the same list* is a valid target); dragging a member out past the block ejects it. The move handle overlaps the group handle's right side (z-index), so the bracket is grabbed at its left edge.

### Streaks

A streak is its own entity (not a task flavour), living in a section with `kind: "streaks"`. Tabs are seed-authored, so the Streaks tab is created in `seed.ts`; `ensureStreaksTab` adds it non-destructively to pre-existing DBs.

- **`Streak { id, sectionId, name, type, mode, since, legacy, legacyBest, matcher, groupId?, order?, createdAt, updatedAt }`.** `groupId`/`order` are list structure, exactly like a task's or reward's (see Groups) — a streak's position in its section and the group it's in, if any, both server-derived/stamped in `readStreak`, never evented directly (`StreaksReordered` writes the shared `itemOrder` map, the same mechanism `TasksReordered`/`RewardsReordered` use, rather than splicing the `streaks` array as it once did). `type = "daily" | "weekly" | "counter"`, `mode = "all" | "any"`, `since = "created" | "all"` (see "Settings & period close" below — absent on old events → `"created"`, no migration; the UI labels these **Now** / **All time**). **`legacy`** (int ≥ 0, default 0) is a one-time **backfilled starting value** — the count carried over from before the app (e.g. a whiteboard streak). It's the *pre-app history*, so it's added **only when counting from All time** (`since === "all"`); counting from **Now** starts fresh and ignores it. `legacy` never affects `active`. **`legacyBest`** (int ≥ 0, default 0) is a **separate, non-additive** backfill for the record: `StreakView.best` (daily/weekly only) is **`max(legacyBest, longest satisfied run in the app's whole history)`** — so it seeds a pre-app record the app then only beats. Both are edited only from **Settings → Backfill** (`PATCH /api/streaks/:id { legacy?, legacyBest? }` → `StreakEdited`), carried on `StreakCreated` so reset-keep-board preserves them, and folded in inside `computeStreak`/`computeCounter` so live state and rebuild agree. `best` is computed **unwindowed** (ignores `since`/`createdAt` — it's your all-time-in-app record even for a fresh "Now" streak) by a second walk-back in `computeStreak` bounded to the earliest completion; counters return `best: 0`. (`type` was named `period` until a counter — which isn't a period — was added; the `StreakCreated` event field is `streakType` to dodge the event's own `type` discriminant, exactly like `TaskCreated.taskType`. Old events wrote `period` on `StreakCreated`/`StreakEdited`; both are read as optional legacy aliases and resolved to `type` in the projection, so pre-rename streaks project unchanged with no migration.) `daily`/`weekly` count **consecutive satisfied periods** (from history); **`counter`** is a live **sum of the linked tasks' currently-ticked boxes** — ticking raises it, unticking lowers it — see the compute note below. **Streaks carry no color of their own** — the flame and the form's condition dots inherit the Streaks *section*'s color (passed down as a display-only prop). (Old `StreakCreated`/`StreakEdited` events may still hold a `color` key; Zod strips it on read, so no migration was needed.) Streaks are never stored with a count — `count`/`active` are **derived on read** from completion history and returned as a `StreakView` (`Streak` + `count` + `active`).
- **`matcher` is a discriminated union (`kind`), pluggable by design.** `{ kind: "tasks", conditions[] }` is fully functional: each condition is `{ taskId, required }` where `required` is a **number** ("done at least N times this period") or **`"all"`** (every box, resolved **live** against the task's current box count — so changing a count task's amount later moves the requirement with it). The streak is satisfied in a period when *all* (or *any*, per `mode`) of its conditions are met. **Legacy events stored a bare `taskIds[]`**; a Zod `transform` on read normalises it to `conditions` each requiring one completion (exactly the old "was it done this period?"), so pre-existing streaks project unchanged with no migration. `{ kind: "filter", rules[] }` remains in the union server-side (it needs tags + a filter-AST engine, a `BACKLOG.md` item) but has **no UI** — the form's "Filter (debug)" toggle was removed, so `StreakForm` only ever emits `tasks`. When `filter` is revived and evaluated for real it must follow the security rule: structured AST → parameterised query, never string interpolation.
- **Computation is a pure function** in `packages/contracts/src/streak.ts`: `computeStreak(completions, streak, now, boxCounts, timeZone)`. **`daily`/`weekly` fold completion history**; **`counter` reads current state instead** (see `computeCounter` below) and never touches history. For the history path, it first **windows completions to `streak.createdAt`** — only completions at/after the streak was created count, so a freshly-added streak starts from zero rather than inheriting the linked task's whole past (ISO-UTC strings compare lexicographically; the count stays *derived*, so it's still rebuild-safe). It then buckets those into local **day** (`YYYY-MM-DD`) or ISO **week** keys, tracking the **max level reached** per task per period (`CompletionRecord.count`); a condition is met when the reached level ≥ its `required` (with `"all"` resolved via `boxCounts`, the projection's live box count per task), then it walks backward from `now` counting consecutive satisfied periods — **the current period being unsatisfied is a grace state, not a break** (`active: false` but the count holds); an *earlier* gap breaks the run.
- **A `counter` honours `since`** (`computeCounter(streak, currentLevels, opts?)`): **"Now"** (`since !== "all"`) is the **sum of the linked tasks' currently-ticked boxes** (`behaviorOf(task).filled(task)`, resolved live in `readStreak`) — ticking raises it, unticking lowers it, **every tick moves it by exactly one**, no history/periods. **"All time"** (`since === "all"`) is the **lifetime tick total**: for each linked task, **the level it held each time a period roll unticked it, summed, plus its live level now**. The projection folds that per-task sum as **`bankedLevels`** on every `TasksReset` (the box counterpart of `banked` points — a fold rule, not an event, so a rebuild lands in the same place) and `readStreak` passes it to `computeCounter`. It's honest because a box unticked before its reset was never banked, and an untick now lowers the live part at once. **Counted per reset cycle, never per day** — it used to sum each *day's* level from the day-close snapshots, which counted a tick that stays up across day closes (a weekly task all week, a one-time task forever) once for every day it sat ticked; a weekly workout ticked Sunday read +2 by Monday. Without `bankedLevels` it degrades to the live sum. "All time" adds `legacy` (the pre-app history); "Now" ignores it and starts fresh. Both are lit while non-zero, no `mode`/`required`. Consequence to know for "Now": it can't exceed the total boxes that exist, and a task **already ticked when you link it counts immediately** (no per-streak baseline — a deliberate simplification). Time zone is **always `Asia/Jerusalem`** (`DEFAULT_TIME_ZONE`) — not user-configurable. Period stepping is UTC-noon-anchored for DST safety; capped at `MAX_PERIODS` (4000). Covered by `packages/contracts/test/streak.test.mjs` (the pure functions) and `apps/api/test/counter.test.mjs` (an "all time" counter through real rolls, resets and a rebuild — including the weekly-task double count).
- **Completion history** feeds it: the projection keeps a `completions` list (`{ taskId, occurredAt, count? }`, where `count` is the level reached), appended to on `TaskCompleted`, on `TaskTierSet` when a tier becomes active, and on `TaskProgressSet` when `progress > 0`. Streak events (`StreakCreated`/`StreakEdited`/`StreaksReordered`/`StreakDeleted`) are part of the same append-only log.

Frontend: `StreakForm` (shared add/edit body, wrapped in a `Popover` by the caller) — its task matcher is a **Notion-style condition builder**: condition rows animate in/out (framer `AnimatePresence` + `layout`), joined by a single shared AND/OR connector that reads/writes the streak's `mode` (`all`=AND, `any`=OR; only the first join is an interactive toggle, later joins mirror it). There is no separate all/any control — the connector *is* it. **For a `counter` streak the connector is instead a fixed, non-interactive `+`** (mode doesn't apply — each task tallies independently), the type selector is a third `Counter` pill alongside Daily/Weekly, and the whip links the **whole task**: per-box `×N`/`all` targeting is disabled (`resolveTarget` short-circuits to the row) and no `.cond-req` badge is shown, because any completion counts at its level. Tasks are linked with an **After Effects–style pick-whip** (`.whip-*` classes) — the drag, the line and the row highlight are the shared `usePickWhip` hook (`pickWhip.tsx`), which the Blocked form (Status) reuses to link the task a blocked one waits on; each caller supplies what a point on the board resolves to and what a drop does: `onPointerDown` on the handle starts window pointer listeners that draw an SVG line (portaled to `document.body`, screen-space so canvas zoom/pan needs no correction; neutral slate ink, **not** the streak color) and hit-test with `elementFromPoint().closest("[data-task-id]")` — every `.task-item` already carries `data-task-id`. The line's end snaps to the hovered target, not the row centre: for a **count** task (`supportsQuantity`) hovering a specific box (`[data-box-index]`) links `required: N` (that box's index+1), while hovering the row elsewhere links `required: "all"`; any other task links `required: 1`. The line lands on the resolved box (or `input[type=checkbox]`/first `.tier-dot`). The hovered row is highlighted imperatively (`.whip-target`, amber `.whip-target-dupe` if already linked, red `.whip-target-refused` when the target carries a `refused` reason — shown in a `.whip-refusal` tag beside the line's end, and a drop there does nothing) and the condition is **upserted** on release (re-dropping a linked task updates its amount instead of duplicating). Each condition row shows a `.cond-req` badge (`×N` or `all`) for multi-box tasks. **A streak only counts tasks on its beat** — `streakCanCount(type, section)` (`streak.ts`): daily ↔ a `period: "day"` tab, weekly ↔ `"week"`, a counter anything; any other pairing can't be counted honestly (a weekly task stays ticked all week, so a daily streak would count every day; a daily one is reset before its week's snapshot, so a weekly streak never sees it; one that never resets counts for ever). The form gets `allSections`, refuses such a target ("Daily streaks only take daily tasks") and marks linked tasks a type switch no longer fits (`.cond-row.misfit`, blocking save); the server asserts the same in `createStreak` and in `editStreak` when `type` or `matcher` changes (400 "daily streaks only take daily tasks"). Streaks saved before the rule aren't touched. **Caveat:** you can only whip to a task that's on screen — a task on a panned-away card isn't reachable without panning to it first. The "Filter (debug)" branch is still the inert shell. `StreakItem` is a row on the same shared `ItemRow` base as `TaskItem`/`RewardItem` (see "Shared bases"), rendered inside an `ItemList` by `SectionCard` when `section.kind === "streaks"` — so streaks reorder, range-drag into groups, and drag out of them exactly like tasks and rewards do, through the identical `ItemList`/`GroupBlock` mechanics and the same `groupsApi`/`withOrder`/`withMembership` client plumbing (`listOps.ts`). (Streaks were originally their own bespoke `Reorder.Group` with no grouping at all — draggable-but-not-groupable was a real gap, closed by putting them on the same list base as everything else rather than duplicating drag/group logic a third time.) Edits apply optimistically then reconcile `count`/`active` from the server response, since only the server can recompute the count.

## Settings & period close

**Settings are server truth, not a client preference** (contrast the canvas layout, which is per-device localStorage). The day/week a completion falls in decides streak counting, and the server is the sole authority on time — so timezone and period boundaries live in the event log.

- **`Settings { timeZone, dayStartMinutes, weekStartDay (0=Sun…6=Sat), weekStartMinutes, windDown, pointsFormula, bounty }`** (`packages/contracts/src/period.ts`) — `pointsFormula` (rate + effort presets) is the editable time→% conversion (see "Points formula & rebalancing"); `.default({})` so a pre-feature board parses unchanged with today's values., defaulting to `Asia/Jerusalem`, day start 00:01, week start **Sunday** 00:01 (the Israeli week). A `SettingsChanged` event carries a **full snapshot** (not a delta); the projection keeps the latest. `DEFAULT_SETTINGS` applies until one lands, so a pre-settings board is unchanged. `windDown` (`WindDown { enabled, targetMinutes, leadMinutes, message }`) is a `.default({})` sub-object so a pre-wind-down `SettingsChanged` parses unchanged with the nudge simply off — the screen-off nudge config (see below); `PatchSettingsBody` accepts the **whole** `windDown` object (the command layer shallow-merges the top-level patch, so a partial would drop the untouched knobs).
- **Period keys are pure functions of an instant + settings** (`dayKeyFor`/`weekKeyFor`/`periodKeyFor`). A day key is the local civil date after shifting back by `dayStartMinutes` (so "my day starts at 4am" pushes early hours to the previous day); a week key is the anchor date (`YYYY-MM-DD`) of the most recent `weekStartDay`. These replace the old hardcoded `DEFAULT_TIME_ZONE` and ISO-Monday week in production — **`streak.ts` uses settings-based keys when `opts.settings` is passed, and falls back to the legacy local-day / ISO-week keys when it isn't** (that fallback is what keeps the pure unit tests, which pass no settings, valid).
- **Period lifecycle.** `PeriodStarted { kind, periodKey }` marks the current open period of each kind; `PeriodClosed { kind, periodKey, snapshot }` settles it, freezing **every task's filled-box level at close time**. **Periods are never auto-started** — a fresh or reset board has *no* open period, and `periodStatus(now)` reports that as `due` (`openKey !== currentKey`, which is true when `openKey` is `null`). So the owner consciously **starts** the first day via the prompt (the week starts with it); thereafter it's `due` once `now` crosses into a later period. **Only the day is ever asked about:** `rollPeriod("day")` follows its close with `rollPeriod("week")` whenever the week is due by then (`periodStatus`) — a command-level follow-up of the owner's one answer — and returns that week's recap as `week` (none for a first week, which only starts). With the default boundaries that's ending a week's last day or any later one; with a week boundary off the day's, the week simply waits for the next day's end. **The open day is today until it's ended:** each completion record carries the open `dayKey`/`weekKey` at the time (`recordCompletion`; none open → the moment's own keys, derived at read), `computeStreak` takes the open period as `openKey` — the current period (live levels, grace) and where the walk starts, whatever `now` says — and the recap tally files a tick under the open day. So a tick at 2am before ending yesterday is yesterday's everywhere. `PeriodClosed` drops its period from `openPeriods`, so between a close and the next start (where a week freezes its streaks' start) the clock's period is current, not the one just closed. The web's lock gate agrees: `BoardClock.openDay` reaches `isBoxLocked(entry, now, settings, openDay)`, which, once the clock is past the open day, opens its daily gates and reads a weekly gate as of the open day's last minute. **Gaps are just missing:** days and weeks never opened get no events at all — the stale open day and week close when the owner is back, the current ones open, and anything between reads as nothing done (a recap's empty day shows "—"; streaks count it as a miss). `rollPeriod(kind)`: with an open period it closes it (live snapshot), **unchecks every ticked task in the tabs whose `period` is that kind**, and opens the current one; with **no** open period (fresh/reset) it just opens the current one (nothing to close). It returns a `PeriodRecap` plus recomputed streaks; the client skips the recap card on a first-start. The recap is **the closing period day by day**, from a fold rule (`BoardStore.tallies`, one per kind, started afresh on its `PeriodStarted`, each keyed by the board day an event happened in — `dayKeyFor(occurredAt)`): every tick event (`TaskCompleted`/`TaskUncompleted`/`TaskTierSet`/`TaskProgressSet`) adds the task's value after it less before (so a boost is in it, and an untick of an earlier win counts against its day) to that task's gain, and every `RewardPurchased` its frozen cost under the reward's name then. `recapDay` groups a day's gains by tab (in the tabs' order, with each tab's name and colour): `cleared` = its tasks with a positive gain, `earned` = the net; plus the day's `earned`/`lost` and `purchases`. A day's recap is one `RecapDay` (whatever days it ran over); a week's is each of its seven days (and any later one it ran into). A period's own `TasksReset` is banking, never counted; a deleted task leaves the tally. **Streaks from start to end:** a week's `PeriodStarted` freezes every streak's count (`streaks`) — counted *after* the last week is closed and reset, so a tick still up from it isn't counted for both weeks (computing before the close did exactly that) — and the week's recap pairs the open week's start with the counts frozen on the next start. Covered by `apps/api/test/recap.test.mjs`. **Web:** `Recap.tsx` — pages flipped with Back / Next and dots (a week: days, streaks if any, the Bounty roll if one; a day: one page), the days' tiles popping in on a stagger; `periodLabels.ts` has the date labels the prompt and the recap share (a week's both carry their month). A day's recap is a card over the soft scrim; a **week's is sticky notes on the board** (`NoteWall`): a frosted wash (`backdrop-filter`) fades the board back, the days and the streaks are `.recap-note`s slapped on (framer: in from above, bigger, leaning harder, landing at a fixed tilt per place), and Done sets `leaving` — every `.recap-drop` falls by a CSS animation on the individual `translate`/`rotate` properties (so it adds to framer's transform rather than fighting it) — then closes, and the wash's exit clears. **The board only takes the new day and week once their recaps close**: `App.endDay` shows the day's recap, queues the week's after it (`recapQueueRef`; `closeRecap` shows the next, keyed per period so it mounts fresh), and waits on a promise the last `closeRecap` resolves, then reads tasks, status and Bounties back (fresh — a reroll in the recap may have moved one since the roll), so the new Bounty never shows on the board before its reel lands; the prompt is hidden at once by marking the day (and the week) not due until the real status lands. (It replaced a list of every task with boxes ticked at the close — which, since one-time tasks never reset, grew with every task ever finished.) Missed intermediate periods get no snapshot and correctly read as empty (nothing done).
- **Period reset + banking.** The unchecking is one `TasksReset { taskIds, pointsBanked }` event, committed right **after** `PeriodClosed` (so the snapshot, streaks and recap still see what the period reached). The fold sets each task back to level 0 via `behaviorOf(t).patchForLevel(t, 0)` (the one level→storage mapping) and adds the frozen `pointsBanked` (what those tasks held at that moment, current config) to a `banked` total — and each task's pre-reset level to its `bankedLevels` entry (what an "all time" counter keeps; see Streaks). Points are `live board total + banked − spent` everywhere (`pointsAvailable()` on the server; `App` reads `banked` off `/api/periods/status`, refetching tasks + status together after a roll so the counter never dips). Only a real close resets — a first start or a no-op roll (already current) doesn't. Known limits: a **"Now" counter** (live sum) drops to 0 at each reset of its tasks; a **tier timer**'s elapsed time isn't cleared, so restarting it can re-pick a tier.
- **Why the snapshot matters (the honest-streak fix).** For daily/weekly streaks, `computeStreak` takes a `settled` map (`periodKey → taskId → level`) and, for any settled period, the snapshot **wins outright** over raw completions — so a box checked then unchecked before close reads as 0 and never inflates a streak. Unsettled/legacy periods fall back to raw history (max level reached that period, the original behaviour) — **except the current open period, which reads live state** from a `currentLevels` map (`behaviorOf(task).filled(task)`) the projection passes in. This is load-bearing: raw history never drops (an uncheck doesn't erase the "checked today" record), so without the live read a same-day check-then-uncheck would keep counting. With it, the open period tracks live state (grace), so unchecking today drops it immediately. (Counters were always live via `currentLevels`; this brought daily/weekly in line.)
- **`streak.since`.** `"created"` windows the fold to the streak's `createdAt` (original behaviour); `"all"` drops that window and counts the linked tasks' whole history — trustworthy precisely because settled periods only count what was genuinely done. Counter streaks ignore `since` (they mirror current state).
- **Reset.** `POST /api/reset` → `store.clearAll()` (the only `DELETE FROM events`, on the `EventStore.clear()` added for it) then `initializeBoard`. The web responds with a full reload rather than reconciling piecemeal.
- **Debug clock (`apps/api/src/clock.ts`).** A debug-only override of the server's `now`, so the owner can simulate opening the app at another time (Settings → Debug → pick a time → Refresh). The projection reads `clock.now()` everywhere it needs the present — `periodStatus`/`rollPeriod` defaults, `readStreak`'s streak compute — **and stamps new events with it** (`commit`), so a completion made under a faked time buckets into that day/week and the simulation stays coherent end to end. It's a deliberate backdoor (single-user, self-hosted, never public), **in-memory only** — a restart or a `null` POST returns to real time; it never touches the append-only log's authority beyond the timestamp it stamps. The web fetches `/api/debug/clock` on load and drives the date header from the effective `now`, then reloads after a Refresh so every time-derived read re-computes against the new clock. While a fake time is pinned, a persistent amber **debug badge** sits in the header (both views) showing the pretend time; clicking it clears the pin (`POST { at: null }`) and returns to the real/browser clock — the always-visible "exit debugging" control (the Settings "Reset to real time" button does the same). Pure logic still takes `now` as a parameter — only the projection's *default* source of "now" moved from `new Date()` to `clock.now()`, so the time rule ("never read a global clock inside pure logic") holds.

- **Wind-down nudge (the screen-off pressure).** An optional escalating full-screen overlay that pushes the owner to shut their screens off by a chosen time (see `PRODUCT.md`). **`windDownState(now, settings)`** in `period.ts` is the pure timing curve — minute-of-day civil arithmetic in the board timezone (same style as `isBoxLocked`, a **display gate only**, never scoring): `idle` before the lead window, `ramp` (with a 0→1 `progress`) inside it, `takeover` at/after the target, resetting on its own at local midnight. It deliberately ignores `enabled` — the enabled flag and per-day dismissal are the overlay's concern. **`WindDownOverlay.tsx`** (mounted at `App` top-level, *outside* the view switch so it pressures in board **and** settings) reads the effective clock (`debugNow ?? realNow` + a `pinned` flag) — when pinned it **freezes to that instant so the owner can preview any moment via the debug clock**, otherwise it self-ticks every **1s** so the clock actually ticks. **The full message doesn't show continuously — it pops at configured `displayTriggers`:** a user-editable list of `{ kind: "before", minutes }` and `{ kind: "refresh" }` (defaults 30/15/5 min before + on refresh). On (re)mount the overlay *seeds* — any `before` whose moment already passed is marked fired (no retro-pop) and an `on refresh` trigger pops once we're already inside the window (`phase !== "idle"`); on later 1s ticks a `before` pops as `minutesToTarget` crosses its value. `shownFull` = takeover up now, `hasAppeared` = at least one trigger fired this session (so the candle persists between pops), all re-armed on a day change / reload. **`windDownLeadMinutes(wd)`** (largest `before`) defines the window `windDownState` uses. The panel still **grows** with progress (size/font/backdrop scale from the earliest trigger toward the target) but via **inline `width`/`minHeight`/`border-radius`/`font-size`** — `minHeight` (not a fixed `height`) so the stacked content can't be clipped by the panel's `overflow: hidden` (that was a real cut-off bug); size floors are generous since it pops at discrete moments and never needs to be tiny. The red top line is the **live current time** (`HH:MM:SS`, board tz). Actions stack **centred and vertical**: a large **neutral (not red) Acknowledge** on top, and below it a smaller **red Dismiss for today** that first swaps to an inline **confirm** ("Dismiss until tomorrow?"). **Acknowledge** sets `shownFull=false` — the takeover plays an **echo-trail** exit (the panel streaks toward the corner — `x/y` to ~42vw/44vh, `scale`→0.06 — while two staggered `.wind-down-ghost` copies fade behind it, After-Effects style) and the small **floating candle** (`WindDownClock`) springs in on a short delay; **Dismiss for today** (confirmed) sets `doneDay` (keyed by `dayKeyFor`, so it re-arms next day). Only the panel takes pointer events, so a click on the dimmed board can't dismiss it. The **minimized widget** shows a **burning candle** (`Candle` SVG — wax height burns *down* with `burn` = progress; a flickering flame while there's time, a rising smoke wisp once past) plus the live time, parked by **`useFreeSpot(".hud-anchor")`** — the same gap-finder the points HUD uses, extended with an optional extra-obstacle selector so the widget also dodges the HUD; it pulses a red glow (CSS `box-shadow` keyframe, so it never fights framer's transform) once past the target, click re-expands (`acknowledged=false`), a hover `×` dismisses for the day. `acknowledged`/`doneDay` are in-memory (a reload re-nudges) and re-arm on a day change. Lead time is chosen from **Settings presets (30 / 10 / 5 min before)**. Reduced-motion drops the breathing glow, the growth transition and the clock pulse. **ponytail:** if the window would cross midnight (`target < lead`) the ramp start is clamped to day-start rather than wrapping to the prior evening.

**ponytail:** the walk-back anchors each period at UTC noon before applying the day/week-start offset, so a configured day-start past ~11:00 could misbucket; widen the anchor if that's ever needed (`streak.ts`, `keyForCivil`).

## Frontend architecture

### State & data flow

`App.tsx` owns all server-derived state: it fetches `sections` + `tasks` once on mount and holds them in React state. Every mutation is **optimistic** — update local state immediately, fire the `fetch` in the background — because instant feedback is the whole point of this app (see `PRODUCT.md`). The server is still the authority; local optimism is a UI nicety layered on top.

`SectionCard` renders one board tab and `TaskItem` one row — each a thin *tab kind* on the shared bases (see "Shared bases" below), which own the canvas, the card's move/resize, the sort/display controls, and the list's reorder/grouping. Props flow down, callbacks flow up — no global store; the only React contexts are two thin canvas ones — the **zoom scale** (`useCanvasScale`), which cards read to convert screen-pixel drags into world pixels, and the **canvas settings** (`useCanvasSettings`: snap/grid-size/show-grid), read by `CanvasCard` (snapping) and `BoardCanvas` (grid overlay). If cross-cutting *app data* state grows, introduce a store deliberately rather than prop-drilling further.

### The derived-points pattern (don't regress this)

`totalPoints = computeTotalPoints(tasks)` is the single source of truth for what the tasks hold; the counter shows `points = displayedPoints − shop.spent` (the owner's points after shop purchases — see "Shop"). `displayedPoints = totalPoints − pendingGain`, where `pendingGain` sums the amounts of flyers still mid-flight. So a gain bumps `totalPoints` immediately but `pendingGain` grows by the same amount at the same instant (net-zero visible change), and the counter only catches up when a flyer *lands* and drops out of `pendingGain`. Losses (uncheck, downgrade, delete) have no flyer, so they show instantly; any in-flight flyer for that task is cancelled (`cancelFlyersFor`).

`displayedPoints` is **derived, never separately tracked state.** A previous hand-maintained `displayedPoints` with manual +/- bookkeeping drifted — a fast check/uncheck could get permanently stuck. Keep it derived.

### Client vs server state

- **Server** (via API): everything about *what the board is* — sections, tasks, done state, tiers, points, order, and the shop (its tabs, rewards and purchases). Under the target model, also all history.
- **Client-only** (`useLocalConfig.ts`, `localStorage`): purely-local display preferences that don't belong to the board's shared truth. Today that's each card's **free-canvas layout** (`layouts: Record<id, {x, y, w, h, z}>`) — position, size and stacking order on the whiteboard — plus the **canvas settings** (`settings: {snap, gridSize, showGrid}`, edited via the `CanvasToolbar` on top of the board). This is deliberately per-device: a spatial arrangement tuned for a wide monitor would be nonsense on a phone, so it doesn't sync (owner's explicit call), and how *this screen* snaps/shows its grid is the same kind of preference. Two more per-device preferences persist here the same way (both pure display transforms — the task *order* itself stays server-side so it agrees across devices): **per-tab view prefs** (`tabPrefs: Record<id, {sortMode, display, collapsed?}>` — a tab's chosen sort, its row display toggles and which broken-down tasks have their pieces folded away, for board and shop tabs alike; `display` maps the tab kind's Display option keys to on/off, an absent key falling back to that option's default — see `TabControls.tsx`. Configs saved in the older `{showEstimate, showTimer}` shape are normalised on read into `display: {estimate, timer}`) and the **globally-pinned sort set** (`pinnedSorts: string[]` — which sorts show in a tab's Sort menu without expanding "Show more"; defaults to `["manual", "quick"]` = Recommended + Get done quick). These were briefly component-local `useState` and so reset on reload — persisting them here is what makes them survive reloads/restarts. (The shop briefly lived here too, as a device-local preview under `localStorage` key `board-shop`; once purchases had to really deduct points it moved to the server — a spend another device can't see would make the two disagree about your points. `useShop` clears the stale key on load.) When a real "settings" surface grows, keep this line: anything another device would need to agree on goes to the server; anything that's "how *this screen* looks right now" can stay local. (The server still stores a section *order*, but the web client no longer uses it for layout — see "Board canvas".)

### Component map

`App` owns a top-level **`view`** ("board" | "shop" | "settings"), switched by **`AppNav`** — a slim fixed left rail (Board / Shop / Settings). The board view renders `PointsCounter` (the HUD) + `FlyingPoints` + a `CardCanvas` (name `"board"`) of `SectionCard`s; the settings view renders **`SettingsView`** (server `Settings` editor + reset).

**Shared bases.** Every canvas, tab and row is built on one set of item-kind-agnostic bases, so a feature added to a base lands on the board *and* in the shop (and in any future canvas) at once; a tab kind only supplies what's genuinely its own:

**Shop mode.** "shop" is not a separate place — it's a *mode of the board's* (`shopOpen = view === "shop"`). (A soft grey "cartoon cloud" was tried first and read as off-style.) **`ShopView`** then fades in over the same board frame (`AnimatePresence`): its top is a **`.hud-dock`** slot, and `PointsCounter` passes that selector as `useFreeSpot`'s `dock` — while the slot is in the DOM the HUD sits centred in it instead of free-parking, so the counter flies there on enter and back once ShopView's exit finishes (presence-driven, animated by `.hud-anchor`'s existing transform transition, with a short `docked` delay so it follows the poof). The counter is the same **Points** readout in both modes (board live total − spent, see below); a purchase calls `PointsCounter.spend()` (flinch + red −cost) and `PointsPlate`'s count-up animates the drop. The shop itself is a **second `CardCanvas`** (`name="shop"`) laid exactly over the board's frame (`.shop-layer`, absolute over `main`), holding user-defined **shop tabs** (purely organisational shelves — no behaviour differs between them) as `ShopSectionCard`s — so shop tabs move, resize, snap, sort, display-toggle, reorder and group exactly like board tabs (see "Shared bases"). The two canvases share the device-local config (layouts keyed by card id, canvas settings, tab prefs, pinned sorts) but reset independently. With no shop tabs yet, a centred first-tab form stands in for the canvas; later tabs come from the toolbar's `+`. Because both canvases use the same classes, every shop-mode rule is scoped to the **board** canvas (`[data-canvas="board"]`, or `main`'s direct children for its toolbar/zoom) — an unscoped `.board-card` rule would hide the shop's own tabs.

**Shop (server truth).** Buying **really spends the board's points**: the owner's points everywhere are `live board total + banked − spent`, where `spent` sums every `RewardPurchased.pointsSpent` (and `banked` every `TasksReset.pointsBanked` — see "Settings & period close"). The shop lives in the event log like the rest of the board — `ShopSectionCreated/Edited/Deleted`, `RewardCreated/Edited/Deleted` (edits carry `changes` + `previous`, cf. `TaskEdited`), and `RewardPurchased { rewardId, pointsSpent }`. The purchase **freezes its cost** (the counterpart of the scoring events' `pointsAwarded`), so a later price edit or deleting the reward never rewrites what was paid; deleting a shop section drops its rewards from the projection, but their purchases stay in `spent`. Affordability is checked in `BoardStore.purchaseReward` against the server's own `pointsAvailable()` (sum of `taskPointValue` − `spent`) — the client's disabled button is only a mirror of that. Because spending is its own event stream, **lifetime points earned stay derivable** from the scoring events alone (independent of anything spent) — the hook for levels/XP later. Costs are integer thousandths-of-a-percent like every point value (`> 0`), and a negative total closes the shop (per the spec). Tabs and rewards are the owner's data (nothing named in code). Web side: `useShop.ts` fetches `GET /api/shop` and applies edits optimistically; a purchase is optimistic too (so the drop lands with the animation) but the server's reply — or, if it refused, a fresh read — replaces it. Note the points are still the board's *live* total (no cross-day banking yet — `BACKLOG.md`): unchecking a task takes its points back off, so buying and then unchecking can push the total negative.

On load `App` also fetches `/api/settings` and `/api/periods/status`; when the day is due it shows **`PeriodPrompt`** (a board banner — the day only) and, on confirm, **`PeriodRecapCard`** (`Recap.tsx`) — a day's over a soft scrim, a week's as sticky notes over the whole screen. **`WindDownOverlay`** is mounted at `App` top-level (above the view switch, so it shows in every place) and self-gates on `settings.windDown.enabled` (see "Wind-down nudge"). Deferring the day is session-only (`dayDeferred`), re-offered on reload. Back after a gap, the prompt lists what was skipped since the open day — `skippedSince(status)` (`periodLabels.ts`): the days strictly between the open day and today, and the whole weeks strictly between the open week and this one. Shared primitives, reused deliberately (see `CONVENTIONS.md` "build once"): `Popover` (every inline form), `ConfirmPopover` (deletes), `ActionMenu` (every row's right-click / long-press menu; the actions all kinds share — Edit, Delete — are built once in `rowActions.ts`), `PointsBracket` (the `[%]` text, used by both the row and the flyer so they're identical by construction), `PointsPlate` (the framed count-up % readout — the `PointsCounter` HUD is this plate plus flyer-landing bursts/purchase flinches/placement), `Icons`, `ColorPicker`, `TaskTimer` (the timer, tier-aware only when tiers are passed — see "Task timer"). A `CanvasToolbar` floats in the top-right corner *inside* the board — bare icon buttons (no bar), one per settings group, each opening its own inline popover (the per-tab control pattern). Canvas geometry (grid step, margins, snap, default placement, `placeCards` — saved layout or the tidy default, shared by `CardCanvas` and `BoardSnapshot`) lives in `canvas.ts`. **Settings → Backups** is `BackupSlots` (the list, fetched again whenever `settings.backup` changes — the server may just have taken one; a slot's preview on hover, or on tap for touch, placed beside it and portaled to the body, never taking the pointer) drawing `BoardSnapshot` — a still picture of a board: each tab at this device's layout as a plain card listing `listedByDefault` tasks (`listOps.ts`) as boxes and words, plus its streaks, measured once drawn (cards grow past their set height, as on the board) and scaled down to fit. "Backups to keep" commits on blur (`CommitWholeField`) — saved per keystroke, a passing 1 on the way to 12 could drop all but one. Hooks: `useCanvasScale` (zoom context), `useCanvasSettings` (snap/grid context), `useClickOutside`, `usePickWhip` (link a task by dragging a line onto its row — the streak form and the Blocked form), `useFreeSpot`, `useDiegeticDepth`, `useLocalConfig` (exposing `setCardLayout`, `setSettings`, `resetLayouts`, plus `setTabPref` for per-tab view prefs and `togglePinnedSort` for the global pinned-sort set).

## Frontend implementation lore

These are the traps that cost real debugging time. Each is load-bearing — re-solve before removing.

### Board canvas (`BoardCanvas.tsx` + `canvas.ts` + `.board-viewport/.board-scaler/.board-world`)

The board is a **free whiteboard canvas**, not a flow layout. Three nested elements:

- **`.board-viewport`** — the camera window (`overflow: auto`, fixed height). Native scroll *is* the pan, so it clamps to content for free. **`isolation: isolate` here is load-bearing** (don't remove): cards carry an ever-growing `z-index` (`zCounter`, ~1000+) so the last-touched one floats above its neighbours, but that only matters *among cards*. At 100% zoom framer applies no transform to `.board-world`, so it isn't a stacking context — without the isolate, those z:1000 cards leak to the body level and paint over the fixed HUD (`z:40`) and the body-portaled flying-points layer (`z:200`), so the flyer arcs *behind a tab*. Isolating the viewport keeps card z-indexes self-contained so the HUD and flyer always sit above the board. `touch-action: none` hands *all* touch gestures to our own pointer handlers (the browser's native pan/pinch is off) instead of the browser's page scroll. **One unified gesture** (`onPanStart` + `onGestureMove`/`onGestureEnd`, tracking a `pointers` map): a mouse grabs on the **middle button only** (`e.button === 1`) so left-click stays free for interaction; **touch pans one-finger and pinch-zooms two-finger**. Lifting one finger of a pinch continues as a pan with no jump (`rebaseline` re-seeds the pan/pinch baseline whenever the finger count changes). **Pinch reuses the same `zoom()` helper** as the wheel and buttons (anchored on the two-finger midpoint) — mobile added gesture *recognition*, not a second zoom/pan code path. A gesture must start on empty canvas (a press on a `.board-card` is left to that card's own move/resize stream), so a two-finger pinch with both fingers over a card won't zoom — fine on a margined whiteboard. `preventDefault` on start suppresses the browser's middle-click autoscroll. The grab cursor shows only while actively panning (`.grabbing`), not on idle hover.
- **`.board-scaler`** — sized to the **zoomed** world (`worldW*scale × worldH*scale`, `min-*: 100%`) so the (hidden) native scroll extent represents the zoomed area. Scrollbars are hidden (`scrollbar-width: none` + `::-webkit-scrollbar`) — you pan by dragging, so the bars just read as clutter; scrolling still works via wheel/grab-pan.
- **`.board-world`** — the **unscaled** coordinate space cards live in, scaled by the camera. Flat background (no grid lattice — the owner found it too busy); snap-to-grid still applies, just without a visible guide. **The zoom scale is applied by framer** (`motion.div` with `layoutRoot` and `style={{ scale, originX: 0, originY: 0 }}`), *not* a CSS `transform: scale()`. Both properties are load-bearing: `layoutRoot` makes `.board-world` a layout-measurement boundary — `Reorder.Item`s inside only detect layout changes *relative to each other within this root*, so when the zoom scale on the root changes they don't run a layout animation (which would show as "all card text jumps for ~0.5s"). Without `layoutRoot`, framer re-measures all descendants after a zoom, sees them as "moved" (parent scaled), and springs a phantom correction. Without the `motion.div` (i.e. plain CSS `transform: scale()`), framer's projection tree doesn't know about the scale at all and the same thing happens on every re-render while `scale != 1` — task moved, grid/snap toggled. Origin `0,0` keeps top-left anchoring, which the scaler-sizing and scroll-restore math rely on. Don't revert either without re-solving this.

Camera rules, all in `canvas.ts`: zoom is **clamped** (`MIN_SCALE 0.4 … MAX_SCALE 1`) — 1 is native (a whiteboard; zooming past 1:1 only magnifies, never reveals more), 0.4 pulls back to see more tasks at once. Driven by ctrl/⌘+wheel (trackpad pinch sends exactly that), **anchored on the cursor** (a layout effect restores scroll so the point under the pointer stays put), *and* by on-screen **zoom controls** — a `−` / `%` / `+` cluster floating bottom-right (`.zoom-controls`, a sibling of the viewport like `.canvas-toolbar`, so it stays pinned while panning), for anyone without a wheel/pinch; the `%` chip resets to 100%. Both wheel and buttons share one `zoom(compute, anchor?)` helper in `BoardCanvas` — the buttons anchor on the viewport centre, the wheel on the cursor. The world is just the cards' bounding box + `MARGIN` (220px) of slack — that's the entire reachable area, so the camera can't wander into a void; dropping a card further out grows the world next render. Wheel is attached **non-passively** because zoom must `preventDefault` the browser's own page-zoom.

### Card move & resize (motion values in `CanvasCard.tsx` — every tab on every canvas)

- **Position (`x`/`y` transform) and size (`width`, `min-height`) are framer `useMotionValue`s**, not React state. A drag writes them at 60fps with **zero re-renders**, then on release everything settles via `commit()`: if snapping is on (canvas settings) it lands on the grid (`snap(n, gridSize)`), otherwise it lands exactly where dropped (rounded to whole px) — either way it **springs** to that target (`animate(mv, target, settle)`), so there's no jump between "let go" and "settled". The snap toggle and grid size come from `useCanvasSettings` (see "Canvas settings"). Reading layout via a `layoutRef` keeps the pointer-move closures from going stale mid-drag.
- **Drags are scale-corrected**: screen-pixel deltas are divided by the current zoom (`useCanvasScale`) to become world pixels — without this, dragging under zoom lags or leads the cursor.
- **Resize corners adjust the origin, not just the size.** For a left/top corner (`xSign/ySign === -1`) the edge follows the pointer: `x`/`y` move while `width`/`height` shrink to match. Right/bottom corners just grow. All clamp to `MIN_W`/`MIN_H`.
- **Height is a `min-height` floor, never a hard cap.** A hard cap would need `overflow: auto`, which clips this card's own `position: absolute` popovers (color picker, sort menu, add-task, timer, and the per-row edit/delete popovers *inside* the list). So content taller than the set size grows the card downward instead.
- **Popover placement measures against its clip container, not the window** (`Popover.tsx`, `clipContainer`). Inside the board the clipping ancestor is `.board-viewport` (overflow: auto), which starts *below* the date header — measuring room to the window top made a tall popover open upward into space the header/viewport edge then clipped (the "NAME label cut off" bug). It now finds the nearest overflow ancestor and measures above/below against *that*. Separately, **tall forms opt into `scrollable`** (add-task, add/edit-streak): the panel caps its height to the room available in that container and scrolls internally rather than spilling past an edge. It's opt-in and **off by default** precisely because the shared `Popover` also wraps short popovers that contain their *own* nested absolute popovers (color picker, timer) — giving those an `overflow` would clip the nested one, the same trap as the card cap above. Ceiling of the current model: a card whose content overruns its floor by more than `MARGIN` can extend past the scrollable area — bump `MARGIN`, or measure real card heights for the world bounds, if that ever bites.
- **Last-touched card floats on top.** A module `zCounter` (in `CanvasCard.tsx`, shared by every canvas) hands out increasing `z` on any pointer-down (`focusCard`) and on drag/resize start (`bringToFront`), persisted into the layout — so an active card's popovers are never covered by an overlapping neighbour.
- **`.board-card`'s `motion.section` still has NO framer `layout` prop** — Framer's `layout` runs a `ResizeObserver` and applies corrective transforms to size changes it didn't initiate, which fights the manual pointer-drag move/resize (same root cause that broke the old corner-resize). Don't re-add it without re-solving this.

### Canvas settings (`CanvasToolbar.tsx` + `useCanvasSettings` + `useLocalConfig`)

Per-device knobs for the whiteboard, edited from the `CanvasToolbar` (bare icon buttons floating in the board's top-right corner; one per settings group, each opening its own `Popover` via the shared `popover-anchor` pattern — a `ToolbarGroup` helper wraps that button-plus-popover). Stored in the same `localStorage` config as the layouts (`settings: {snap, gridSize, showGrid}`, defaulted + merged on load so a stale pre-settings config still parses). `App` provides them through `CanvasSettingsProvider`, so both canvases share them; the two consumers read via `useCanvasSettings` — `CanvasCard.commit()` for snap on/off + step, `BoardCanvas` for the dot-grid overlay (a `radial-gradient` background on `.board-world`, sized in world px so it scales with the zoom transform and stays aligned to where cards snap). The toolbar's **grid** group holds those three; its **reset** group runs `CardCanvas.resetPositions()`: it clears **that canvas's** saved layouts (`resetLayouts(ids)` — resetting the shop leaves the board's arrangement alone; each card falls back to `defaultLayout`, a balanced √-based grid arranged from the tab count, optionally pushed down by `topInset`) **and** bumps a `resetSignal` handed to each card in its `CardFrame`. A canvas adds its own toolbar groups through `CardCanvas`'s `toolbar` slot (`ToolbarGroup` is exported for that — the shop's "New tab"). That signal is needed because a card's position lives in framer motion values seeded once from the `layout` prop and deliberately **not** re-synced to it (so a drag isn't overridden mid-flight); an effect keyed on `resetSignal` springs the motion values to the freshly-arranged `layout`. Without the signal, clearing layouts changed the prop but moved nothing — the original "reset does nothing" bug (confirmed by the button inside the popover; device-local, never touches the server). `main` is the offset parent (`position: relative`) and the toolbar is a sibling of `.board-viewport` (not inside the scroller), so it's `position: absolute` in the corner with a `z-index` above the world and stays pinned while you pan.

### List rows (CSS Grid + `subgrid`)

- Rows use grid + `subgrid`, not flexbox, so the `[%]` points column lines up whiteboard-style per tab. `.item-list` (the `ItemList` base) defines `grid-template-columns: minmax(24px, max-content) minmax(0, max-content) 1fr auto` (col1 / value / name / delete); `.item-row` (the `ItemRow` base) is `grid-template-columns: subgrid; grid-column: 1 / -1`. A task row's cells are checkbox / `[%]` / name / trash; a reward row's are emoji / price pill / name+note / trash.
- **Column 1** `minmax(24px, max-content)`: the 24px floor beats a single checkbox's 17px so it sits at the column start with breathing room; `max-content` lets the same column grow for tiered rows' tier-dots.
- **Column 2** `minmax(0, max-content)`, not bare `max-content`. Bare `max-content` ignored container width and blew a long tier bracket (NASA, 4 tiers) past its grid cell, spilling across tabs. `minmax(0, …)` lets it shrink under pressure. That alone wasn't enough — the fix is a **`<wbr/>` per segment in `PointsBracket.tsx`** (built from `percents.map(...)`, not a joined string), so wrapping only ever happens *between* whole percentages, never inside `2.4%`. The `<wbr/>` sits before each `/` separator, so a single-value `[0.5%]` can't split either.
- **`PointsBracket` is shared by `TaskItem` and `FlyingPoints` deliberately** — the flyer must be the row's actual bracket, not a lookalike. See the flyer section.
- Any *direct child* of `.item-row` auto-places into the next grid column in DOM order — adding/removing a real child shifts everything (the handles and the edit-popover anchor are `position: absolute`, so they take no track). Don't revert to flexbox without re-solving alignment.

### Row actions menu (`ActionMenu.tsx`, wired by `ItemRow`)

Right-click on any list row (task, streak, reward) — or a 500ms touch hold, since iOS never fires `contextmenu` — opens a menu of that row's actions. A row kind only declares `actions: RowAction[][]` (groups; separators fall between them; an action with `checked` is one of a set of choices — a `menuitemradio` ticked when current, like a task's Status; an action's `set` names the set it belongs to, captioned once above its first item, so a set reads apart from the actions beside it without a separator line), **Edit first by convention** so right-click → Enter edits; the base does the gestures, placement, keyboard (arrows, Home/End, Enter, a letter shortcut, Esc/Tab closes) and closing (press elsewhere, wheel, resize, blur). Traps, each one real:

- **Portaled to `<body>`, fixed in screen space** — so the canvas zoom doesn't shrink it and neither a card's clip nor the card z-counter can hide it (z 300, above the HUD and flyers). It opens at the pointer and, measured in a layout effect before paint, flips to the pointer's other side where it would leave the window.
- **A portal still bubbles through the *React* tree.** Without the `stopPropagation` on the menu's root, a tap on an item reaches `BoardCanvas` (starting a touch pan) and a right-click inside it reaches the row's own handler (reopening the menu). Keep them.
- **The click that ends a touch hold must be swallowed natively.** React derives a checkbox's `onChange` from the same native click, so `onClickCapture`/`stopPropagation` in React can't stop the tick; `ItemRow` adds a *native* capture listener on the row that kills that one click before it reaches React's root. The same `held` flag ignores the `contextmenu` Android fires after a hold (the menu is already open) and resets on the next press.
- **Right-click keeps its native meaning inside the row's forms and text inputs** (`NATIVE_TARGETS` — so the browser's paste menu still works in the edit form and the inline rename); a hold on the drag/group handles is a drag, not a menu.
- **A tally box's right-click stays "remove one"** — the box stops propagation, so it never reaches the row's handler.
- **Delete goes through the same confirm as the trash button**, which is why `RowRemove` is controlled (`confirming`/`onConfirmingChange` held by the row kind): the menu's Delete and the hover trash open one confirm, in one place.

### Box dots (tiered + count rows)

- Both tiered and count rows render as a strip of checkbox-styled squares (`.tier-dot`) in column 1, driven by the behaviour (`boxes`/`filled`/`levelOnClick`) — whiteboard-accurate (the physical board had a row of boxes). **Styled identically to the real checkbox** (17px, `border-radius: 5px`, white check via `.filled::after`), not small circles — a direct owner correction. Clicking dot *i* resolves a target level: tiered selects that tier (toggle off if already active), count fills to *i*+1 (clicking the topmost ticked box unticks just it); dots fill cumulatively. Each dot carries `data-box-index` (for the streak pick-whip) and, for tiered, `data-label` (the tier label tooltip). (The timer that used to be tiered-only now lives in a generic `.task-footer` on any row when the tab's Timer toggle is on — see "Task timer".)
- The dots are the *only* tier-selection UI — the old labelled `.tier-chip` pills were removed; the label is now a `title` tooltip on each dot.
- **Tier creation and editing reuse the full points builder, one per tier.** A tiered task's tiers each render their own `PointsBuilder` (Duration + Effort → %), as `TierBuilderRow` (in `PointsBuilder.tsx`), **shared by the add form and the edit form** — editing seeds a builder-sourced tier with its saved duration/effort (the same rule as a checkbox task's edit) and keeps the tier count fixed, so it shows no remove control. (The edit form once had its own bare %-per-tier inputs with no builder — a one-off fork that was the bug this sharing closed.) Each tier row carries a stable `id` so its builder's `onPointsChange`/`onMinutesChange` stay stable — those are effect deps in `PointsBuilder`). Each tier's picked duration is stored as `TierDef.minutes`.
- **`TaskTimer` is the one timer component, shown on any row when the tab's Timer display toggle is on** (see "Sort" / Display). It's a plain stopwatch (start/pause/reset/type-minutes, persisted via `PATCH …/timer`) for every task; passing `tiers` + `onSetTier` (only `TaskItem` does, and only for tiered tasks) additionally lights up **tier mode** — auto-advance as elapsed time crosses each tier's threshold, plus a **Submit** that locks in the reached tier. Thresholds come from **`tier.minutes`** (set via each tier's builder), falling back to scraping the tier *label* for legacy tiers; a tier with neither never auto-selects. Trap the stored minutes fix: labels are auto-generated (`"Tier 1"`), so the old label-scrape (`parseTierMinutes`) never matched and the timer never appeared. A non-tiered task passes no tiers, so it shows the stopwatch with no Submit and no scoring effect.
- **`.tier-dots` is `flex-wrap: nowrap`, not `wrap`.** With `wrap`, dots wrapped onto a second line even with room, because a wrapping container's max-content contribution to its grid column is ambiguous. `nowrap` makes it unambiguous.

### Checkboxes

Custom-styled (`appearance: none`), not native, so the tab color shows on the *unchecked* border too (native only tints `:checked` via `accent-color`). Each `TaskItem` sets `--task-color` inline; `App.css` reads it for border + checked fill + white checkmark. If checkboxes look gray, check that custom property, not `accent-color`.

### Completed styling

A done checkbox row looks **disabled**, not struck through: a gray diagonal-hatch `::after` overlay + muted text, zero transition so it snaps in. Deliberately not red/white (read as a warning) and not strikethrough-only. A **multi-box** checkbox gets the same look once every box is ticked (`task.count != null && isDone` in TaskItem's `boxes` branch; its dots dim like the checkbox). **Tiered** rows share that branch but deliberately don't — picking a tier isn't "finished", a higher one may still come.

### Drag & reorder — two separate mechanisms

- **Items within a tab:** framer-motion `Reorder.Group`/`Reorder.Item` (`⠿` handle, hover-reveal) — the `ItemList`/`ItemRow` bases, so tasks and rewards reorder identically. Persists via `PATCH /api/sections/:id/reorder` (tasks) or `PATCH /api/shop/sections/:id/reorder` (rewards).
- **Tabs themselves:** no longer *reordered* at all — they're **freely positioned** on the canvas via the header `⠿` handle (`onPointerDown={startMove}`, see "Card move & resize"), stored per-device in `localStorage`. The old native-HTML5-DnD swap was removed. `PATCH /api/sections/reorder` still exists on the server but the web client no longer calls it (a section's array order now only seeds the *default* placement of a never-moved card and its initial `z`).
- **Drag handle CSS, rule order matters.** The row handle is `position: absolute; left: -16px` on the `position: relative` `.item-row` so it overlaps the padding and never shifts the first cell from flush-left. `.section-drag-handle` overrides that back to static flow **and must appear *after* the base `.drag-handle` rule in `App.css`** (equal specificity → source order wins). If the tab handle "disappears" after touching `.drag-handle`, check rule order first.

### Sort

The Sort and Display buttons are the shared `SortMenu`/`DisplayMenu` (`TabControls.tsx`); each tab kind only declares its options (`SORT_OPTIONS`/`TASK_DISPLAY` in `SectionCard`, `REWARD_SORT_OPTIONS`/`REWARD_DISPLAY` in `ShopSectionCard`) and does its own sorting of its items. Per-tab Sort opens a `Popover` of named options (for tasks: Manual [internally `manual` = drag order], Get done quick, Points ↑/↓, Incomplete/Completed first, **Time short→long / long→short**, Date added newest/oldest), each with a leading icon, checkmark on the active one; with pinning on, only the pinned set (plus the active sort) shows up front, the rest under "Show more". The time sorts key on a checkbox task's `estimateMinutes` (tasks without an estimate sink to the bottom either way; tiered tasks have no task-level estimate so they sink). The chosen sort is a pure client-side display transform, **persisted per tab and per device** in `tabPrefs` (see "Client vs server state") — not board truth.

Beside Sort sits a per-tab **Display** button (every tab kind; a streak tab's only toggle is its add button) → a `Popover` with a vertical checkbox list of view toggles (same reused `Popover`; the app has no `Modal`). For tasks the toggles are **Time estimate** — a small clock + `Xh Ym` beside each **checkbox** task that has an `estimateMinutes` (the badge lives *inside* the name cell so it takes no subgrid column) — and **Timer**, which shows a `TaskTimer` footer on *every* row (a stopwatch on any task; tiered tasks also get auto-advance + Submit — see "Task timer"); both default off. A tab whose allowed types include one that retires when done (today: Tasks, via `once`) also gets **Completed tasks** (default off), which lists its finished one-time tasks again — see the `once` note under "Core types". A tab that recurs and allows a prunable type (today: Daily, Weekly) gets **Pruned tasks** (default off) — see "Prune" under Core types. Every task tab gets **Status** (the bands — see "Status" under Core types), on by default where the tab allows a type that retires when done (today: Tasks), and **Grouping** — the group handle's range-drag and dragging a row into a group (`ItemList`'s `grouping`) — off by default in that same kind of tab and on elsewhere; groups already in the list render either way. For rewards they're **Note** and **Times bought**, both default on. Like the sort, the toggles persist per tab and per device and aren't board truth — how *this tab* is viewed — so **Timer defaults off and the Registry's tiered timer is behind it too** (it was always-on before this unification). (Tiered tasks deliberately show no time-estimate clock for now — they store minutes per-tier for the timer, not a single task estimate.) The only stored order is the manual drag order; dragging is disabled while a non-manual mode is active. Don't add a second persisted per-mode order — considered and rejected.

### Points counter HUD (`PointsCounter.tsx` + `useFreeSpot.ts` + `useDiegeticDepth.ts`)

- Styled as a fixed-width (160px) "bracket" widget — sci-fi corner spans, no glass/blur, no idle motion. This was picked from a live 8-way comparison after two description-based attempts were rejected on sight. **Lesson: for visual-only requests here, if a described CSS change is rejected once, build a live comparison instead of guessing again.** Fixed width so digit-count changes (`9%`→`10%`) don't restretch it.
- **Count-up animation holds a fixed decimal precision for the whole tween**, computed once from the target (`decimalsNeeded`, stored in `precisionRef`), never trimmed per-frame — trimming only the final value made the digit-count change at settle-time read as a jump.
- **Placement is a motion problem, not a positioning one** (this is the 4th design; step 3 was handed to another AI to get right). `.hud-anchor` is `position: fixed` but its position is *computed* by `useFreeSpot`: it measures every card, the add-tab tile, open popovers, and the date header on each layout/scroll change, then places the widget in the gap **nearest screen-centre** (candidates are obstacle edges + viewport edges/centre, not a grid). `findSpot` is exported as a pure function (boxes + viewport + size → `{x,y}`) so it's testable without a DOM. Placement is written straight to `el.style.transform` (never React state — a scroll reflow must not re-render the board); first placement runs in `useLayoutEffect` (no untranslated flash); re-placement smoothed by `transition: transform 0.55s`. Falls back to bottom-centre if there's no clear gap.
- **`.hud-depth` (`useDiegeticDepth`)** owns scroll "inertia" — a damped spring kick against scroll direction, so a fixed element still *feels* like it moves when you scroll. rAF loop self-terminates when motion settles. **A previous pointer-driven 3D tilt was removed** — the owner disliked the widget tracking the mouse. Don't reintroduce cursor-following motion. That's also why the anchor no longer sets `perspective` and depth no longer sets `transform-style: preserve-3d`.
- **Keep the anchor and depth layers separate** — the static position and the animated transform would clobber each other on one element. The `MutationObserver` watches `<main>`, not `body`, so it catches tab/task/popover changes without picking up depth's per-frame transform writes (which would fire it forever).
- **Don't wrap `.hud-anchor` in anything with its own `transform`/`filter`/`perspective`/`will-change: transform`** — that becomes the containing block for `position: fixed` and the widget would scroll away. If ever needed, portal `PointsCounter` through `createPortal(…, document.body)` instead.

### Flying points (`FlyingPoints.tsx`, `flyerTiers.ts`)

Checking a box or picking a tier flies the row's `[%]` bracket into the counter, landing with a scale-pulse + particle burst. This is the app's signature "satisfying feedback" — treat it as high-stakes (see `PRODUCT.md`). There's deliberately **no origin flash** (owner found it noisy).

- **The flyer must read as the row's actual bracket detaching, not a badge appearing.** Four things carry this illusion; it breaks if any one drops: (1) it renders the same `PointsBracket` as the row (identical text incl. `<wbr/>`s); (2) it carries the row's `points-prefix` class so size/weight/figures/colour match by construction — `.flyer` sets only position/pointer-events and must not re-acquire font/colour; (3) it's pinned to the source's exact `getBoundingClientRect()` (left/top/width, not a centre point), overlaying it pixel-for-pixel at `scale: 1`; (4) the row hides its real bracket via `.points-prefix.in-flight` (`visibility: hidden`, so the points column doesn't reflow), driven by `flyingTaskIds` from `App.tsx`.
- **The flight is an arc, not a line:** `x`/`y` animate to a centre-to-centre delta with *different* easings (bends the path); `scale` keyframes `[1, 1.14, 0.72]`; `opacity` holds at 1 until 88% (fading early looked like it dissolved before arriving); `color` animates to the HUD red on a delay so it visibly stops being a board element. Framer reads the *start* colour off the DOM, so only the destination red is named.
- **Landing target is the counter's value text** (`getRect()` returns `valueRef`'s rect), not the box centre — it lands in the gap beside the number rather than merging into it. `getBoundingClientRect` composes the depth transform, so the target is always the widget's real current position mid-drift.
- **Burst particle ids are `uid()`s, never the clock** — two landings in one millisecond (a broken-down task's pieces ticked in a row) gave their particles the same React keys.
- **Finishing a broken-down task celebrates the whole task:** a flyer spawned with `finale` (the tick that finishes its last piece, or its own box) plays one tier above its gain's, never below `surge` (`tierFor(amount, finale)`).
- **Celebration scales with the *gain*, in four tiers, all defined in `flyerTiers.ts`** (`tierFor(amount)`: `spark` <1%, `charge` 1–3%, `surge` 3–10%, `overdrive` ≥10%). Nothing else holds a magnitude number — retune feel by editing that object, not animation code. For a tiered task the gain is `nextPoints − prevPoints`. Deliberately HUD-confined (no page flashes). `tierFor` collapses to `spark` under `prefers-reduced-motion`.
- **`FlyerItem` is a separate component** because per-flyer phase state (`windup` → `flight`) can't live in a `.map()` body. Phase advances in `onAnimationComplete`, which also reports landing — and that callback fires for *every* settled target including the exit fade, so it's guarded by both `useIsPresent()` and a `landed` ref (without them, unchecking mid-flight fires a burst for points being taken back).
- Ghost afterimages get `duration = flight.duration − delay` so a staggered trail lands with the leader; they render the same `PointsBracket`, carry no `exit`/`onAnimationComplete` (only the real flyer may report landing).
- Flight target is **re-measured at launch** (`getTarget` callback), not reused from spawn — a wind-up can last ~1s and the HUD moves itself.
- **Framer trap that bit this for real:** a per-value transition does *not* inherit the parent `duration` unless it opts in with `inherit: true`. `transition={{ duration: 1, x: {...} }}` gives `x` no duration and it silently falls back to the 300ms keyframe default. Every per-value transition now carries its own explicit `duration`. Also: `times` is ignored unless its length equals the keyframe count, and a literal first keyframe snaps — use `null` for "from wherever this value is." (`spark.flight.duration` in `flyerTiers.ts` is the one knob if the snappier sub-1% flight is ever wanted back.)
- Counter box-shake and corner-flare are driven imperatively (`animate()` on a ref'd node), **not** by a remount-on-`key` — remounting `.points-counter` would throw away in-flight particles/shockwaves. Don't give `.points-counter` a `key`, and don't move the anchor/depth transforms onto it.

### Animation convention

When moving an element between screen positions, **animate transform-based `x`/`y` deltas from a static `left`/`top` anchor, not `left`/`top` directly** — learned the hard way on the flyer; framer owns the transform more reliably.

## Security architecture

Security is not a later phase. The app is destined for a shared VPS alongside the owner's other services, so **containment is the priority** and the realistic risk is supply chain, not app logic.

- **Zero outbound network calls, ideally blocked at the container level.** Never add a dependency that phones home, a CDN link, a remote font, or a telemetry/error-reporting service. Keep dependencies few and justified (`framer-motion` is the one deliberate frontend dep).
- **Validate every input at the trust boundary** (the API already does this with type guards — keep it).
- **When user-defined filters/queries arrive** (a `BACKLOG.md` item), they must be structured ASTs compiled to parameterised SQL — never string interpolation, never `eval`, bounded depth/node count.
- **No hard-coded secrets; never log credentials/tokens/key material** — log presence/type only.
- **Run non-root, unpublished DB, resource-limited, no host mounts** when the deploy story lands.
- **Auth: one shared password, no accounts** (`apps/api/src/auth.ts` / `authRoutes.ts`). There is exactly one person who opens this board, so there's no user table — just a password hash + a session secret in `apps/api/data/auth.json` (gitignored, mode `0o600`). The password is set from the terminal (`pnpm set-password`, prompts hidden input, never a CLI arg) — never through the UI, since anyone who could set it wouldn't need to be locked out. `POST /api/auth/login` checks the password (scrypt, timing-safe compare) and, on success, sets an `HttpOnly`/`SameSite=Lax` cookie good for 10 years, whose value is `HMAC-SHA256(sessionSecret, "board-session")` — stateless (no session store to clean up), and re-running `set-password` rotates `sessionSecret`, which **instantly invalidates every previously issued cookie** (the closest thing to "log out everywhere" this model needs). `requireAuth` gates every `/api` route except `/api/auth/*`; the web app's `AuthGate` (wraps `<App/>` in `main.tsx`) shows a login form until `/api/auth/status` reports `authenticated`. This is a deliberate, reviewed step toward the auth this doc used to flag as missing — the server remains the sole authority on points and time regardless. The API still **listens on `127.0.0.1` only** (`index.ts`) so nothing reaches it except through the proxy in front of it (Vite in dev, nginx in production) — the password gate is defense in depth on top of that, not a replacement for it.

The stance underneath all of this: **containment and verifiability over "just trust it."** The owner can't audit the code and self-hosts next to their other services, so the answer to "is this safe?" is architecture (isolation, no outbound, rebuildable state), never reassurance.
