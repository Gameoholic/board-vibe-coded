## Guiding stance

Build this as if it were a SaaS maintained by a large team, not a personal script: reused components, one source of truth per concept, careful modelling over fast hacks, security as a first-class concern. The owner cannot audit every line and is learning this codebase — clarity and consistency are features.

Two principles override convenience everywhere:

1. **Never hardcode the owner's board.** Sections, tasks, task types, and their config are *data over generic primitives*, editable through the UI — never `if (task.name === …)`, never a `WorkoutStreak` class. Details in `CONVENTIONS.md`; it's repeated there because it's the prime directive.
2. **History is sacred — this is a data silo.** We keep everything, forever: when a task was created, completed, edited, and *what it was edited from and to*; the exact points a completion was worth *at the time*. If we ever want a metric, we should already have the raw data and never need a backfill or a guess. This is the target model — see below for where current reality falls short.

## Data & history model

### Where we're going (the target)

A prior attempt reasoned this out carefully and the owner has re-committed to it. The reasoning is captured below (folded in from that attempt's ADRs) so it lives here and isn't re-litigated:

- **Append-only event log.** Nothing is mutated in place, nothing is hard-deleted. Every meaningful action (task created, completed, uncompleted, tier selected, edited, deleted) is an event with a timestamp. Current state is a *projection* derived from the log, cached for speed but always fully recomputable from zero.
- **Frozen values, live classification** (the subtle one — read the reasoning below twice before touching point-recalculation). The points a completion earned are written onto its event and never recomputed, so changing a task's worth later leaves past completions alone. Classification-type attributes (tags, type, the private flag) are read from the task *as it is now*. Both are recorded so an "as it was then" view stays possible.
- **Points as integer thousandths of a percent:** `1% === 1000`. Floats are banned once persistence lands — float addition isn't associative and the rebuild-parity check would fail randomly forever. `%` stays the only unit the user sees.
- **Backend is the only authority on points and time.** The client may compute optimistically for instant UI (it does today), but the server recomputes from its own config and its own clock. Time is always passed into pure logic, never read from a global clock inside it.
- **Persistence lives on the backend** (Postgres on the owner's VPS is the intended target). Everything is server-stored *except* genuine client-only display settings, which may live in `localStorage` (see "Client vs server state" below).

#### The reasoning, in full (why, not just what)

**1 — Append-only, because rebalancing must be non-destructive.** The owner rebalanced the economy repeatedly on the physical board and expects to keep doing it, and asked explicitly to store *everything*: when a task was completed and for how many points *at that time*, when something was deleted, when anything changed. A conventional mutable schema (`tasks.value`, `wallet.balance`) makes rebalancing destructive — change a task's value and every historical completion silently re-prices itself, so last year's good week becomes a different number. So: `events` is append-only, each scoring event freezing its resolved values, every multiplier applied, and the config version in force; definitions (tasks, types, filters, …) are versioned, edits write a new version, events reference the version live at the time; deletes are soft (`deleted_at`, `deleted_reason`) and are themselves events; current state is a projection with a CI parity check. *Good:* rebalances can be simulated against real history before committing; unanticipated analytics stay answerable; undo is honest (it records the reversal, doesn't erase the action). *Costs:* more rows and machinery than CRUD, every read path needs a projection — the owner waived storage as a concern. *Requires:* integer arithmetic (next), and idempotency keys on every write so a retry can't double-count.

**2 — Integer thousandths, because the rebuild must be exact.** Projections rebuilt from the log must equal the cached values *exactly*, and CI asserts it. Float addition isn't associative — `(0.1+0.2)+0.3 = 0.6000000000000001` vs `0.1+(0.2+0.3) = 0.6` — and a rebuild sums thousands of rows in whatever order the query returns; any index change, `WHERE` clause, or parallel aggregate changes that order and the check goes flaky. Separately, affordability (once a shop exists) is an equality test that floats break. So every point value is an integer number of thousandths of a percent (`1% === 1000`); multipliers compose into one factor, applied once, rounded once, half-up; the display layer divides by 1000 at the very edge. (Hundredths aren't enough — a 0.15% task at ×1.3 has nowhere to land and becomes a permanent overpayment. Postgres `numeric` is exact but node-postgres returns it as a string, forcing decimal.js everywhere for no gain.)

**3 — Frozen values vs. live classification, because two requirements pull opposite ways.** Requirement A: every scoring event freezes what applied at that instant, so changing what a task is worth in 2027 leaves the completions already logged untouched — the whole reason the log exists. Requirement B: a saved filter is reused — "change what counts as a workout in one place and every streak/counter/chart updates." Now retag a task that's been `stretch` for three months to also be `workout`: if the event froze its tags, the workout counter ignores those three months forever with no fix short of editing history (forbidden); if the filter reads tags *as they are now*, the counter jumps on its own. The resolution: **scoring values are frozen on the event** (`xp`/`coins`/`minutes`/`tier`, day classification, the resolved multipliers and composed factor, the definition version) and **never recomputed**; **classification is resolved live** from the task's current definition every time a filter runs (`tags`, type, behaviour, effort, `isPrivate`). The frozen snapshot still records `tagsAtTheTime` etc., so nothing is lost and a future "as it was then" mode needs no migration. Consequences worth stating in the UI: retagging changes what past events match (intended — the tag editor should say so), and marking a task private hides its whole history at once (what you want from a privacy flag; the alternative leaks).

### Where we actually are (current reality — be honest about this)

The append-only log is **built and persisted**. `apps/api/src/db.ts` opens a SQLite database (`apps/api/data/board.db`) via Node's built-in `node:sqlite` `DatabaseSync` — one table, `events`, append-only (`INSERT` only, never `UPDATE`/`DELETE`), each row an `id`, `type`, JSON `payload`, `occurred_at`, and a `UNIQUE idempotency_key`. Every event is validated with `BoardEvent.parse` on the way *out* of the row, so a corrupted payload fails loudly instead of poisoning the rebuild.

**Backups (`apps/api/src/backup.ts`).** The API snapshots the database into `backups/` beside it (`apps/api/data/backups/`, gitignored with the rest of `data/`) — a new one once the newest is `Settings.backup.everyHours` old (default 48), keeping the newest `keep` (default 5), the oldest deleted to make room; `enabled: false` takes none. `startBackups(events, () => settings.backup)` checks on boot, every 10 minutes and after any `PATCH /api/settings` that carries `backup` (so a new pace or a switch back on takes effect at once), so a server that was down when one fell due catches up at start. Lowering `keep` deletes nothing until the next backup is taken (the list marks those "goes at the next backup"). It returns `Backups { check, list, preview }` for the routes: `list` is the slots newest first (`BackupSlot { name, takenAt, bytes }`, `takenAt` the file's mtime) and `nextAt`; `preview(name)` reads a backup with `readSnapshot` (`db.ts`: opened read-only, read whole and **closed at once** — an open handle would stop the rotation deleting it on Windows — served as an `EventStore` whose writes throw) and folds it with the same `BoardStore` as the live board: its sections, tasks, streaks (counted as of when it was taken, or its last event if later — a debug-clock board stamps ahead) and `pointsAvailable()`. Only a name the folder holds is read (404 otherwise), so no path is ever built from the request. The snapshot is SQLite's `VACUUM INTO` (`EventStore.backupTo`), consistent even mid-write, written to a `.tmp` name and renamed so a crash can't leave a half file posing as the newest. Filenames are ISO timestamps (`:`→`-` for Windows), so name order is age order; "is one due" reads the newest file's mtime off the **real** clock, never the debug clock. A failed backup is logged, never fatal. Reset (`clearAll`) doesn't touch backups — they're the undo for it. Covered by `apps/api/test/backup.test.mjs` (`pnpm --filter api test`). Same disk as the DB, so they guard against a bad reset or corruption, not losing the host.

`apps/api/src/projection.ts` (`BoardStore`) folds the whole log into current state on boot (`readAll()` → `apply` per event) and keeps that projection in memory for reads. Writes go through *command* methods that build an event, `append` it (idempotency-key aware — a matched key returns the existing event and is **not** re-applied), then `apply` it to the live projection. `apps/api/src/seed.ts` seeds a default board only when the log is empty (`seedIfEmpty`), plus non-destructive migrations for existing DBs (`ensureStreaksTab`; `ensureRegistryTypes`, which sets the Registry tab's allowed types to exactly `{tiered, repeatable}` — older boards were tiered-only, or, older still, had picked up a stray `checkbox`); and `ensureSectionPeriods`, which backfills `Section.period` (`"day"`/`"week"`) onto pre-existing Daily/Weekly tabs so scheduled-box cadence is inferred from the tab; and `ensureFreezerTab`, which gives the board's one-time tab (no `period`, allows a type that retires when done) a Freezer if it has none — see "Freezer"). (There was also an `ensureWeeklyAllowsCount` migration; it was removed when the `count` task type folded into `checkbox` — a checkbox now carries an optional box count, so Weekly needs no extra allowed type. Legacy `count`-type events and boards whose Weekly lists both types normalise to `checkbox` on read; see the task-type note below.) Transport is a thin layer in `apps/api/src/routes.ts`; `index.ts` just wires store → seed → router.

**What the target model still lacks:** frozen point values per scoring event (points are still recomputed live from current config), versioned definitions, soft-delete events (`deleteTask` appends a `TaskDeleted` event but there's no `deleted_reason`/tombstone read model yet), and integer-thousandths points. The owner earns back to those feature-by-feature — **do not silently backfill them into unrelated feature work; each is a deliberate, reviewed change.**

### Auth surface (`apps/api/src/authRoutes.ts`)

- `GET  /api/auth/status` — `{ configured, authenticated }`, unauthenticated. `configured` is false until `pnpm set-password` has ever been run.
- `POST /api/auth/login` — `{ password }`; wrong password → 401, right password → 204 and sets the session cookie.
- Everything below is gated by `requireAuth` (a missing/invalid session cookie → 401 `{ error: "not authenticated" }`).

### Current API surface (`apps/api/src/routes.ts`)

- `GET  /api/sections` — list sections (tabs), in display order.
- `PATCH /api/sections/reorder` — `{ orderedIds }`, must cover all section ids exactly.
- `PATCH /api/sections/:id` — recolor a section (`{ color }` only; name/allowedTypes are seed-authored, not editable via this route).
- `DELETE /api/sections/:id` — **405 by design**; tabs are fixed once created (see `PRODUCT.md`).
- `PATCH /api/sections/:id/reorder` — reorder a section's tasks; `{ orderedIds }` must match that section's task ids exactly. Grouped tasks move as a block, so the client always sends an order that keeps each group's members contiguous (see Groups).
- `GET  /api/tasks?sectionId=` — all tasks, or one section's.
- `POST /api/tasks` — create (never into a Freezer — tasks freeze into one); validates `type` against the section's `allowedTypes`, requires `points` for checkbox (with optional `count`, `estimateMinutes`, `estimateEffort`, and `pointsSource`), takes an optional `priority` for a type that has one (400 for any other — see "Priority"), `tiers` for tiered (each tier may carry its own `minutes`/`effort`/`pointsSource`); an effort that isn't one of the board's levels is a 400.
- `PATCH /api/tasks/:id` — a bundle of independent edits; each present field (`done`, `activeTier`, `progress`, `text`/`points`/`estimate`/`estimateMinutes`/`estimateEffort`/`pointsSource`/`description`/`tiers`/`count`, `timer`, `pruned` — see "Prune" under Core types, `status` + `blocker` — see "Status", `priority` — see "Priority", `parentId` — tuck into a task / take a piece out, see "Break down", `frozen` — freeze or thaw, see "Freezer") is applied as its own command/event (`estimate`/`estimateMinutes`/`estimateEffort`/`description` accept `null` to clear).
- `POST /api/points-formula/preview` — `{ formula }`; a **dry run** returning `{ willUpdate[], wontUpdateCount }` (which builder values would move `old→new`, and how many stay put). No writes.
- `POST /api/points-formula/apply` — `{ formula, rebalance }`; saves the formula (a `SettingsChanged` snapshot) and, when `rebalance`, recomputes every builder value's points via `TaskEdited`. Returns `{ settings, tasks }`.
- `POST /api/tasks/:id/duplicate` — the row menu's **Duplicate**: a new task with the source's *definition* (never its progress — done, tier, ticked boxes, timer), appended as a `TaskCreated` carrying `duplicatedFrom` (history only; the fold ignores it), then placed right after the source (`TasksReordered`) and into its group (`GroupMembersAdded`) in the same command, so the copy never exists anywhere but beside its source. The placement events only follow a copy that was really created (a key-matched retry just returns it). Returns the copy. `taskDefinition(t)` in `projection.ts` is the one list of definition fields — shared with reset-keep-board, so a new definition field is added in one place. A piece's copy is placed among its task's pieces instead (`PiecesReordered`), and a broken-down task's copy comes with copies of its pieces (the web reads those back, since only the server knows their ids).
- `POST /api/tasks/:id/pieces` — `{ texts }` (1–100 names): **Break down** — creates those pieces inside the task (see "Break down" under Core types) and returns the task, then all its pieces. `PATCH /api/tasks/:id/pieces/reorder` — `{ orderedIds }`, exactly that task's pieces (appends `PiecesReordered`).
- `DELETE /api/tasks/:id` — appends a `TaskDeleted` event; the task drops from the projection. A broken-down task's pieces are deleted first, each with its own `TaskDeleted`.
- `GET  /api/groups?sectionId=` / `POST /api/groups` (`{ sectionId, label, itemIds }`) / `PATCH /api/groups/:id` (`{ label?, addItemIds?, removeItemIds? }`) / `DELETE /api/groups/:id` — labeled bundles of a list's contiguous items, generic over item kind: `sectionId` may be a board tab (its tasks) or a shop tab (its rewards) — see Groups. Create validates the members are in that section and ungrouped (the fold gathers them into one run — see Groups); delete ungroups them (items stay). `GET` lists the board's groups; a shop tab's ship with `GET /api/shop`.
- `GET  /api/streaks?sectionId=` — list streak views (definition + computed `count`/`active`), in display order.
- `POST /api/streaks` — create a streak (only in a `kind: "streaks"` section).
- `PATCH /api/streaks/reorder` — `{ sectionId, orderedIds }`. **Registered before `/streaks/:id`** so "reorder" isn't captured as an id.
- `PATCH /api/streaks/:id` — bundle of edits (`name`, `type`, `mode`, `since`, `matcher`).
- `DELETE /api/streaks/:id` — appends a `StreakDeleted` event.
- `GET  /api/shop` — the whole shop in one payload: `{ sections, rewards, groups, spent, inventory, saleStarted }` (shop tabs, rewards with a derived `redeemed` count, `boughtAt` and their list `order`/`groupId`, the shop tabs' groups, the total of every purchase's frozen `pointsSpent`, every item with how many are `owned` and the week's `free` ones left, and whether the weekend sale was started early this week). See "Shop" below. `POST /api/shop/sale/start` starts the weekend sale early for the rest of the open week (400 with no week open, the sale switched off, or already on) and returns the shop.
- `POST /api/shop/sections` (`{ name, color }`) / `PATCH /api/shop/sections/:id` (`{ name?, color? }`) / `DELETE /api/shop/sections/:id` — shop tabs. Unlike board tabs these are user-created and deletable; delete removes the tab's rewards and groups too (past spending stays).
- `PATCH /api/shop/sections/:id/reorder` — `{ orderedIds }`, exactly that shop tab's reward ids (the reward counterpart of `/sections/:id/reorder`; appends `RewardsReordered`).
- `POST /api/shop/rewards` (`{ shopSectionId, name, emoji, cost, note?, kind?, item?, onSale? }` — `kind` defaults to `repeatable`; a `game` reward names its `item` and no other kind has one; `onSale` defaults to whether it's repeatable) / `PATCH /api/shop/rewards/:id` (`name`/`emoji`/`cost`/`note`/`onSale`, `note: null` clears; the kind is set once) / `DELETE /api/shop/rewards/:id` — rewards. `cost` is integer thousandths and must be > 0.
- `POST /api/shop/rewards/:id/purchase` — `{ price? }`, the price the owner was shown: buy at what it costs now (`priceOf` — the weekend sale off it while it's on). **409 `the price changed`** when `price` differs from the server's; **400 `already bought`** for a bought one-time reward; **400 `not enough points`** unless the board's live total − `spent` ≥ the price (checked server-side, never trusted from the client); else appends `RewardPurchased` with the price and its modifiers frozen (and, for an Item reward, its item's grant) and returns the updated shop.
- `GET  /api/settings` — the board's `Settings` (timezone, day-start, week-start). `PATCH /api/settings` — partial patch, logs a full `SettingsChanged` snapshot.
- `GET/POST /api/debug/clock` — the debug clock (see "Debug clock" below). `GET` returns `{ now, real }` (`now` = pinned instant or `null`, `real` = the true clock); `POST { at }` pins the server's `now` to an ISO instant or clears it with `null`. In-memory only.
- `GET  /api/periods/status` — for `day` and `week`: `{ openKey, currentKey, due }` (due = the open period differs from the one `now` falls in), plus `banked` (points kept from tasks the rolls unchecked).
- `POST /api/periods/roll` — `{ kind }`; closes the open period (freezing a snapshot), unchecks that cadence's tabs (banking their points) and opens the current one, returning `{ recap, streaks, week? }` — a week close also banks the week's frost and freezes the tasks that waited too long (`recap.frost`, `recap.frozen` — see "Freezer"), then deals the new week's Bounty reel, in `recap.bounty` (a `BountyStatus`: the reel to stop, nothing rolled yet; `recap.bountyEmpty` when there was nothing on ice to deal — see "Weekly Bounty"). The web only ever sends `day`: ending a day ends its week too once that's over, and the week's recap comes back as `week`.
- `GET  /api/backups` — `BackupList { slots, nextAt }`: the saved backups newest first and when the next falls due (`null` while they're off), real clock. `GET /api/backups/:name` — `BackupPreview { takenAt, sections, tasks, streaks, points }`, that backup's board as saved (404 for a name the folder doesn't hold). See "Backups".
- `GET  /api/bounty` — `BountyStatus { bounties, rerollsLeft, reel }`: the open week's Bounties still to win (each a `RolledBounty`), the rerolls left, and its reel while a Bounty is still to roll (`BountyReel { spots, rolls, multiplier }` — the task names on its spots, in order, and the stops left; else null). `POST /api/bounty/roll` — `{ spot }`; the reel has stopped on that spot: the task the deal put there is a Bounty (400 with no reel to roll on, or a spot that isn't on it); returns `BountyStopped` — the status as it now stands, plus `rolled`.
- `GET  /api/booster` — `BoosterStatus { hand, rerollsLeft }`: the open week's Booster hand (`BoosterHand`, see "Weekly Booster"), null when none was dealt or they're off, and the bought Booster rerolls not yet used. `POST /api/booster/reroll` — `{ taskId }`; rerolls that Booster with a bought reroll (400 when it isn't one of this week's, the hand isn't all picked, there are no rerolls left, or nothing else to deal) and returns the new hand, one card to pick. `POST /api/booster/pick` — `{ card }`; picks that card of the hand (400 with no hand, no picks left, or a card already picked / out of range) and returns the hand with it turned over.
- `POST /api/bounty/reroll` — `{ taskId }`; rerolls that Bounty: it stops being one, and a new reel is dealt without it, good for one stop (400 when it isn't one of this week's, once it's won, while the week's reel still has stops left, with no rerolls left, or with nothing else to roll); returns the `BountyStatus` with the new reel.
- `POST /api/reset` — **destructive**: wipes the event log to an **empty board** (`clearAll()` → `initializeInfra` — settings only, **no placeholder tabs/tasks/streaks and no started period**, so the board then prompts you to start your first day/week). `POST /api/reset/keep-board` — wipes all history/progress but **rebuilds the current tabs/tasks/streaks and shop tabs/rewards** (`reseedFromCurrent`: re-emits their creation events with ids preserved, so streak links survive; done/progress/tier/timer/periods and **purchases** drop, so `spent` restarts at zero alongside the points). Both are the only places the append-only log is cleared; settings actions, confirmed in the UI. (Boot uses `initializeBoard`, which additionally seeds the demo content on a truly fresh DB.)

Every body is parsed through a contract Zod schema before the command layer runs (a `ZodError` becomes a 400 via the error middleware) — that's the trust boundary. Writes accept an optional `Idempotency-Key` header, namespaced per operation, so a retried request is a no-op rather than a duplicate event.

### Core types (`packages/contracts`, re-exported by `apps/web/src/types.ts`)

The contracts package is the single source of truth; the web `types.ts` just re-exports the inferred types. `Section { id, name, color, allowedTypes[], kind, period?, freezerFor? }` where `kind: "tasks" | "streaks"` (defaults `"tasks"`), `freezerFor?` marks a Freezer — the id of the tab its tasks freeze out of (see "Freezer") — and `period?: "day" | "week"` is the seed-authored recurrence cadence (drives scheduled-box daily/weekly — see below — and which period roll unchecks the tab's tasks: Daily + Registry are `"day"`, Weekly `"week"`, Tasks has none and never resets; see "Settings & period close"), `Task { id, sectionId, type, text, done, order?, groupId?, points?, estimate?, estimateMinutes?, description?, tiers?, activeTier?, count?, progress?, schedule?, timer?, pruned?, status?, statusSince?, blocker?, priority?, parentId?, bounty?, paidWith?, frostDays?, tabSince?, waitMs?, waitingSince?, thawBonus? }`, `TaskType = "checkbox" | "tiered" | "repeatable" | "once"`. `estimateMinutes` is an optional estimated duration in minutes for a **checkbox** task, derived from its points builder (a duration was picked); a **tiered** task instead stores its estimate **per tier** (`TierDef.minutes`), since each tier has its own duration. Both are captured from the shared `PointsBuilder` (its optional `onBuilderChange`), persisted like any definition field, and feed the tier timer + the per-tab time display/sort. Alongside them each builder value carries **`estimateEffort`** (the id of the effort level it used; a tier's is `TierDef.effort`) and **`pointsSource: "builder" | "manual"`** — see the points-formula section below. `order` is the server-derived position in its section; `groupId` is set when the task is bundled into a group (see Groups). `description` is an optional free-text note (revealed behind an inline info affordance on the row); it mirrors `estimate` end-to-end — set on create, edited via PATCH (nullable there to clear it), frozen on `TaskCreated`/`TaskEdited` like any other definition field. Streak types are below.

- **Task-type behaviour registry (`packages/contracts/src/taskKinds.ts`).** Every task type shares one shape — *a row of boxes*: `boxes` of them, `filled` currently ticked, a point `valueAt(filled)`. Each type is one `TaskBehavior` entry (`behaviorOf(task)`); consumers read board state through it instead of switching on `task.type`, so **adding a type is one entry here, not edits scattered across the UI** (capability flags like `prunable` and `breaksDown` say which row actions a type gets) (the row render, the running total, the sort orders and the streak counting all pick it up for free). **A checkbox and a "count" (do-it-N-times) task are the same type** — a `checkbox` with an optional `count` box count (default 1); `valueAt = points × filled`, `supportsQuantity: true`. Tiered is one box per tier (`valueAt` = that tier's points, `supportsTimer: true`). **`repeatable`** is the whiteboard tally: a single box completed again and again, storing its completion count in `progress`, worth `points` per completion (`valueAt = points × progress`). It takes an **optional `count` cap** (chosen at creation — blank ≡ unlimited): uncapped it climbs forever and is never `isDone` (the `unbounded: true` flag lets `setProgress` accept any level *unless* a `count` is present, which re-clamps it to `count`); capped it stops at `count`, counts as `isDone` once reached, and `maxValue = points × count`. **Left-click adds one** (`levelOnClick = min(progress+1, count ?? ∞)`, ignoring the box index); **right-clicking the box removes one** (down to 0) to fix a mis-click — that gesture replaced the old "Times done" edit field, which is gone. It's `renderKind: "counter"` — a number-bearing box + an "N" badge — and seed-allowed in the Registry tab alongside `tiered`. **`once`** is the Tasks tab's kind: a task done exactly once and then gone (reschedule the dentist, call grandma). It's `TASK_BEHAVIORS.once = { ...checkbox, supportsQuantity: false, retiresWhenDone: true }` — it scores exactly like a plain 1-box checkbox (same native toggle), but the add/edit forms never offer a box count or scheduled times for it (`supportsQuantity: false`; `CreateTaskBody` also rejects either on a `once` task), and a finished one **leaves its list** (`retiresWhenDone` → `isRetired(task)`). **Retired ≠ deleted:** the task stays in state, still `done`, still worth its points in the live total — it's just not listed. Two derived fold rules in `BoardStore` (`settleDoneChange`/`settleRetired`, run after `TaskCreated`/`TaskCompleted`/`TaskUncompleted`/`TaskTypeChanged`/`TasksReordered`) keep the list base working around hidden tasks: a task that retires **drops out of its group** (a hidden member would split the group's run), and a section's retired tasks **always trail its order** (a stable partition) — so the listed tasks are one contiguous run that `ItemList` can reorder and group without a hidden task stranded inside, and the server's contiguity check never trips on one. They're fold rules, not events, so a rebuild lands in the same place. The client mirrors both optimistically (`App.setLevel`/`addTask` via `listOps.withTrailing`), `SectionCard` filters retired tasks out and appends their ids when posting a reorder (the server wants the whole tab), and `TaskItem` holds a local `retiring` flag so the leaving row (which keeps rendering its last, unchecked props) shows checked + hatched through a short delayed exit (`ItemRow`'s `exitDelay`, `RETIRE_EXIT_DELAY`) before it's tossed off. A tab that allows a retiring type gets a **"Completed tasks"** Display toggle (off by default) — a flat, read-mostly look-back (no drag/group while it's on) where finished tasks show hatched at the end and can be unchecked; unchecking one rejoins the listed run at its end. **Type changes:** `TaskTypeChanged { taskId, taskType, previousType }` is its own event (the type is structural — it decides which fields mean anything — so it isn't a `TaskEdited` field), emitted only by migrations via `BoardStore.changeTaskType`, which refuses a type the section doesn't allow or one that can't hold the task's data (a box count/schedule on a no-quantity type). `ensureTasksTabOnceType` (`seed.ts`) sets the Tasks tab's `allowedTypes` to `[once]` and converts its existing plain checkboxes to `once` (a checkbox with a box count or schedule is left alone rather than losing data). **Known consequence:** reset-progress-keep-board re-creates every task undone, so finished one-time tasks come back. The three render shapes are the one place the row branches: `renderKind(task)` returns `"checkbox"` (native input, count 1), `"boxes"` (a strip — count>1 or tiered), or `"counter"` (repeatable). Because a 1-box checkbox must keep its native `<input>` + `done` toggle while a multi-box one renders as boxes and stores its level in `progress`, **`rendersAsBoxes(task)` and `patchForLevel(task, level)` take the task** (not a constant) and branch on count: count 1 ⇒ native checkbox, `done`/`TaskCompleted`; count > 1 ⇒ box strip, `progress`/`TaskProgressSet`. `levelOnClick(task, i)` maps a box click to a target *filled level* — so `App`'s single `setLevel` handler and `TaskItem` never branch on type. Points live in this shared contract because the **server is the sole scorer**: the projection and the web counter compute from the same functions and so agree by construction.
- **Scheduled boxes (`schedule`)** — a "do this box at a certain hour" gate, duck-typed onto **any checkbox task** (1-box or multi-box), never a task type of its own. `Task.schedule` is an optional array indexed by box, each slot `{ minutes?, dayOfWeek? } | null` with **at least one field set** (`packages/contracts/src/period.ts` → `BoxSchedule` refine; `minutes` = minutes past local midnight, `dayOfWeek` 0–6). Two shapes, two cadences: a **daily gate carries only `minutes`** (no weekday — unlocks at that time every day); a **weekly gate carries a `dayOfWeek`** and *optionally* `minutes` (unlocks on that weekday within the board's week, at the time if given, else from the start of that day — "Friday, any time"). So teeth-plates (count 2) is box 0 → Friday, box 1 → Saturday. So teeth-plates lives in the Weekly tab. The daily/weekly cadence is **inferred from the section's `period`** — `"week"` → weekly scheduling (weekday + optional time), anything else → daily (time only) — so it's read off the *tab*, never a per-task option and never section-name matching. `Section.period` is a **generic seed-authored primitive** (`SectionPeriod` in `domain.ts`, like `kind`): the seed sets Daily→`"day"`, Weekly→`"week"`; a `SectionPeriodSet` event + `ensureSectionPeriods` migration backfill it onto pre-existing Daily/Weekly tabs (name-keyed, which is fine in seed/migration code — cf. `ensureRegistryTieredOnly`). The `SectionCard`/`AddTaskPopover`/`TaskItem` read `section.period` into a `scheduleCadence` prop; the shared `ScheduleEditor` takes that cadence, it isn't chosen in the form. (There's still no daily/weekly *task* type — Daily/Weekly/Registry remain seeded section names, everything non-registry is a `checkbox`, and the period-close system stays global; `Section.period` only informs scheduling today.) `isBoxLocked(entry, now, settings)` is a **pure** function (pure civil arithmetic: minute-of-day for daily, position-within-week for weekly — no timezone-aware instant construction) and a **display/interaction gate only** — the server never rejects an early tick, so it isn't a scoring concern. Persisted like any definition field: sent on create/edit, frozen on `TaskCreated`/`TaskEdited`, and **normalised on read/apply so an all-`null` array collapses to "no schedule"** (`.some(Boolean)`). Applies to `checkbox` only (`supportsQuantity`); meaningless for tiered ladders. Frontend: a locked box (dot, or the single checkbox wrapped in `.checkbox-cell` to stay one grid child) shows a `LockIcon` badge + an "Unlocks …" hint via the reusable **`Tooltip`** component (the box uses `aria-disabled` + a click guard rather than the `disabled` attribute so it still takes hover/focus to reveal the tooltip); an already-ticked box never shows a lock. **Any scheduled box carries the hover tip, not just locked ones** — an already-open timed box reads "For 08:00" so several timed boxes on a row stay distinguishable (`boxTip`). The board's effective `now` + `Settings` reach `TaskItem` through a **`BoardClockProvider`/`useBoardClock`** context (not prop-drilled through `SectionCard`/`GroupBlock`), and `App` re-stamps `realNow` on a **60s interval** so a box unlocks when its time arrives without a manual reload (a debug-pinned time still wins). The add/edit forms share one `ScheduleEditor` (a Daily/Weekly pill toggle + per-box time input, plus a weekday select in weekly mode). **ponytail:** a pathological schedule where a lower box unlocks *later* than a higher one can be filled past via the higher box's cumulative click — acceptable for a personal board; add per-box click clamping if it ever bites.
- **Multi-box checkbox tasks** (`count` 2–100) carry `progress` (0–`count` ticked). Each ticked box is a completion worth `points`; the task is "done" only when `progress ≥ count`. Editing `count` down clamps `progress` in the projection so state stays valid. Set via the `TaskProgressSet` event (`{ taskId, progress, pointsAwarded }`, `pointsAwarded = points × progress`). **`count` was named `target` before the checkbox/count merge**; old `TaskCreated`/`TaskEdited` events (and a retired `count` task type) are normalised on read — `taskType: "count" → "checkbox"`, `target → count` (`count ?? target`) — like the streak `period → type` alias, no backfill.
- **Prune (`Task.pruned`)** — "not this cycle" for a daily/weekly task. `TaskPruned { taskId, periodKey }` records the open period of the task's tab (`Section.period`); `TaskUnpruned` undoes it. The projection keeps them in a side map (`prunedIn`, like the timers) and `readTask` derives `pruned` as *that period is still the tab's open one* — so the roll that opens the next day/week ends it with **no event of its own**, and a rebuild lands in the same place. Eligibility is one rule, `canPrune(task, section)` in `taskKinds.ts`: the behaviour's `prunable` flag (plain `checkbox` only — tiered, tally and one-time tasks aren't) **and** a tab that recurs; never a tab name. `setPruned` refuses anything else, and refuses before any day/week has started. It changes nothing else — done, progress, points and streak counting are untouched (pruning isn't doing). Web: `SectionCard` hides pruned tasks unless the tab's **Pruned tasks** Display toggle is on (then they list dimmed in a look-back `ItemList` of their own under the tab's list — no drag or grouping there — so the rest of the tab still drags and groups; it used to flatten the whole tab, which hid every handle wherever something was pruned); the row menu offers Prune / Unprune and names the streaks pruning would break (`streaksBrokenByPruning` in `pruning.ts`: an unmet daily/weekly condition on the task, in an all-mode or single-condition streak; a weekly streak on a daily task is exempt, since the task is back tomorrow). **Trap:** pruned tasks are the first hidden rows that sit *inside* the listed run (retired ones always trail), so a reorder, an eject, or a new/extended group must keep them in place — `withUnlistedKept` (`listOps.ts`) rebuilds the tab's full order from a list's reorder (see "Status" for the rule, which the bands share), and `runBetween` pulls a hidden task lying inside a new group's span into the group. Pruned styling dims the row's *cells*, never the row — framer owns the row's `opacity` for its enter/exit.
- **Status (`Task.status`, `statusSince`, `blocker`)** — which band of its tab a task sits in: `TaskStatus = "in-progress" | "backlog" | "blocked"` (absent ≡ backlog; the words the owner sees are display labels in `taskStatus.ts`, never these ids). Organisation only: it never touches points, progress or **the tab's order** (how much a task matters is a field of its own — see "Priority"). `TaskStatusSet { taskId, status, previousStatus, note?, blockedBy? }` is the one event — only the owner's own choices are events. The shared pure rules live in `packages/contracts/src/taskStatus.ts` and both sides fold through them: `statusChange` (what a move sets: `statusSince` only when the band really changes; a blocker `{ note?, taskId?, resume }` whose `resume` is the band it goes back to — kept when a blocked task's reason is re-said) and `releasedFrom`. **A task blocked on another is released by a fold rule, not derived at read** (`BoardStore.releaseDependents`, run after `TaskCompleted`/`TaskTierSet`/`TaskProgressSet`/`TaskEdited` once the blocker `isDone`, and on its `TaskDeleted`): it goes back to `resume` for good. Deriving "blocked while the blocker is open" on read looked simpler but is wrong — a *daily* blocker is unchecked again by its day's reset and would re-block it. `setStatus` refuses a blocker that is the task itself, missing, or already done. Reset-keep-board drops statuses (they're state, not definition); Duplicate's copy starts in the backlog. Covered, with rebuild parity and the group-gathering rule, by `apps/api/test/status.test.mjs`.
  - **The bands (web):** the tab's **Status** Display toggle (`SectionCard`; `defaultOn` where the tab allows a type that retires when done — a to-do list, never a tab name) renders `StatusBand`s — In progress (tinted, "in hand N d" from a task's second day there — none on the day it started, its band says it — and a nudge above `IN_PROGRESS_NUDGE_ABOVE`), Backlog, Blocked (folded; only while non-empty) and, with Completed tasks on, a trailing Completed look-back. **Each band is the same `ItemList` over its own tasks** (sorting, reorder, groups — a group whose tasks sit in two bands shows in both), and they share **one grid**: `.status-bands` carries the list tracks (`--list-tracks` in `:root`, the one home also used by `.item-list`) and every band and band list is a `subgrid`, so the `[%]` column lines up across bands. A band's box reaches 8px past the list (`margin: 0 -8px; padding: 0 8px` — a subgrid's margin and padding net to 0 on its edge tracks) so a group's rail sits inside the tint. An empty list's line spans the row (`.item-list > .empty`) — in column 1 it would widen that track for the shared grid. A row moves between bands by the hover `StatusPill` (icons, each named by its `Tooltip` — words hid the name on a narrow tab; the name's end fades under it), the menu's Status choices (`statusActions`, `RowAction.checked` radio items), or dragging onto another band (`ItemList`'s `dropOutside` — below). Blocked opens `BlockForm` (note + the shared pick-whip) on the row; the tab holds which row's form is open, since a drop on Blocked opens it too. `App.setTaskStatus` is optimistic through `statusChange` and adopts the server's stamp; `App.setLevel`/`removeTask` mirror the release (`releasedFrom`) so the waiting task moves in the same render.
  - **Trap — keeping the rest of the tab in place.** A band's list sees only its own tasks, but a reorder must post the whole tab. `withUnlistedKept(oldOrder, listedOrder, inList, moved)` merges: an unlisted task inside its group's run rides with the group; any other stays beside the neighbours the drag *didn't* move (after the nearest one before it, else before the nearest one after it). It needs `moved` from the list (`ItemList` tracks what its drag moves — a row, or a group block's members — and passes it with `onReorder`): framer reorders one adjacent swap at a time, and a swap alone can't say which side moved — anchoring to the old predecessor (the first version) let a dragged row carry the folded Blocked task after it, and guessing the moved side from the orders still drifted by a slot. Checked in the e2e: a Backlog drag leaves the Blocked task exactly where it was.
  - **Trap — one group, two lists.** A group can now render in two lists of one tab, so nothing may find a group by a page-wide `[data-group-id]` lookup: `ItemList` and `GroupBlock` find their list/block from the dragged row (`closest(".item-list" / ".group-block")`), which stays in its list for the whole drag.
- **Priority (`Task.priority`; `packages/contracts/src/taskPriority.ts`)** — how much a task matters among its tab's tasks: `TaskPriority = "high" | "medium" | "low"`, absent ≡ low (`priorityOf`; `PRIORITIES` is the order, highest first). Organisation only, like Status: it never touches points or the tab's order. Which tasks take one is `canPrioritise(task)` — a type whose behaviour `takesPriority` (`once`), and not a piece — never a tab name. **It's a definition field, not state:** it's set through the ordinary edit event, `TaskEdited { changes: { priority }, previous: { priority } }` (`BoardStore.setPriority` → `editTask`; `previous` always names one, Low for a task never given one; refused where `canPrioritise` says no; saying what it already is writes nothing), and `TaskCreated` may carry one — picked in the add form (`CreateTaskBody.priority`; `createTask` refuses it for a type that doesn't take one), or handed on by `taskDefinition` to a Duplicate's copy and to reset-keep-board, unlike a Status. A task made without one has none, and reads as Low. It stays on the task through a freeze and a thaw. Covered, with rebuild parity, by `apps/api/test/priority.test.mjs` and `packages/contracts/test/taskPriority.test.mjs`.
  - **Web.** `taskPriority.ts` is the one home for how a priority looks — `PRIORITY_LOOKS`: its word, its arrows (`PriorityHighIcon`… — three, two, one), its colour (the theme tokens `--pri-high` / `--pri-med` / `--pri-low`) and `onRow` (only High and Medium colour a row: Low is what every task starts as) — and for its menu set (`priorityActions`, captioned like Status's). `SectionCard` hands a row `priority` (`{ onSet }`) where its task takes one and the tab isn't a Freezer; `TaskItem` then adds the set to its menu and wears `priorityInk` on its box (`--task-color`) and, while it's still to do, on its name (`nameInk` — the one line to drop if the name goes plain again). The write is `App.editTask`, optimistic like any edit; the add form picks one with `PriorityField` (the edit form has none — the menu is how it's changed). `TaskCount` (Display → **Task count**, key `task-count`, on by default in a to-do tab) is the line under the tab's title: a number per priority where its tasks have more than one, else "N tasks". **Trap:** it must never have a negative margin — that left the tab's body a few px shorter than its content, so a resized tab's `useOverflows` saw an overflow, turned on the scroll, and cut the count's top off; the header gives up some of its own gap instead (`.board-card:has(.task-count) > .board-card-header`).
  - **The two priority sorts split a list rather than order it** — a `SortOption` with `parts`; see "Sort".
- **Weekly Bounty (`Task.bounty`)** — every week close deals a reel of the tasks on ice, and the owner swings it: the spot it stops on is a Bounty (`Settings.bounty.max` at a time), worth a multiplier until the next close; a Bounty stays in the Freezer until the owner thaws it. The shared rules are `packages/contracts/src/bounty.ts`: `canBounty` (an open task in a Freezer, of a type that's done once, not a piece), `bountyWeight` (1 + whole weeks it has waited — on ice, `waitDays` counts from when it froze), `bountyReel` (each candidate on as many spots as its weight, shuffled, cut to `BOUNTY_REEL_MAX` (48) — every spot is as likely to be stopped on as any other, so the roll leans toward what's been avoided longest), and `rerollSource` (the week's free rerolls first, then bought ones). What a Bounty pays is the `bounty` modifier (see "Modifiers": its own multiplier, else its parent's — a broken-down task's Bounty pays its remaining pieces). A missed or rerolled Bounty just stops being one, wherever it is. `Settings.bounty` is `{ enabled, max, multiplier, rerolls, rollOnWin }`.
  - **The reel is recorded, so a stop is a real draw.** `rollPeriod("week")` on a real close (not a first start), while Bounties are `enabled`, runs `startWeekBounties`: it grants the week's free rerolls, then `dealBountyReel` builds the reel with the store's `random` (a constructor parameter — tests inject one; a rebuild never calls it) from candidates that aren't already a Bounty, and commits it as `BountyReelDealt { periodKey, taskIds, rolls, replaces?, rerollFrom? }` — which spot holds which task settled before any stop, and good for `rolls` stops (`max`, or fewer when there aren't that many tasks on it). `rollBounty(spot)` commits `BountyRolled { taskId, periodKey, multiplier, spot }` with the task the deal put on that spot and `Settings.bounty.multiplier` at the time. The fold keeps one reel a week (`bountyReels`: a new one takes the last one's place): a stop takes its task off it and one from its `rolls`, so the next stop lands on another, and it's gone once none are left. What the owner is shown and swings is `openReel()` — the reel's spots still worth stopping on, a task that has left the Freezer (or the board) since the deal dropped at read time, like `activeBounties` — so the `spot` a stop sends is a place on *that* list, and a reel with nothing left on it is simply no reel. Nothing is a Bounty until its reel has stopped; a reel never swung ends with its week. Any reel (a reroll's, one after a win) also leaves off every task the week has already had (`bountiedIn`, folded from the week's `BountyRolled`s) while enough others are left — otherwise a second reroll could just bring the first one back. The fold keeps each week's Bounties in the order rolled (`bounties`). A week's `PeriodStarted` starts its Bounties, reel and free rerolls afresh — the debug clock can reopen a week, and an earlier run's ended when that run closed (keeping them stacked a second Bounty onto a reopened week). `readTask` stamps `bounty` while its week is the open one and Bounties are enabled, so the next close (or switching them off) ends it with no event (like Prune). **A reroll deals a reel too:** `rerollBounty(taskId)` — refused for a task that isn't one of this week's, a won one, while the week's reel still has stops left, with no rerolls left, or with nothing else to roll — commits a `BountyReelDealt` carrying `replaces` and `rerollFrom`: the fold drops that Bounty at once and spends the reroll, and the reel is good for one stop. `BountyStatus { bounties, rerollsLeft, reel }` is what the recap (`recap.bounty`), `GET /api/bounty`, a reroll and a stop (`BountyStopped`, with the `rolled` one) all return; a `RolledBounty` is the task, its multiplier and other candidates' names to draw a landed reel with (display only, most avoided first). A real week close with Bounties on that deals no reel (nothing on ice) sets the recap's `bountyEmpty`, so the recap can say why. **Before reels** the server rolled each Bounty itself and a reroll was a `BountyRolled` too (`reroll`, `replaces`, `rerollFrom`, no `spot`); those events still fold as they did (a reroll swaps the one it replaces and spends its reroll there) — never drop those fields.
  - **Rerolls are a ledger, so they can be bought later.** `BountyRerollsGranted { count, source: "week" | "purchase", periodKey }`: a week close grants that week's free ones (`Settings.bounty.rerolls` frozen then, so changing the setting mid-week leaves the week alone); `purchase` is the shop's way in (an Item reward's grant — see "Shop"), banked until used, whatever the week. A reroll spends free ones first (`rerollSource`), and the pool it spent is frozen on its `BountyReelDealt` as `rerollFrom`. `rerollsLeft` = the open week's grant less what it spent (a week from before grants were recorded falls back to the setting) + what's banked.
  - **Winning one may roll another.** With `rollOnWin` on, `setDone` follows a win (fewer Bounties left to win than before the command) with `rollAfterWin`: a reel for as many as would bring those still to win back up to `max` — counting any stops a reel already has left, so it only deals when it's owed more — a command-level follow-up, recorded like any deal. Counting "still to win" before and after is what stops an untick-and-retick farming new ones.
  - **Freeze the modifiers on the completion.** `BoardStore.completion(task)` builds every `TaskCompleted` (a tick, the fan-out, `settleParent`) with the task's `modifiers` now (`modifiersOf` — a Bounty's factor, its frost, Subzero) and `pointsAwarded = payout(points, modifiers)`; the fold keeps them as `task.paidWith` while it's done (cleared on untick and by a period reset), and `taskPointValue` pays with them — so the live total, the server's `pointsAvailable` and the web counter all keep a won Bounty's ×2 after it ends, and a rebuild agrees. Completions from before modifiers recorded only a `boost`, read as one Bounty factor (`fromBoost`) — never drop that field. Covered by `apps/api/test/bounty.test.mjs` (the stop decides, a task leaving the Freezer leaves the reel, events from before reels, rebuild with a random that throws) and `packages/contracts/test/bounty.test.mjs`.
  - **Web.** `App.withLevel` mirrors `paidWith` (kept if already ticked); `setLevel` takes a tick's gain as the board total after it less before (so modifiers and a finished task's own points need no separate sums), and plays the `finale` flyer for winning the Bounty too. `SectionCard` pins the open Bounty above the rest of its list (the Freezer's, or its band's once thawed) as a single-row, non-draggable `ItemList` — never by moving it in the tab's order — with both lists on one grid (`.list-stack`, or the band's subgrid). Its bracket, tag and line are the `bounty` modifier's (see "Modifiers"). A Bounty still to win gets "Reroll Bounty" in its menu (`TaskItem`'s `reroll`, from `App.bountyStatus` — `GET /api/bounty`). The reel is `BountyRoll` (`BountyRoll.tsx`): the server's `spots` drawn round and round (so a reel of one or two tasks still spins), its place a motion value **in spots, not px** — the track starts at the reel's middle and is moved by `calc(var(--reel-cell) × −place)`, so nothing is measured and a resize can't knock it off its spot. **Every spot is the same width** (`--reel-cell`; a longer name is cut short until it lands): each spends the same time under the pointer, so a stop is as likely to land on one as on another — with names as wide as their text, long-named tasks were likelier. **The owner swings it:** at rest it waits to be swiped (pointer events on `.bounty-stage`, captured, `touch-action: pan-y`), follows the pointer while it's held, and the swipe's pace as it's let go (px a second over its last `SWING_WINDOW` ms) is the swing. One of at least `SWING_MIN` sends the reel off that way at `SWING_GAIN` × its pace (capped at `REEL_TOP`), for `SPIN_BASE` + `SPIN_PER_SPEED` × that speed seconds, slowing by 1 − (1 − t)^`SPIN_POWER` — which sets off at exactly the swing's speed and covers speed × time ÷ `SPIN_POWER`, so **how hard it's swung is where it lands**; the place is unbounded (round after round) and `cellAt` wraps it onto the drawn cells, which hold the same names a round on, so either direction works and nothing special-cases the wrap. The spot it will stop on is known as it sets off and posted at once (`onRoll`), while it spins there, runs `REEL_PAST` beyond it and springs back (`SETTLE`); it lands only once the server has answered, and the landed name is the server's `rolled` one. **A softer swipe is no swing:** the reel springs back to where it rested and the line under it says to swipe harder — the floor is what stops it being eased onto a chosen name, since even the weakest swing that counts carries it some ten spots (a click, or a swipe the browser took over, is told nothing). **Skip** (and reduced motion, where the reel is never swung and a Roll button stands in) picks any spot and lands at once; a roll the server turns away leaves the reel where it stopped, to be swung again, with a line saying so. Its velocity drives a motion blur, and a listener on it lights the name under the pointer and flicks the pointer as each passes (DOM classes, no re-render). Landing adds CSS rays and framer sparks (in `.bounty-burst`, a box sized for the rays' whole circle — the rays fade out by themselves, `closest-side` so their reach is exact, and no wider than the screen — with fading sides, so nothing is ever cut off in a straight line; the Booster's burst works the same way), a shake and the stamped multiplier. `BountyRolls` (same file) is a reel for each of the week's Bounties — those already rolled drawn landed, then one per stop left, each to be swung once the last has landed — and what a Bounty means; it keeps its own list of them from when it's first shown, so a roll or a reroll (which swaps that one's reel for the new one, keyed afresh so it starts again) changes a reel in its place. Both the recap's page (`BountiesPage`, which holds the recap's way on until every reel has landed; `App` keeps `recap.bounty` as each roll leaves it, so flipping back shows them landed) and the reveal use it. **Mid-week reveal:** `BountyReveal` shows a reel to swing in a card over the board — after a row's Reroll (`App.rerollRevealed`), a win that dealt one for another (`App.revealRolledAfterWin` queues it in `revealNext` until no flyer is in the air, so it never cuts the win's own celebration short), or one left unswung (`GET /api/bounty` has a `reel` on load, or as the recap closes — shown before a Booster pick left over, and never while the day prompt is up). It stays up until its reel has landed — a click beside the card closes it only then; Skip is the quick way through, and a reload brings an unswung one back. The board reads its tasks back when it closes, so the new one isn't given away early.
- **Weekly Booster (`Task.booster`; `packages/contracts/src/booster.ts`)** — every week close deals a hand of the Registry's habits face down; the owner picks a card (`Settings.booster.max` of them), and each picked card's task is a Booster until the next close, adding `Settings.booster.amount` to every tick of it. `canBoost(task, section)` is a type that's `boostable` (a habit you level up: tiered, tally — a `TaskBehavior` flag, so nothing branches on `task.type`) in a tab that recurs (`period`), not a piece — the Registry, read off its settings, never its name. What a Booster pays is the `booster` modifier (a flat; see "Modifiers"). `Settings.booster` is `{ enabled, max (1–3), amount (points) }`.
  - **The deal is recorded, so a pick is a real draw.** `rollPeriod("week")` on a real close (not a first start), while Boosters are `enabled`, runs `dealBooster`: every candidate `shuffled` with the store's `random` (the same injectable randomness as the Bounty's; a rebuild never calls it) and cut to `BOOSTER_HAND_MAX` (9) cards — face down, every task keeps the same chance — committed as `BoosterDealt { periodKey, taskIds }`, which card holds which task settled before any pick. `pickBooster(card)` commits `BoosterPicked { periodKey, card, taskId, amount }` with the task the deal put under that card and the setting's amount then. The owner never sees the order first: `BoosterHand { cards, names, picks, picked, revealed }` lists the hand's tasks sorted by name, and `revealed` (every card's task, in the order dealt) only once every pick is made. The fold keeps each week's hand (`boosterHands`); a week's `PeriodStarted` starts it afresh, and `readTask` stamps `booster` while its week is the open one and Boosters are on — so the next close (or switching them off) ends it with no event, like the Bounty.
  - **Ticks are paid at their modifiers, box by box.** A Booster is the first modifier on tiered and tally tasks, so `TaskTierSet` and `TaskProgressSet` carry `modifiers` like `TaskCompleted` (folded into `paidWith`; cleared at level 0 and by a period reset). `tickModifiers` resolves them when a task's first box is ticked and keeps them while any box stays ticked, so a later tick never re-prices an earlier one (switching Boosters off mid-day leaves that day's run as it was paid). `paidAt(task, filled, modifiers)` (`taskKinds.ts`) is what `taskPointValue` pays: a type whose boxes are each a completion (`eachBoxCompletes`: a count's boxes, a tally's ticks) pays `filled × payout(points, modifiers)` — so +0.5% lands on every tick — and a tier is one completion, `payout(tier, modifiers)`. With no modifiers it's exactly the old `valueAt`.
  - **Rerolls are bought.** A Booster reroll (an Item reward — see "Shop") is `BoosterRerollsGranted { count }`, banked in `bankedBoosterRerolls`. `rerollBooster(taskId)` — once the week's hand is all picked — commits a new `BoosterDealt` carrying `replaces`: the fold keeps the week's *other* Boosters as the hand's `kept` picks, starts the new deal (the Registry less every Booster the week has, the replaced one included) with one card to pick (`reroll: true`), and spends a banked reroll. `boosterOn` reads `kept` and `picked` alike (`weekBoosters`). The web offers **Reroll Booster** in a Booster's menu (`SectionCard.rerollOf`, the same `RowReroll` a Bounty's uses) while rerolls are left and another habit could be dealt, and shows the new hand with `BoosterReveal`. Ticks the old Booster already paid keep their boost (they're frozen in `paidWith`); a habit already ticked today when it becomes the Booster gets the boost from its next first tick (`tickModifiers`).
  - **Web.** The recap's last page (`BoosterPage` in `Recap.tsx`) and a pick left over (`BoosterReveal`, over the board on load when `GET /api/booster` has picks to make — never while the day prompt is up, since ending the day may close the week — and, like the Bounty's reveal, up until its pick has landed: a click beside the card closes it only then) both play `BoosterDeal`: the hand's tasks dealt face up, turned over, stacked, riffled and fanned (framer `animate` on the cards' DOM nodes; a CSS-variable z-order so a hovered card rises above the rest); hovering lifts a card with a purple glow, a click or tap posts the pick, and the card is turned over only with the server's answer — its face set to the task the deal put there, then risen to its slot, flipped with a lilac foil shine, stamped with the boost, sparks and rays behind it. Once every pick is made the rest turn over into a row, in the fan's order, showing what was where. The recap's Done waits for the pick to land. A hand already picked from (Back and forth, or a reload) is laid out where it was (`settle`). **Skip** (`.skip-btn`, shared with the reel's: just under the prompt, out of the flow, and at `opacity: 0` until it's pointed at or focused — like a tab's add button — except under `@media (hover: none)`, a touch screen, where nothing points and it's always shown) passes the deal by: it stops the deal's sequence where it is (the `dealing` flag its steps check), posts a card picked at random for every pick left, and lays the hand out as that leaves it with the same `settle` — so its payoff (stamp, sparks) still plays, and nothing else does. Covered by `apps/api/test/booster.test.mjs` (the card decides the task, ticks and tiers paid with the boost, kept as paid, ended with the week, the hand cap, rebuild with a random that throws).
- **Modifiers (`packages/contracts/src/modifiers.ts`, `apps/web/src/modifierLooks.ts`; the rule is `CONVENTIONS.md` → "Modifiers")** — the generic layer every point-changing mechanic sits on. Four today, in the order a row lists them: **bounty** (a factor: the task's own Bounty multiplier, else its parent's), **frost** (a share: `frostShare`, see "Freezer" — a piece's is its task's, so pieces made after a thaw pay it too), **subzero** (a floor: `Settings.freezer.subzeroMin`, on a task out of the Freezer whose frost is full) and **booster** (a flat: the week's Booster amount — on every tick of a tally, once on a tier; see "Weekly Booster").
  - **What it does is the contract's.** Each entry is `{ id, kind: "share" | "flat" | "factor" | "floor", valueOn(task, ctx) }` — its value on the task now, or `null` when the task doesn't have it; `ctx` is `{ settings, section, parent?, hasPieces?, piecesPaid? }`. `modifiersOf(task, ctx)` lists a task's as `AppliedModifier { id, kind, value }`, and `payout(points, modifiers)` composes them: `max((points × (1 + Σ shares) + Σ flats) × Π factors, highest floor)`, rounded once, half-up, to whole thousandths. The server pays with these (`BoardStore.completion` freezes them on the `TaskCompleted` as `modifiers`, and `tickModifiers` on a `TaskTierSet` / `TaskProgressSet` — folded into `task.paidWith`) and the web renders from the same calls, so the two can't disagree.
  - **A broken-down task is paid as a whole.** Shares and factors split cleanly over pieces, so each piece pays its task's Bounty and frost as it's ticked. A floor doesn't, so it's on the whole task: `modifiersOf` never gives a piece one, and when the last piece finishes the task, `completion` passes `piecesPaid` (what they paid), which goes on the floor as `AppliedModifier.piecesPaid` — `payout` then counts `value − piecesPaid`, so the task's own completion tops the whole up to the floor (a Subzero task broken in three pays its pieces ×3 as you go and the rest of 100% at the finish), and unticking a piece takes the top-up back with that completion. The web passes it the same way only when paying (`App.modifiersNow(…, paying)`). What the whole task shows — its bracket, its frost line, the thaw note, the Avalanche's stamp, the recap's frost — is `wholeWorth(task, pieces)` (`pieces.ts`) at `onWholeTask(modifiers)` (the floor on all of it, without `piecesPaid`).
  - **How it looks is the web's.** `MODIFIER_LOOKS` (`modifierLooks.ts`), keyed by the same ids: `{ tag, color, icon, line(m, points), tagOnIce, fill?, aura?, plainTag? }` — its tag beside the name (`tagOnIce: false` hides it in the Freezer, where frost's would say nothing), its coloured line under the task ("×2 bounty", "+0.8% frost", "=100% subzero", "+0.5% boost" — frost's is the points it adds, not a share), a bar on the line while on ice (`fill`), and an always-on row look (`aura` names an `aura-…` class in `App.css`: Bounty's embers, Subzero's breath and drifting snow, held still under reduced motion; the Booster's is only a purple border — the owner wants its row calm, so it has no wash or moving dots, its tag doesn't glow (`plainTag`; every other aura's tag pulses), and it's left out of the white glint every other aura sweeps over the bracket). `PointsBracket` takes the task's `modifiers` and shows what it pays (`.points-modified`), inked by `modifierInk` — the one modifier's colour, or a gradient across theirs (`background-clip: text`). `TaskItem` renders the tags, lines and auras from whatever modifiers it's handed; `SectionCard.modsOf` hands it a done task's `paidWith`, else `modifiersOf` now (`App.modifiersNow` for the same in `App`). Nothing else names a modifier.
  - **Not a modifier:** the thaw bonus (see "Freezer") — it doesn't change what the task pays, it's paid beside it: `taskPointValue = paidAt(task, filled, paidWith) + thawBonus`.
  - **Prices take modifiers too.** `PRICE_MODIFIERS` (same file, under "Prices") is the list for a reward's price, over the same `Modifier` shape (`valueOn(reward, { settings, now })`) and composed by the same `payout`: `priceModifiersOf(reward, ctx)` and `priceOf(reward, ctx)`. One today, **sale** (a factor of `1 − percentOff/100` while `saleOn(now, settings)` and the reward is `onSale`); its look ("Sale" tag, "50% off" line, `--mod-sale`) is a `MODIFIER_LOOKS` entry like any other. The tag and line are drawn by the shared `ModifierTag`/`ModifierLine` (`ModifierBadges.tsx`), on a task row and a reward row alike.
  - **Tests:** `packages/contracts/test/modifiers.test.mjs` (each kind alone, every pair in the one order, the single rounding, which tasks have which, a done task's frozen value, the sale's window and a price under it) and the rebuild-parity checks in `apps/api/test/bounty.test.mjs` / `freezer.test.mjs` / `booster.test.mjs`.
- **Freezer (`Section.freezerFor`; `packages/contracts/src/freezer.ts`)** — a tab of tasks left waiting. A tab is a Freezer because its `freezerFor` names the tab it freezes out of (never by its name — the code only knows tabs by settings); `seedIfEmpty` seeds one right after Tasks and `ensureFreezerTab` gives an older board's one-time tab one. Its tasks have no status and can't be done — only thawed.
  - **The rules (shared).** The **wait** is `waitMs` (stretches already over) + `waitingSince` (the running one): `waitDays` counts it in the Freezer, the Backlog and Blocked; `waitAcross` (folded into `statusChange`) pauses it going In progress and resumes it leaving — a status change never restarts it; a freeze or thaw does. `freezesAtWeekEnd` (a Backlog task — not In progress, Blocked, a Bounty, a piece or done — that has waited more than `Settings.freezer.freezeAfterDays`) and `willFreezeAtWeekEnd` (the same, at the coming close). `freezeRefusal` says why one can't be frozen by hand (a piece, a Bounty, Blocked, done). **Frost** is whole banked days on ice (`frostDays`): `frostShare` = days × `frostPerWeek` ÷ 7, capped at `frostCap` (% of the task's own points, so it never compounds); `isFullFrost` is Subzero; `frostFill` is 0–1 for bars and effect sizes. `Settings.freezer` is `{ freezeAfterDays: 7, frostPerWeek: 20, frostCap: 200, subzeroMin: 100%, thawBonus: 0.5% }`.
  - **Events.** `TaskFrozen { taskId, sectionId, waited? }` (`waited` only when a week close froze it), `TaskThawed { taskId, sectionId, thawBonus? }`, `FrostBanked { periodKey, through, tasks: [{ taskId, days }] }`. `setFrozen` (`PATCH /api/tasks/:id { frozen }`) refuses a tab with no Freezer, `freezeRefusal`, and thawing a piece on its own (it thaws with its task); a thaw stamps `Settings.freezer.thawBonus` only when the task has frost. `createTask` refuses a Freezer; `setStatus` and `setDone` refuse a frozen task.
  - **Fold.** `TaskFrozen` puts the task at the end of the Freezer's order, out of its group; it and its pieces take the Freezer's `sectionId` and a fresh `tabSince` and wait, and lose status, blocker and thaw bonus. `TaskThawed` puts it at the top of its tab, In progress (so its wait is paused), with its `thawBonus`. Frost is banked only at a week's end, from a side map like Prune's: `frostFrom` (the day each task's unbanked frost runs from — the open day it froze, a day not yet ended still being today) is set on a freeze, dropped on a thaw (that week's days are lost: frost stops the moment it thaws), and moved past `through` by `FrostBanked`, which adds the days to `frostDays`. The thaw bonus counts while the task is In progress or done; `statusChange` drops it for good when it leaves In progress, and a refreeze clears it so a later thaw can pay it again.
  - **The week close** runs `PeriodClosed` → `TasksReset` → `PeriodStarted` → `bankFrost` (one `FrostBanked` for everything on ice, through the closing week's last day) → `freezeWaiting` (a `TaskFrozen` per task over the limit) → the Bounty reel — so a task frozen at the close gathers frost from the new week's first day, and is on the reel at once. Both return recap entries: `RecapFrost` (each task whose frost grew: points and fill before → after, and whether it just went Subzero) and `RecapFrozen` (each task the close froze, and how long it waited).
  - **Web.** `SectionCard` finds a tab's Freezer with `freezerOf` and gives its rows a Freeze action (F; disabled with the refusal in red, or warning that it takes back the thaw bonus); in the Freezer (`freezer-card`) the checkbox is a thaw button (its `Tooltip`, opening from its left edge — `align="start"`, so it stays on the card — says "Thaw now and get +0.5% for starting it" when it has frost), a frosted task has a line under its frost with the thaw bonus (`TaskItem`'s `onIce.thawBonus`, the task's own row only — not a modifier, so it's drawn beside them in `.thaw-line`'s orange), the menu is Edit / Thaw (its note "Start now for +0.5%", plus what it'll pay out of the Freezer when that's more) / Reroll Bounty / Delete, there's no Status, Completed or add button, and only the Bounty's tag shows. `App.setTaskFrozen` moves it optimistically, then reads tasks back; a thaw flies its bonus to the counter (`thaw:<id>` flyer) and plays `thawFx`, and finishing a frosted task or a won Bounty plays `finishFx`. `AgeChip` is the wait beside the name (days, then weeks, then months; Display → **Age**, on by default in the Freezer and in a tab of one-time tasks) with its hover lines; the row's Status pill sits over the end of the name's line, so the chip marks the row `age-peek` while the pointer is over its spot and the pill steps aside — except where the pill itself is: there the pill wins, so a long name pushing the chip under it can't hide its buttons. Recap: a Frost page and a Frozen page after the streaks, and `NoBountyPage` when `bountyEmpty`. Streaks never link a one-time tab's tasks (`streakRefusal`).
  - **Effects (`freezeFx.ts`, sizes in `freezeFxTiers.ts`).** Drawn on their own body layer (`.freeze-fx`, z 190, under the flyers, never taking the pointer) with framer's `animate()`; a row is only touched through a class (`fx-shiver`, `fx-hold`, `fx-pulse`) whose keyframes use the individual `translate`/`scale` properties, so they add to framer's transform. `frostTierFor(fill)` picks none / **Crack** / **Shatter** / **Avalanche** (Subzero); every magnitude — shard counts, rings, the slam, the snowfall — lives in `freezeFxTiers.ts` (the `flyerTiers.ts` rule), and reduced motion skips them.
  - **Tests:** `apps/api/test/freezer.test.mjs` (the migration by settings, freeze/thaw and their guards, the wait clock, the week-end freeze — over the limit, at it, In progress, Blocked — frost banking from the day it froze and a mid-week thaw's lost days, the thaw bonus, Subzero, each with rebuild parity) and `packages/contracts/test/freezer.test.mjs`.
- **Break down (`Task.parentId`)** — a one-time task split into pieces that sit inside it, one level deep. Only a type whose behaviour `breaksDown` (`once`) can, and never a piece (`canBreakDown`); pieces are tasks of that same type. The shared rules are `packages/contracts/src/pieces.ts`: `newPiecePoints` (the task's own points split evenly across the new pieces by `splitPoints` — on hundredths, remainder to the first pieces, so they always sum exactly; once its own points are all in pieces, a new piece is worth an average existing one) and `doneFromPieces`.
  - **Events.** A piece born by Break down is a `TaskCreated` carrying `parentId`; `breakDown` also moves the task's own points into them with a `TaskEdited { points: 0, pointsSource: "manual" }` (manual, so a formula rebalance never hands its old value back on top of the pieces'). Tucking a task in, or taking a piece out ("Make it its own task"), is `TaskParentSet { taskId, parentId | null, previousParentId }`; reordering pieces is `PiecesReordered`. `setParent` refuses a parent that is a piece, finished, in another tab, the task itself, or full (`PIECES_MAX`), and a task that has pieces of its own.
  - **Order: a task is a list of its pieces.** Pieces aren't items of their tab's list — they're ordered in `itemOrder` under their task's id (`listOf(t) = t.parentId ?? t.sectionId`), so the tab's order, `reorderTasks`' permutation, groups (`sectionItems` leaves pieces out; a tucked task leaves its group) and the retire/gather rules never see them. Taken out, a piece lands right after the task it left, then the tab's rules settle (`settleGroups`, `settleRetired`).
  - **Done follows the pieces — as events.** `settleParent` runs after every command that changes a piece (tick, untick, delete, tuck, take out, a piece's copy) and commits the task's own `TaskCompleted` (its own points frozen on it, like any completion) / `TaskUncompleted` when `doneFromPieces` disagrees with it — so the task retires, releases what waits on it and counts for streaks through the ordinary rules. A command-level follow-up rather than a fold rule because it's a scoring moment. The task's own box is all its pieces at once: `setDone` on a task with pieces ticks (or unticks) each piece instead, then settles. Reset-keep-board re-creates each task's pieces right after it (from its piece order). Covered by `apps/api/test/pieces.test.mjs` (rebuild parity included) and `packages/contracts/test/pieces.test.mjs`.
  - **Web.** `SectionCard` lists only the tab's own tasks (`topTasks`) and hands each one that can break down a `RowPieces` (its pieces, fold state, callbacks); `Pieces.tsx` draws the strip, the "1 of 4 · Next: …" line (the next open piece that isn't blocked, plus "· N blocked"), the pieces (a `Reorder.Group` of ordinary `TaskItem`s inside the task's row, a second grid row on the same four tracks — not a subgrid, whose indent would widen the tab's first column) and the Break down entry (typed pieces wait there with `newPiecePoints` shown, created together on Esc / empty Enter / a click elsewhere; its pick-whip tucks a task in). A piece's menu has Make it its own task and `pieceStatusActions` (Blocked / Unblock — a piece has no band). `App.setLevel` fans a task's own tick out to its pieces and `settleParents` mirrors `settleParent`; the tick that finishes a task spawns a `finale` flyer (see Flying points) whose bracket shows everything that tick won. Which tasks' pieces are folded is a per-device tab pref (`TabPrefs.collapsed`). Ticking the task's own box in the UI doesn't send the fan-out: `TaskItem` ticks its open pieces one by one, `PIECE_CASCADE_MS` apart (timers read the row's latest state through a ref, and stop if it unmounts), so each pays and flies on its own. Whichever tick finishes the task sets its `retiring` to `"finale"`: the `.finishing` animation (the rail fills up, the box pops with a ring) and a longer `FINALE_EXIT_DELAY`; the leaving row renders its pieces ticked, since its frozen props are from before the last tick.
  - **Trap — rows inside a row.** A piece is an `ItemRow` inside its task's `ItemRow`, so a right-click, a hold and `:hover` all reach both. `ItemRow` ignores a right-click or hold that started in a nested row (`fromNestedRow`), and the row hover rules match only the innermost hovered row (`.item-row:hover:not(:has(.item-row:hover))`, with `>` to the row's own handles, trash and pill).

### Points formula & rebalancing (`packages/contracts/src/pointsFormula.ts`)

The builder turns a task's time into a `%`: **`% = hours × ratePercentPerHour × effortMult`**, rounded to 2 decimals. Both the rate and the effort levels live in **`Settings.pointsFormula`** (`{ ratePercentPerHour: 2.5, effortLevels: [{casual, Casual ×0.75}, {normal, Normal ×1}, {grind, Ugh ×1.5}, {dread, Dread ×2.5}] }`, names and multipliers editable), so the formula is board-wide server truth, not a builder constant. `pointsFromMinutes(minutes, effortMult, formula)` is the one scorer — the projection and the web builder both call it, so they agree by construction (same rule as `taskKinds`).

- **Provenance per value.** Each builder value (a task's own points — checkbox, one-time or tally — or each `TierDef` of a tiered one) stores **`pointsSource: "builder" | "manual"`** plus the inputs that produced it — `estimateMinutes`/`minutes` and `estimateEffort`/`effort` (a level's `id`; absent ≡ `DEFAULT_EFFORT_ID`, Normal). `pointsSource` is the builder's own report: `"builder"` while the current `%` still equals what its duration+effort produce at the live formula, `"manual"` the moment you type a different `%` (or pick no duration). It's **stored, never re-derived from the current formula** — otherwise declining a bulk rebalance (or a rate change) would silently flip an untouched value's provenance. `resolvePointsSource` returns the stored flag if present, else derives **once against the historic formula** (2.5%/hr, Normal ×1 / the old Challenging ×1.5 — pinned as `HISTORIC_POINTS_FORMULA`, not read off the defaults, so retuning a default can't reclassify anything) — the only formula pre-feature values were ever created under; `readTask` fills this so the API always returns a concrete source. (This is how the pre-feature Daily/Weekly tasks whose `estimateMinutes` was backfilled read as `builder`.)
- **Rebalance.** Changing the formula in Settings → `previewFormula(formula)` (dry run) → the **`RebalanceConfirm`** card (soft scrim; says what saving does, then a scrollable capped-height `old→new` list grouped by tab, rises green and drops red, + a *will-update* / *won't-update* count — counted in values, so a tiered task's tiers count one each, which is why its copy says "prices", not "tasks"). **Reprice** → `applyFormula(formula, true)`: recompute every `builder` value's points from its stored `minutes`+`effort` at the new formula, via `TaskEdited` (each re-stamped `pointsSource:"builder"`). **Only new tasks** → save the formula for future tasks only. **Cancel** → nothing. `manual` values and estimate-less values are never touched.
- **History stays honest.** Rebalancing edits a task's *current* points only; completion/tier/progress events already froze their `pointsAwarded`, so a future "% ever earned" tally reads those frozen values — old completions keep the points they earned. This is why storing frozen awards on the scoring events (already done) matters even though the live total still recomputes from current config.
- **Effort levels are stored by id, edited in place, and rebalanced too.** A value stores its level's `id`, so editing Ugh's multiplier and applying rebalances every value on Ugh, exactly like a rate change, and renaming one touches no task (the level first named Grind is Ugh now; its id is still `grind`). Their order is the scale, lightest first — what the effort sorts rank by (`effortRank`). The server refuses a formula that adds, removes or reorders levels (`assertSameLevels`) and a task or tier on an unknown one (`assertEfforts`); add/remove would need a UI and a rule for the tasks on a removed level, neither built.
- **Before levels had ids** there were exactly two, stored as a *place* in the list (`estimateEffortIndex`, a tier's `effortIndex`). Old events keep those fields: `TaskCreated`/`TaskEditFields` accept `estimateEffortIndex` and a stored tier is a `StoredTierDef`, and the projection resolves them with `legacyEffortId` (0 → normal, 1 → grind) — like `target` → `count`, no backfill. A stored pre-id formula (every board seeds one) is read into the four levels by `PointsFormula`'s preprocess, each old multiplier kept on the level it became (a tuned Challenging ×1.3 becomes Ugh ×1.3), so no task's points move. Tested in `apps/api/test/effort.test.mjs`.

### Groups (labeled bundles of a list's contiguous items)

A **group** bundles a contiguous run of a section's items under one label — the generic primitive behind "group my tasks" (morning / meds / evening …), never a hardcoded group. It's **list structure, not task structure**: the same groups work over a board tab's tasks, a streaks tab's streaks, and a shop tab's rewards (`sectionId` is whichever tab it's in). `Group { id, sectionId, label }`; it carries no scoring and has **no position of its own** — its place is wherever its members sit. Membership lives on the items (`task.groupId` / `streak.groupId` / `reward.groupId`).

- **Order.** The projection keeps `itemOrder: Map<sectionId, string[]>` — each section's item id order (and each broken-down task's piece order, under the task's id — see "Break down") (board, streaks, and shop tabs alike; ids are distinct), the single source of order (`TaskCreated`/`StreakCreated`/`RewardCreated` append, `TasksReordered`/`StreaksReordered`/`RewardsReordered` replace it). Each read item is stamped with an `order` index; the web sorts by it and builds the render rows. (Streaks joined this in the same change that gave them groups — before it, `StreaksReordered` spliced the `streaks` array directly; now it's list structure like everything else, ordered the same way tasks and rewards are.)
- **Written once over any item kind.** `BoardStore.sectionItems(sectionId)` returns the live items a section lists (its tasks, its streaks, or its rewards — branching on the board section's `kind`) and `allItems()` every groupable item (tasks + streaks + rewards); the group commands validate against the former and the fold tags/untags over the latter — no per-kind copy.
- **Contiguous by construction.** After anything that can change a list's order or a membership (`TasksReordered`/`StreaksReordered`/`RewardsReordered`, `GroupCreated`, `GroupMembersAdded`), the fold gathers each group's members into one run at its first member's place (`BoardStore.settleGroups` over the pure `gatherGroups` in `packages/contracts/src/listOrder.ts`; the web mirrors it with `listOps.withGathered` in `App`'s reorder/group updates). This replaced a contiguity *check* on create: with Status bands, a run the owner groups in one band can have another band's tasks between its members in the tab's full order, and they're simply gathered out of the way. Consequence: `duplicateTask` adds the copy to its group **before** placing it beside its source — placed first, an ungrouped copy beside a middle member would split the run and be pushed past the group's end.
- **Membership on the items.** `GroupCreated { groupId, sectionId, label, itemIds }` tags each member's `groupId` (validated on create: members exist, are in the section, and are ungrouped). `GroupMembersAdded/Removed { addedItemIds / removedItemIds }` extend/shrink it. `GroupEdited` relabels (carries `previousLabel`, self-describing like `TaskEdited`). `GroupDeleted` clears `groupId` on its members — deleting a group **ungroups** its items, it doesn't remove them; a group left with no members is pruned on item delete (`dropGroupIfEmpty`), and a deleted shop tab drops its groups.
- **Member-id rename (history).** The member fields were `taskIds` / `addedTaskIds` / `removedTaskIds` when only tasks could be grouped. New events write the `item` names; the old ones stay optional in the schema so logged events still parse, and the fold resolves `itemIds ?? taskIds` — the same pattern as the streak `streakType ?? period` rename. Never drop the old fields.
- **Born with a value.** Created with label `"Group name"` (shown uppercased by CSS), edited in place; no empty state — clearing the field reverts.
- **Frontend** (the list base, `ItemList.tsx` + `GroupBlock.tsx` — see "Shared bases"): the list scans the ordered items and collapses each consecutive same-`groupId` run into a `GroupBlock` row (ungrouped items are lone rows). A `GroupBlock` is one framer `Reorder.Item` in the list's outer `Reorder.Group`, so the group **moves as a block**; a nested `Reorder.Group` inside it reorders members without letting them leave. It's drawn as a left rail with a gray small-caps label. Groups show only in **manual** sort; other sorts flatten and hide them (a sort would scramble the run). A reorder always posts the flat item order (members kept contiguous). Reset-progress-keep-board re-emits `GroupCreated` after all items exist so grouping survives. Client plumbing (the `/api/groups` calls + the pure order/membership updates) lives once in `listOps.ts`, used by `App` (tasks and streaks) and `useShop` (rewards).
- **Gestures** (all in `ItemList`): each ungrouped top-level row shows a **group handle** (⌗) beside its drag handle; pressing and dragging it down the list range-selects a contiguous run (`startGroupDrag`, imperative `.group-selecting` highlight via `elementFromPoint` + `data-item-id`), and release creates (or extends) the group. Dragging an ungrouped row over a group block adds it (only a group *in the same list* is a valid target); dragging a member out past the block ejects it. The move handle overlaps the group handle's right side (z-index), so the bracket is grabbed at its left edge.

### Streaks

A streak is its own entity (not a task flavour), living in a section with `kind: "streaks"`. Tabs are seed-authored, so the Streaks tab is created in `seed.ts`; `ensureStreaksTab` adds it non-destructively to pre-existing DBs.

- **`Streak { id, sectionId, name, type, mode, since, legacy, legacyBest, matcher, groupId?, order?, createdAt, updatedAt }`.** `groupId`/`order` are list structure, exactly like a task's or reward's (see Groups) — a streak's position in its section and the group it's in, if any, both server-derived/stamped in `readStreak`, never evented directly (`StreaksReordered` writes the shared `itemOrder` map, the same mechanism `TasksReordered`/`RewardsReordered` use, rather than splicing the `streaks` array as it once did). `type = "daily" | "weekly" | "counter"`, `mode = "all" | "any"`, `since = "created" | "all"` (see "Settings & period close" below — absent on old events → `"created"`, no migration; the UI labels these **Now** / **All time**). **`legacy`** (int ≥ 0, default 0) is a one-time **backfilled starting value** — the count carried over from before the app (e.g. a whiteboard streak). It's the *pre-app history*, so it's added **only when counting from All time** (`since === "all"`); counting from **Now** starts fresh and ignores it. `legacy` never affects `active`. **`legacyBest`** (int ≥ 0, default 0) is a **separate, non-additive** backfill for the record: `StreakView.best` (daily/weekly only) is **`max(legacyBest, longest satisfied run in the app's whole history)`** — so it seeds a pre-app record the app then only beats. Both are edited only from **Settings → Backfill** (`PATCH /api/streaks/:id { legacy?, legacyBest? }` → `StreakEdited`), carried on `StreakCreated` so reset-keep-board preserves them, and folded in inside `computeStreak`/`computeCounter` so live state and rebuild agree. `best` is computed **unwindowed** (ignores `since`/`createdAt` — it's your all-time-in-app record even for a fresh "Now" streak) by a second walk-back in `computeStreak` bounded to the earliest completion; counters return `best: 0`. (`type` was named `period` until a counter — which isn't a period — was added; the `StreakCreated` event field is `streakType` to dodge the event's own `type` discriminant, exactly like `TaskCreated.taskType`. Old events wrote `period` on `StreakCreated`/`StreakEdited`; both are read as optional legacy aliases and resolved to `type` in the projection, so pre-rename streaks project unchanged with no migration.) `daily`/`weekly` count **consecutive satisfied periods** (from history); **`counter`** is a live **sum of the linked tasks' currently-ticked boxes** — ticking raises it, unticking lowers it — see the compute note below. **Streaks carry no color of their own** — the flame and the form's condition dots inherit the Streaks *section*'s color (passed down as a display-only prop). (Old `StreakCreated`/`StreakEdited` events may still hold a `color` key; Zod strips it on read, so no migration was needed.) Streaks are never stored with a count — `count`/`active` are **derived on read** from completion history and returned as a `StreakView` (`Streak` + `count` + `active`).
- **`matcher` is a discriminated union (`kind`), pluggable by design.** `{ kind: "tasks", conditions[] }` is fully functional: each condition is `{ taskId, required }` where `required` is a **number** ("done at least N times this period") or **`"all"`** (every box, resolved **live** against the task's current box count — so changing a count task's amount later moves the requirement with it). The streak is satisfied in a period when *all* (or *any*, per `mode`) of its conditions are met. **Legacy events stored a bare `taskIds[]`**; a Zod `transform` on read normalises it to `conditions` each requiring one completion (exactly the old "was it done this period?"), so pre-existing streaks project unchanged with no migration. `{ kind: "filter", rules[] }` remains in the union server-side (it needs tags + a filter-AST engine, a `BACKLOG.md` item) but has **no UI** — the form's "Filter (debug)" toggle was removed, so `StreakForm` only ever emits `tasks`. When `filter` is revived and evaluated for real it must follow the security rule: structured AST → parameterised query, never string interpolation.
- **Computation is a pure function** in `packages/contracts/src/streak.ts`: `computeStreak(completions, streak, now, boxCounts, timeZone)`. **`daily`/`weekly` fold completion history**; **`counter` reads current state instead** (see `computeCounter` below) and never touches history. For the history path, it first **windows completions to `streak.createdAt`** — only completions at/after the streak was created count, so a freshly-added streak starts from zero rather than inheriting the linked task's whole past (ISO-UTC strings compare lexicographically; the count stays *derived*, so it's still rebuild-safe). It then buckets those into local **day** (`YYYY-MM-DD`) or ISO **week** keys, tracking the **max level reached** per task per period (`CompletionRecord.count`); a condition is met when the reached level ≥ its `required` (with `"all"` resolved via `boxCounts`, the projection's live box count per task), then it walks backward from `now` counting consecutive satisfied periods — **the current period being unsatisfied is a grace state, not a break** (`active: false` but the count holds); an *earlier* gap breaks the run.
- **A `counter` honours `since`** (`computeCounter(streak, currentLevels, opts?)`): **"Now"** (`since !== "all"`) is the **sum of the linked tasks' currently-ticked boxes** (`behaviorOf(task).filled(task)`, resolved live in `readStreak`) — ticking raises it, unticking lowers it, **every tick moves it by exactly one**, no history/periods. **"All time"** (`since === "all"`) is the **lifetime tick total**: for each linked task, **the level it held each time a period roll unticked it, summed, plus its live level now**. The projection folds that per-task sum as **`bankedLevels`** on every `TasksReset` (the box counterpart of `banked` points — a fold rule, not an event, so a rebuild lands in the same place) and `readStreak` passes it to `computeCounter`. It's honest because a box unticked before its reset was never banked, and an untick now lowers the live part at once. **Counted per reset cycle, never per day** — it used to sum each *day's* level from the day-close snapshots, which counted a tick that stays up across day closes (a weekly task all week, a one-time task forever) once for every day it sat ticked; a weekly workout ticked Sunday read +2 by Monday. Without `bankedLevels` it degrades to the live sum. "All time" adds `legacy` (the pre-app history); "Now" ignores it and starts fresh. Both are lit while non-zero, no `mode`/`required`. Consequence to know for "Now": it can't exceed the total boxes that exist, and a task **already ticked when you link it counts immediately** (no per-streak baseline — a deliberate simplification). Time zone is **always `Asia/Jerusalem`** (`DEFAULT_TIME_ZONE`) — not user-configurable. Period stepping is UTC-noon-anchored for DST safety; capped at `MAX_PERIODS` (4000). Covered by `packages/contracts/test/streak.test.mjs` (the pure functions) and `apps/api/test/counter.test.mjs` (an "all time" counter through real rolls, resets and a rebuild — including the weekly-task double count).
- **Completion history** feeds it: the projection keeps a `completions` list (`{ taskId, occurredAt, count? }`, where `count` is the level reached), appended to on `TaskCompleted`, on `TaskTierSet` when a tier becomes active, and on `TaskProgressSet` when `progress > 0`. Streak events (`StreakCreated`/`StreakEdited`/`StreaksReordered`/`StreakDeleted`) are part of the same append-only log.

Frontend: `StreakForm` (shared add/edit body, wrapped in a `Popover` by the caller) — its task matcher is a **Notion-style condition builder**: condition rows animate in/out (framer `AnimatePresence` + `layout`), joined by a single shared AND/OR connector that reads/writes the streak's `mode` (`all`=AND, `any`=OR; only the first join is an interactive toggle, later joins mirror it). There is no separate all/any control — the connector *is* it. **For a `counter` streak the connector is instead a fixed, non-interactive `+`** (mode doesn't apply — each task tallies independently), the type selector is a third `Counter` pill alongside Daily/Weekly, and the whip links the **whole task**: per-box `×N`/`all` targeting is disabled (`resolveTarget` short-circuits to the row) and no `.cond-req` badge is shown, because any completion counts at its level. Tasks are linked with an **After Effects–style pick-whip** (`.whip-*` classes) — the drag, the line and the row highlight are the shared `usePickWhip` hook (`pickWhip.tsx`), which the Blocked form (Status) reuses to link the task a blocked one waits on; each caller supplies what a point on the board resolves to and what a drop does: `onPointerDown` on the handle starts window pointer listeners that draw an SVG line (portaled to `document.body`, screen-space so canvas zoom/pan needs no correction; neutral slate ink, **not** the streak color) and hit-test with `elementFromPoint().closest("[data-task-id]")` — every `.task-item` already carries `data-task-id`. The line's end snaps to the hovered target, not the row centre: for a **count** task (`supportsQuantity`) hovering a specific box (`[data-box-index]`) links `required: N` (that box's index+1), while hovering the row elsewhere links `required: "all"`; any other task links `required: 1`. The line lands on the resolved box (or `input[type=checkbox]`/first `.tier-dot`). The hovered row is highlighted imperatively (`.whip-target`, amber `.whip-target-dupe` if already linked, red `.whip-target-refused` when the target carries a `refused` reason — shown in a `.whip-refusal` tag beside the line's end, and a drop there does nothing) and the condition is **upserted** on release (re-dropping a linked task updates its amount instead of duplicating). Each condition row shows a `.cond-req` badge (`×N` or `all`) for multi-box tasks. **A streak only counts tasks on its beat** — `streakRefusal(type, section)` (`streak.ts`, with `streakCanCount` its yes/no): never a tab with no `period` (the one-time tasks and their Freezer — "Streaks don't take one-time tasks"), else daily ↔ a `period: "day"` tab, weekly ↔ `"week"`, a counter either; any other pairing can't be counted honestly (a weekly task stays ticked all week, so a daily streak would count every day; a daily one is reset before its week's snapshot, so a weekly streak never sees it; one that never resets counts for ever). The form gets `allSections`, refuses such a target with `streakRefusal`'s reason ("Daily streaks only take daily tasks") and marks linked tasks a type switch no longer fits (`.cond-row.misfit`, blocking save); the server asserts the same in `createStreak` and in `editStreak` when `type` or `matcher` changes (400 "daily streaks only take daily tasks"). Streaks saved before the rule aren't touched. **Caveat:** you can only whip to a task that's on screen — a task on a panned-away card isn't reachable without panning to it first. The "Filter (debug)" branch is still the inert shell. `StreakItem` is a row on the same shared `ItemRow` base as `TaskItem`/`RewardItem` (see "Shared bases"), rendered inside an `ItemList` by `SectionCard` when `section.kind === "streaks"` — so streaks reorder, range-drag into groups, and drag out of them exactly like tasks and rewards do, through the identical `ItemList`/`GroupBlock` mechanics and the same `groupsApi`/`withOrder`/`withMembership` client plumbing (`listOps.ts`). (Streaks were originally their own bespoke `Reorder.Group` with no grouping at all — draggable-but-not-groupable was a real gap, closed by putting them on the same list base as everything else rather than duplicating drag/group logic a third time.) Edits apply optimistically then reconcile `count`/`active` from the server response, since only the server can recompute the count.

## Settings & period close

**Settings are server truth, not a client preference** (contrast the canvas layout, which is per-device localStorage). The day/week a completion falls in decides streak counting, and the server is the sole authority on time — so timezone and period boundaries live in the event log.

- **`Settings { timeZone, dayStartMinutes, weekStartDay (0=Sun…6=Sat), weekStartMinutes, windDown, pointsFormula, bounty, freezer, backup, booster, sale }`** (`sale` is the weekend sale: `{ enabled, percentOff, startDay, startMinutes }` — it runs until the week is ended; see "Shop") (`packages/contracts/src/period.ts`) — `pointsFormula` (rate + effort presets) is the editable time→% conversion (see "Points formula & rebalancing"); `.default({})` so a pre-feature board parses unchanged with today's values., defaulting to `Asia/Jerusalem`, day start 00:01, week start **Sunday** 00:01 (the Israeli week). A `SettingsChanged` event carries a **full snapshot** (not a delta); the projection keeps the latest. `DEFAULT_SETTINGS` applies until one lands, so a pre-settings board is unchanged. `windDown` (`WindDown { enabled, targetMinutes, leadMinutes, message }`) is a `.default({})` sub-object so a pre-wind-down `SettingsChanged` parses unchanged with the nudge simply off — the screen-off nudge config (see below); `PatchSettingsBody` accepts the **whole** `windDown` object (the command layer shallow-merges the top-level patch, so a partial would drop the untouched knobs).
- **Period keys are pure functions of an instant + settings** (`dayKeyFor`/`weekKeyFor`/`periodKeyFor`). A day key is the local civil date after shifting back by `dayStartMinutes` (so "my day starts at 4am" pushes early hours to the previous day); a week key is the anchor date (`YYYY-MM-DD`) of the most recent `weekStartDay`. These replace the old hardcoded `DEFAULT_TIME_ZONE` and ISO-Monday week in production — **`streak.ts` uses settings-based keys when `opts.settings` is passed, and falls back to the legacy local-day / ISO-week keys when it isn't** (that fallback is what keeps the pure unit tests, which pass no settings, valid).
- **Period lifecycle.** `PeriodStarted { kind, periodKey }` marks the current open period of each kind; `PeriodClosed { kind, periodKey, snapshot }` settles it, freezing **every task's filled-box level at close time**. **Periods are never auto-started** — a fresh or reset board has *no* open period, and `periodStatus(now)` reports that as `due` (`openKey !== currentKey`, which is true when `openKey` is `null`). So the owner consciously **starts** the first day via the prompt (the week starts with it); thereafter it's `due` once `now` crosses into a later period. **Only the day is ever asked about:** `rollPeriod("day")` follows its close with `rollPeriod("week")` whenever the week is due by then (`periodStatus`) — a command-level follow-up of the owner's one answer — and returns that week's recap as `week` (none for a first week, which only starts). With the default boundaries that's ending a week's last day or any later one; with a week boundary off the day's, the week simply waits for the next day's end. **The open day is today until it's ended:** each completion record carries the open `dayKey`/`weekKey` at the time (`recordCompletion`; none open → the moment's own keys, derived at read), `computeStreak` takes the open period as `openKey` — the current period (live levels, grace) and where the walk starts, whatever `now` says — and the recap tally files a tick under the open day. So a tick at 2am before ending yesterday is yesterday's everywhere. `PeriodClosed` drops its period from `openPeriods`, so between a close and the next start (where a week freezes its streaks' start) the clock's period is current, not the one just closed. The web's lock gate agrees: `BoardClock.openDay` reaches `isBoxLocked(entry, now, settings, openDay)`, which, once the clock is past the open day, opens its daily gates and reads a weekly gate as of the open day's last minute. **Gaps are just missing:** days and weeks never opened get no events at all — the stale open day and week close when the owner is back, the current ones open, and anything between reads as nothing done (a recap's empty day shows "—"; streaks count it as a miss). `rollPeriod(kind)`: with an open period it closes it (live snapshot), **unchecks every ticked task in the tabs whose `period` is that kind**, and opens the current one; with **no** open period (fresh/reset) it just opens the current one (nothing to close). It returns a `PeriodRecap` plus recomputed streaks; the client skips the recap card on a first-start. The recap is **the closing period day by day**, from a fold rule (`BoardStore.tallies`, one per kind, started afresh on its `PeriodStarted`, each keyed by the board day an event happened in — `dayKeyFor(occurredAt)`): every tick event (`TaskCompleted`/`TaskUncompleted`/`TaskTierSet`/`TaskProgressSet`) adds the task's value after it less before (so a boost is in it, and an untick of an earlier win counts against its day) to that task's gain, and every `RewardPurchased` its frozen cost under the reward's name then. `recapDay` groups a day's gains by tab (in the tabs' order, with each tab's name and colour): `cleared` = its tasks with a positive gain, `earned` = the net; plus the day's `earned`/`lost` and `purchases`. A day's recap is one `RecapDay` (whatever days it ran over); a week's is each of its seven days (and any later one it ran into). A period's own `TasksReset` is banking, never counted; a deleted task leaves the tally. **Streaks from start to end:** a week's `PeriodStarted` freezes every streak's count (`streaks`) — counted *after* the last week is closed and reset, so a tick still up from it isn't counted for both weeks (computing before the close did exactly that) — and the week's recap pairs the open week's start with the counts frozen on the next start. Covered by `apps/api/test/recap.test.mjs`. **Web:** `Recap.tsx` — pages flipped with Back / Next and dots (a week: days, streaks if any, the frost the Freezer gathered and what the close froze if any — see "Freezer" — then the Bounty roll, or a line saying there was nothing on ice to roll; a day: one page), the days' tiles popping in on a stagger; `periodLabels.ts` has the date labels the prompt and the recap share (a week's both carry their month). A day's recap is a card over the soft scrim; a **week's is sticky notes on the board** (`NoteWall`): a frosted wash (`backdrop-filter`) fades the board back, the days and the streaks are `.recap-note`s slapped on (framer: in from above, bigger, leaning harder, landing at a fixed tilt per place), and Done sets `leaving` — every `.recap-drop` falls by a CSS animation on the individual `translate`/`rotate` properties (so it adds to framer's transform rather than fighting it) — then closes, and the wash's exit clears. **The board only takes the new day and week once their recaps close**: `App.endDay` shows the day's recap, queues the week's after it (`recapQueueRef`; `closeRecap` shows the next, keyed per period so it mounts fresh), and waits on a promise the last `closeRecap` resolves, then reads tasks, status and Bounties back (fresh — the recap's stops rolled them), so the new Bounty never shows on the board before its reel lands; the prompt is hidden at once by marking the day (and the week) not due until the real status lands. (It replaced a list of every task with boxes ticked at the close — which, since one-time tasks never reset, grew with every task ever finished.) Missed intermediate periods get no snapshot and correctly read as empty (nothing done).
- **Period reset + banking.** The unchecking is one `TasksReset { taskIds, pointsBanked }` event, committed right **after** `PeriodClosed` (so the snapshot, streaks and recap still see what the period reached). The fold sets each task back to level 0 via `behaviorOf(t).patchForLevel(t, 0)` (the one level→storage mapping) and adds the frozen `pointsBanked` (what those tasks held at that moment, current config) to a `banked` total — and each task's pre-reset level to its `bankedLevels` entry (what an "all time" counter keeps; see Streaks). Points are `live board total + banked − spent` everywhere (`pointsAvailable()` on the server; `App` reads `banked` off `/api/periods/status`, refetching tasks + status together after a roll so the counter never dips). Only a real close resets — a first start or a no-op roll (already current) doesn't. Known limits: a **"Now" counter** (live sum) drops to 0 at each reset of its tasks; a **tier timer**'s elapsed time isn't cleared, so restarting it can re-pick a tier.
- **Why the snapshot matters (the honest-streak fix).** For daily/weekly streaks, `computeStreak` takes a `settled` map (`periodKey → taskId → level`) and, for any settled period, the snapshot **wins outright** over raw completions — so a box checked then unchecked before close reads as 0 and never inflates a streak. Unsettled/legacy periods fall back to raw history (max level reached that period, the original behaviour) — **except the current open period, which reads live state** from a `currentLevels` map (`behaviorOf(task).filled(task)`) the projection passes in. This is load-bearing: raw history never drops (an uncheck doesn't erase the "checked today" record), so without the live read a same-day check-then-uncheck would keep counting. With it, the open period tracks live state (grace), so unchecking today drops it immediately. (Counters were always live via `currentLevels`; this brought daily/weekly in line.)
- **`streak.since`.** `"created"` windows the fold to the streak's `createdAt` (original behaviour); `"all"` drops that window and counts the linked tasks' whole history — trustworthy precisely because settled periods only count what was genuinely done. Counter streaks ignore `since` (they mirror current state).
- **Reset.** `POST /api/reset` → `store.clearAll()` (the only `DELETE FROM events`, on the `EventStore.clear()` added for it) then `initializeBoard`. The web responds with a full reload rather than reconciling piecemeal.
- **Debug clock (`apps/api/src/clock.ts`).** A debug-only override of the server's `now`, so the owner can simulate opening the app at another time (Settings → Debug → pick a time → Go). The projection reads `clock.now()` everywhere it needs the present — `periodStatus`/`rollPeriod` defaults, `readStreak`'s streak compute — **and stamps new events with it** (`commit`), so a completion made under a faked time buckets into that day/week and the simulation stays coherent end to end. It's a deliberate backdoor (single-user, self-hosted, never public), **in-memory only** — a restart or a `null` POST returns to real time; it never touches the append-only log's authority beyond the timestamp it stamps. The web fetches `/api/debug/clock` on load and drives the date header from the effective `now`, then reloads after a Go so every time-derived read re-computes against the new clock. While a fake time is pinned, a persistent amber **debug badge** sits in the header (both views) showing the pretend time; clicking it clears the pin (`POST { at: null }`) and returns to the real/browser clock — the always-visible "exit debugging" control (the Settings "Back to now" button does the same). Pure logic still takes `now` as a parameter — only the projection's *default* source of "now" moved from `new Date()` to `clock.now()`, so the time rule ("never read a global clock inside pure logic") holds.

- **Wind-down nudge (the screen-off pressure).** An optional escalating full-screen overlay that pushes the owner to shut their screens off by a chosen time (see `PRODUCT.md`). **`windDownState(now, settings)`** in `period.ts` is the pure timing curve — minute-of-day civil arithmetic in the board timezone (same style as `isBoxLocked`, a **display gate only**, never scoring): `idle` before the lead window, `ramp` (with a 0→1 `progress`) inside it, `takeover` at/after the target, resetting on its own at local midnight. It deliberately ignores `enabled` — the enabled flag and per-day dismissal are the overlay's concern. **`WindDownOverlay.tsx`** (mounted at `App` top-level, *outside* the view switch so it pressures in board **and** settings) reads the effective clock (`debugNow ?? realNow` + a `pinned` flag) — when pinned it **freezes to that instant so the owner can preview any moment via the debug clock**, otherwise it self-ticks every **1s** so the clock actually ticks. **The full message doesn't show continuously — it pops at configured `displayTriggers`:** a user-editable list of `{ kind: "before", minutes }` and `{ kind: "refresh" }` (defaults 30/15/5 min before + on refresh). On (re)mount the overlay *seeds* — any `before` whose moment already passed is marked fired (no retro-pop) and an `on refresh` trigger pops once we're already inside the window (`phase !== "idle"`); on later 1s ticks a `before` pops as `minutesToTarget` crosses its value. `shownFull` = takeover up now, `hasAppeared` = at least one trigger fired this session (so the candle persists between pops), all re-armed on a day change / reload. **`windDownLeadMinutes(wd)`** (largest `before`) defines the window `windDownState` uses. The panel still **grows** with progress (size/font/backdrop scale from the earliest trigger toward the target) but via **inline `width`/`minHeight`/`border-radius`/`font-size`** — `minHeight` (not a fixed `height`) so the stacked content can't be clipped by the panel's `overflow: hidden` (that was a real cut-off bug); size floors are generous since it pops at discrete moments and never needs to be tiny. The red top line is the **live current time** (`HH:MM:SS`, board tz). Actions stack **centred and vertical**: a large **neutral (not red) Acknowledge** on top, and below it a smaller **red Dismiss for today** that first swaps to an inline **confirm** ("Dismiss until tomorrow?"). **Acknowledge** sets `shownFull=false` — the takeover plays an **echo-trail** exit (the panel streaks toward the corner — `x/y` to ~42vw/44vh, `scale`→0.06 — while two staggered `.wind-down-ghost` copies fade behind it, After-Effects style) and the small **floating candle** (`WindDownClock`) springs in on a short delay; **Dismiss for today** (confirmed) sets `doneDay` (keyed by `dayKeyFor`, so it re-arms next day). Only the panel takes pointer events, so a click on the dimmed board can't dismiss it. The **minimized widget** shows a **burning candle** (`Candle` SVG — wax height burns *down* with `burn` = progress; a flickering flame while there's time, a rising smoke wisp once past) plus the live time, parked by **`useFreeSpot(".hud-anchor")`** — the same gap-finder the points HUD uses, extended with an optional extra-obstacle selector so the widget also dodges the HUD; it pulses a red glow (CSS `box-shadow` keyframe, so it never fights framer's transform) once past the target, click re-expands (`acknowledged=false`), a hover `×` dismisses for the day. `acknowledged`/`doneDay` are in-memory (a reload re-nudges) and re-arm on a day change. Lead time is chosen from **Settings presets (30 / 10 / 5 min before)**. Reduced-motion drops the breathing glow, the growth transition and the clock pulse. **ponytail:** if the window would cross midnight (`target < lead`) the ramp start is clamped to day-start rather than wrapping to the prior evening.

**ponytail:** the walk-back anchors each period at UTC noon before applying the day/week-start offset, so a configured day-start past ~11:00 could misbucket; widen the anchor if that's ever needed (`streak.ts`, `keyForCivil`).

## Frontend architecture

### State & data flow

`App.tsx` owns all server-derived state: it fetches `sections` + `tasks` once on mount and holds them in React state. Every mutation is **optimistic** — update local state immediately, fire the `fetch` in the background — because instant feedback is the whole point of this app (see `PRODUCT.md`). The server is still the authority; local optimism is a UI nicety layered on top.

`SectionCard` renders one board tab and `TaskItem` one row — each a thin *tab kind* on the shared bases (see "Shared bases" below), which own the canvas, the card's move/resize, the sort/display controls, and the list's reorder/grouping. Props flow down, callbacks flow up — no global store; the only React contexts are two thin canvas ones — the **zoom scale** (`useCanvasScale`), which cards read to convert screen-pixel drags into world pixels, and the **canvas settings** (`useCanvasSettings`: snap/grid-size/show-grid), read by `CanvasCard` (snapping) and `BoardCanvas` (grid overlay). If cross-cutting *app data* state grows, introduce a store deliberately rather than prop-drilling further.

### The derived-points pattern (don't regress this)

`totalPoints = computeTotalPoints(tasks)` is the single source of truth for what the tasks hold; the counter shows `points = displayedPoints − shop.spent` (the owner's points after shop purchases — see "Shop"). `displayedPoints = totalPoints − pendingGain`, where `pendingGain` sums the amounts of flyers still mid-flight. So a gain bumps `totalPoints` immediately but `pendingGain` grows by the same amount at the same instant (net-zero visible change), and the counter only catches up when a flyer *lands* and drops out of `pendingGain`. Losses (uncheck, downgrade, delete) have no flyer, so they show instantly; any in-flight flyer for that task is cancelled (`cancelFlyersFor`).

`displayedPoints` is **derived, never separately tracked state.** A previous hand-maintained `displayedPoints` with manual +/- bookkeeping drifted — a fast check/uncheck could get permanently stuck. Keep it derived.

### Client vs server state

- **Server** (via API): everything about *what the board is* — sections, tasks, done state, tiers, points, order, and the shop (its tabs, rewards and purchases). Under the target model, also all history.
- **Client-only** (`useLocalConfig.ts`, `localStorage`): purely-local display preferences that don't belong to the board's shared truth. Today that's each card's **free-canvas layout** (`layouts: Record<id, {x, y, w, h, z}>`) — position, size and stacking order on the whiteboard — plus the **canvas settings** (`settings: {snap, gridSize, showGrid, oneTab}`, edited via the `CanvasToolbar` on top of the board) and the tab each canvas's one-tab view is on (`shownTabs: Record<canvasName, cardId>` — see "One tab at a time"). This is deliberately per-device: a spatial arrangement tuned for a wide monitor would be nonsense on a phone, so it doesn't sync (owner's explicit call), and how *this screen* snaps/shows its grid is the same kind of preference. Two more per-device preferences persist here the same way (both pure display transforms — the task *order* itself stays server-side so it agrees across devices): **per-tab view prefs** (`tabPrefs: Record<id, {sortMode, display, pinned?, collapsed?}>` — a tab's chosen sort, its row display toggles, which menu options it has pinned or unpinned, and which broken-down tasks have their pieces folded away, for board and shop tabs alike; `display` maps the tab's Display keys to on/off and `pinned` maps `"sort:<key>"`/`"display:<key>"` to pinned or not, an absent key falling back to what the tab offers — see `TabControls.tsx` and `tabViews.ts`. Configs saved in the older `{showEstimate, showTimer}` shape are normalised on read into `display: {estimate, timer}`; the retired board-wide `pinnedSorts` list is dropped on load). These were briefly component-local `useState` and so reset on reload — persisting them here is what makes them survive reloads/restarts. (The shop briefly lived here too, as a device-local preview under `localStorage` key `board-shop`; once purchases had to really deduct points it moved to the server — a spend another device can't see would make the two disagree about your points. `useShop` clears the stale key on load.) When a real "settings" surface grows, keep this line: anything another device would need to agree on goes to the server; anything that's "how *this screen* looks right now" can stay local. (The server still stores a section *order*, but the web client no longer uses it for layout — see "Board canvas".)
- **Client-only, under their own `localStorage` keys** (outside `board-config`'s React state, each for a reason): each canvas's **camera** (`board-camera`, `Record<canvasName, {scale, x, y}>` — see "Board canvas"), written on every pan, so routing it through state would re-render the whole board per scroll event; and the **theme** (`board-theme`, `{choice, dark}` — see "Themes"), read by `index.html`'s boot script before React exists.

**Shop mode.** "shop" is not a separate place — it's a *mode of the board's* (`shopOpen = view === "shop"`). The counter is the same **Points** readout in both modes (board live total − spent, see below); a purchase calls `PointsCounter.spend()` (flinch + red −cost) and `PointsPlate`'s count-up animates the drop. The shop itself is a **second `CardCanvas`** (`name="shop"`) laid exactly over the board's frame (`.shop-layer`, absolute over `main`), holding user-defined **shop tabs** (purely organisational shelves — no behaviour differs between them) as `ShopSectionCard`s — so shop tabs move, resize, snap, sort, display-toggle, reorder and group exactly like board tabs (see "Shared bases"). The two canvases share the device-local config (layouts keyed by card id, canvas settings, tab prefs, pinned sorts) but reset independently. With no shop tabs yet, a centred first-tab form stands in for the canvas; later tabs come from the toolbar's `+`. Because both canvases use the same classes, every shop-mode rule is scoped to the **board** canvas (`[data-canvas="board"]`, or `main`'s direct children for its toolbar/zoom) — an unscoped `.board-card` rule would hide the shop's own tabs.

**Shop (server truth).** Buying **really spends the board's points**: the owner's points everywhere are `live board total + banked − spent`, where `spent` sums every `RewardPurchased.pointsSpent` (and `banked` every `TasksReset.pointsBanked` — see "Settings & period close"). The shop lives in the event log like the rest of the board — `ShopSectionCreated/Edited/Deleted`, `RewardCreated/Edited/Deleted` (edits carry `changes` + `previous`, cf. `TaskEdited`), and `RewardPurchased { rewardId, pointsSpent }`. The purchase **freezes its cost** (the counterpart of the scoring events' `pointsAwarded`), so a later price edit or deleting the reward never rewrites what was paid; deleting a shop section drops its rewards from the projection, but their purchases stay in `spent`. Affordability is checked in `BoardStore.purchaseReward` against the server's own `pointsAvailable()` (sum of `taskPointValue` − `spent`) — the client's disabled button is only a mirror of that. Because spending is its own event stream, **lifetime points earned stay derivable** from the scoring events alone (independent of anything spent) — the hook for levels/XP later. Costs are integer thousandths-of-a-percent like every point value (`> 0`), and a negative total closes the shop (per the spec). Tabs and rewards are the owner's data (nothing named in code). Web side: `useShop.ts` fetches `GET /api/shop` and applies edits optimistically; a purchase is optimistic too (so the drop lands with the animation) but the server's reply — or, if it refused, a fresh read — replaces it. Note the points are still the board's *live* total (no cross-day banking yet — `BACKLOG.md`): unchecking a task takes its points back off, so buying and then unchecking can push the total negative.

**Reward kinds, items and the weekend sale.** A reward's `kind` (`RewardKind`: `repeatable` | `once` | `game`) is set on `RewardCreated` and never edited (like a task's type); a `game` reward carries the `item` (`GameItemId`) it gives. Events from before kinds read as `repeatable` and `onSale` (`onSale ?? kind === "repeatable"` — the shop's rewards then were its leisure ones), so the owner's live rewards needed no migration.
- **One-time rewards retire like one-time tasks.** `isBought(reward)` (`domain.ts`) is a `once` reward with `redeemed > 0`; `purchaseReward` refuses it again. The fold's retire rules are written once over both kinds: `settleRetiredItem` drops a retired item from its group, and `settleRetired` keeps a section's retired tasks *and* bought rewards trailing its order (also after `RewardsReordered`). `ShopSectionCard` hides them unless the tab's **Already bought** Display toggle is on (a flat look-back, no drag or grouping) and appends their ids when it posts a reorder; `RewardItem` asks before buying one (`ConfirmPopover`, its non-destructive `danger={false}`), then holds a local `leaving` flag so the row shows Bought, hatched, through a delayed exit (`BOUGHT_EXIT_DELAY`, the one-time task's trick).
- **Items are a registry.** `BoardStore.gameItems` has one entry per `GameItemId` — `held()` (`{ owned, free }`: bought and kept from week to week, and the open week's free ones left — served as `Shop.inventory`) and `grant()` (the event a purchase commits): `bounty-reroll` grants `BountyRerollsGranted { source: "purchase" }` (owned = banked, free = the week's), `booster-reroll` grants `BoosterRerollsGranted`. The shop's toolbar has an **Inventory** group (`ShopView`'s `Inventory`) listing every item; `HeldChips` (`RewardItem.tsx`) shows a count the same way there and on a row — "2 owned" and a green "1 free". `purchaseReward` commits the grant only when the `RewardPurchased` was new (`result.created`), so a retried purchase never gives twice. The web's `gameItems.ts` holds each one's label and starting name/emoji; a new item is an entry in each. After an item purchase lands, `App` reads back `/api/bounty` and `/api/booster` so the row menus' reroll counts are current.
- **The sale is a price modifier, priced at the moment of purchase.** `purchaseReward` prices with `priceModifiersOf(reward, { settings, now: clock })` and freezes `pointsSpent` (the price), `cost` (the list price then) and `modifiers` on `RewardPurchased` — older purchases have neither, and spent their price. The web prices each row with the board clock (`useBoardClock`, re-stamped each minute, debug-aware), so the sale starts and ends on screen without a reload, and sends that `price` with the purchase; the server's **409** on a mismatch means nothing was bought, and `useShop`'s fresh read shows the real price. `saleOn(now, settings, { openDay, startedEarly })` (`period.ts`) is the start time as a weekly box's gate (`isBoxLocked` at `startDay`/`startMinutes`), so it follows the board's days like everything else: an open day not yet ended is still today, and the sale runs until the week is ended (the next week's position is before the start again) — or it's on all week once started early (`SaleStarted { periodKey }`, folded into `saleStartedIn`, started afresh by the week's `PeriodStarted`). The server prices with the open day and that flag (`BoardStore.priceContext`); the web with the board clock's `openDay` and `Shop.saleStarted`. Settings' **Start the sale now** (`SettingsView`, confirmed) posts `/api/shop/sale/start` through `useShop.startSale`. `ShopView` shows the sale's tag beside the docked counter while it's on and something is on sale (under it on a narrow screen).

## Frontend implementation lore

These are the traps that cost real debugging time. Each is load-bearing — re-solve before removing.

### Board canvas (`BoardCanvas.tsx` + `canvas.ts` + `.board-viewport/.board-scaler/.board-world`)

The board is a **free whiteboard canvas**, not a flow layout. Three nested elements:

- **`.board-viewport`** — the camera window (`overflow: auto`, fixed height). Native scroll *is* the pan, so it clamps to content for free. **`isolation: isolate` here is load-bearing** (don't remove): cards carry an ever-growing `z-index` (`zCounter`, ~1000+) so the last-touched one floats above its neighbours, but that only matters *among cards*. At 100% zoom framer applies no transform to `.board-world`, so it isn't a stacking context — without the isolate, those z:1000 cards leak to the body level and paint over the fixed HUD (`z:40`) and the body-portaled flying-points layer (`z:200`), so the flyer arcs *behind a tab*. Isolating the viewport keeps card z-indexes self-contained so the HUD and flyer always sit above the board. `touch-action: none` hands *all* touch gestures to our own pointer handlers (the browser's native pan/pinch is off) instead of the browser's page scroll. **One unified gesture** (`onPanStart` + `onGestureMove`/`onGestureEnd`, tracking a `pointers` map): a mouse grabs on the **middle button only** (`e.button === 1`) so left-click stays free for interaction; **touch pans one-finger and pinch-zooms two-finger**. Lifting one finger of a pinch continues as a pan with no jump (`rebaseline` re-seeds the pan/pinch baseline whenever the finger count changes). **Pinch reuses the same `zoom()` helper** as the wheel and buttons (anchored on the two-finger midpoint) — mobile added gesture *recognition*, not a second zoom/pan code path. **Both work from anywhere, a card included.** The first rule — a gesture must start on empty canvas — left a phone nothing to grab: its cards cover the screen, so a finger on a tab simply did nothing. What the camera leaves alone is what takes a finger's drag for itself (`OWN_DRAG`: the row, tab and group handles, the resize corners, the pick-whip, panels and text fields). A press on a card may still be a tap or a hold, so there the camera only **takes** the gesture once the finger has travelled `PAN_SLOP` (8px — the distance at which `ItemRow` gives up its hold) and re-baselines at that point, so the board doesn't jump by the slop; empty canvas, the middle button and a second finger take it at once. Two traps: a touch `pointerdown` is left un-cancelled (only the middle button's is `preventDefault`ed, against autoscroll) — cancelling it suppresses the compatibility mouse events that follow a tap; and the lift that ends a pan begun on a card can still arrive as a `click` on whatever is under the finger, so a *native* capture listener on the viewport swallows that one click (the `moved` flag, cleared by the next press — the row hold's trick, for the row hold's reason). A scrolling list inside a card keeps its `touch-action: pan-y`: a vertical drag there is the browser's (it cancels our pointer before the slop is crossed), a sideways one pans the board. The grab cursor shows only while actively panning (`.grabbing`), not on idle hover.
- **`.board-scaler`** — sized to the **zoomed** world (`worldW*scale × worldH*scale`, `min-*: 100%`) so the (hidden) native scroll extent represents the zoomed area. Scrollbars are hidden (`scrollbar-width: none` + `::-webkit-scrollbar`) — you pan by dragging, so the bars just read as clutter; scrolling still works via wheel/grab-pan.
- **`.board-world`** — the **unscaled** coordinate space cards live in, scaled by the camera. Flat background (no grid lattice — the owner found it too busy); snap-to-grid still applies, just without a visible guide. **The zoom scale is applied by framer** (`motion.div` with `layoutRoot` and `style={{ scale, originX: 0, originY: 0 }}`), *not* a CSS `transform: scale()`. Both properties are load-bearing: `layoutRoot` makes `.board-world` a layout-measurement boundary — `Reorder.Item`s inside only detect layout changes *relative to each other within this root*, so when the zoom scale on the root changes they don't run a layout animation (which would show as "all card text jumps for ~0.5s"). Without `layoutRoot`, framer re-measures all descendants after a zoom, sees them as "moved" (parent scaled), and springs a phantom correction. Without the `motion.div` (i.e. plain CSS `transform: scale()`), framer's projection tree doesn't know about the scale at all and the same thing happens on every re-render while `scale != 1` — task moved, grid/snap toggled. Origin `0,0` keeps top-left anchoring, which the scaler-sizing and scroll-restore math rely on. Don't revert either without re-solving this.

Camera rules, all in `canvas.ts`: zoom is **clamped** (`MIN_SCALE 0.4 … MAX_SCALE 1`) — 1 is native (a whiteboard; zooming past 1:1 only magnifies, never reveals more), 0.4 pulls back to see more tasks at once. Driven by ctrl/⌘+wheel (trackpad pinch sends exactly that), **anchored on the cursor** (a layout effect restores scroll so the point under the pointer stays put), *and* by on-screen **zoom controls** — a `−` / `%` / `+` cluster floating bottom-right (`.zoom-controls`, a sibling of the viewport like `.canvas-toolbar`, so it stays pinned while panning), for anyone without a wheel/pinch; the `%` chip resets to 100%. Both wheel and buttons share one `zoom(compute, anchor?)` helper in `BoardCanvas` — the buttons anchor on the viewport centre, the wheel on the cursor. The world is just the cards' bounding box + `MARGIN` (220px) of slack — that's the entire reachable area, so the camera can't wander into a void; dropping a card further out grows the world next render. Wheel is attached **non-passively** because zoom must `preventDefault` the browser's own page-zoom.

**The camera is remembered per canvas, per device** (`loadCamera`/`saveCamera` in `useLocalConfig.ts`, key `board-camera`): zoom plus the world point at the viewport's top-left (world px, so independent of zoom). `BoardCanvas` reads it once on mount (the board remounts on every trip to Settings, so this is also what keeps your place there) and feeds it through the same `pendingScroll` layout effect zoom uses; clamping then handles a world that shrank since. It's written 250ms after movement stops, from a ref updated on every `scroll` (plus a scale effect, since a zoom that leaves scroll unchanged fires no scroll event), and flushed on unmount.

### Card move & resize (motion values in `CanvasCard.tsx` — every tab on every canvas)

- **Position (`x`/`y` transform) and size (`width`, and `height` or `min-height` — see below) are framer `useMotionValue`s**, not React state. A drag writes them at 60fps with **zero re-renders**, then on release everything settles via `commit()`: if snapping is on (canvas settings) it lands on the grid (`snap(n, gridSize)`), otherwise it lands exactly where dropped (rounded to whole px) — either way it **springs** to that target (`animate(mv, target, settle)`), so there's no jump between "let go" and "settled". The snap toggle and grid size come from `useCanvasSettings` (see "Canvas settings"). Reading layout via a `layoutRef` keeps the pointer-move closures from going stale mid-drag.
- **Drags are scale-corrected**: screen-pixel deltas are divided by the current zoom (`useCanvasScale`) to become world pixels — without this, dragging under zoom lags or leads the cursor.
- **Resize corners adjust the origin, not just the size.** For a left/top corner (`xSign/ySign === -1`) the edge follows the pointer: `x`/`y` move while `width`/`height` shrink to match. Right/bottom corners just grow. All clamp to `MIN_W`/`MIN_H` — `MIN_H` (80) is just the header, so a tab folds to its title — but **shrinking past where the list fits takes Shift**: without it the height stops at the fit (the card's border and `body.offsetTop`, the content's height, then the card's bottom padding and border — never the empty room a card taller than its list has below it, which a first try counted, so a short list couldn't shrink at all; read on every move since a narrower card's rows can wrap taller), or at the height it started from if it was already shorter. **Resized edges sit exactly under the pointer**: the offset between where it took hold (the grab area reaches past the corner) and the edge is added back, so the edges jump to the pointer on the first move, and a resize commits without snapping (whole px only) so nothing springs away after release — only a move snaps to the grid. Each corner's grab area straddles the corner (`.resize-corner`, 12px outside, 16px in), so a press just outside the tab still resizes.
- **A card fits its list until it's resized; then its height is a height.** A layout without `fixed` treats `h` as a `min-height` floor and the card grows to fit what it lists (the default and reset layouts, and every layout saved before this); the first corner drag starts from the height the card *shows* (`offsetHeight`, which can be taller than its floor), stamps `fixed: true` and sets `height` from then on. Both `height` and `minHeight` are always in the style (`auto`/`0` for the unused one) — swapping one key for the other left framer's old `min-height` on the element, so a card that had just turned sized couldn't shrink below its old floor until a reload.
- **The list scrolls inside a sized card — and only when it's taller than the card.** `.board-card` is a flex column; the header is `flex: none`, and `.board-card-body` (the list and the tab's add button, inside one wrapper the hook measures) is `flex: 0 1 auto; min-height: 0`, reaching into the card's side padding so the row handles at `left: -16px` stay inside it. `useOverflows` (a `ResizeObserver` on the body and its content) adds `.overflows` — `overflow-y: auto`, `overscroll-behavior: contain` (the wheel doesn't go on to pan the board) and `touch-action: pan-y` (a finger drags the list; the board's own `touch-action: none` stops at the nearest scroll container) — only while the content is taller, because a scroll box clips: a list that fits leaves a row's hover bubbles free to reach past its edges. In a scrolling list a CSS bubble (Tooltip, tier-dot and status-pill labels, the description "i") is clipped at the list's edge — known, accepted. The body is a `motion.div` with **`layoutScroll`**, so the rows' `Reorder` layout animations measure through its scroll; framer's `Reorder` also auto-scrolls the list while a row is held within 50px of its edge, which in a list under ~150px tall covers most of it.
- **Panels open in the top layer** (`useTopLayer.ts`): `Popover` and `ConfirmPopover` carry `popover="manual"` and `useAnchoredPanel` shows them with the Popover API, so no scrolling list, card or canvas can clip or cover them — this is what lets a card's height be a cap. They stay in the DOM where they are, so `useClickOutside`'s `contains`, `ItemRow`'s `NATIVE_TARGETS` and every descendant style still work. The top layer is screen space: the panel is placed `position: fixed` from its anchor's (its DOM parent's) `getBoundingClientRect` **every frame while open** (writing `top`/`left` straight to the element, no render) — the list scrolls, the board pans and zooms, rows move under it — on whichever side has room, slid back onto the window where it would spill off, and the canvas zoom doesn't shrink it. **Tall forms opt into `scrollable`** (add-task, add/edit-streak): capped to the window's height, scrolling inside. It's opt-in and off by default because a short popover may hold a nested one (color picker, timer); nested ones are top-layer too, so it no longer matters for clipping, but an `overflow` would still be wrong for a short panel. `.popover`/`.confirm-popover` undo the browser's own `[popover]` look (`inset: auto; margin: 0; overflow: visible; color: inherit`); `ConfirmPopover`'s backdrop is top-layer too, shown first so the panel sits on it, covering the window. Ceiling: a card that fits its list and runs past its floor by more than `MARGIN` can extend past the scrollable area — bump `MARGIN`, or measure real card heights for the world bounds, if that ever bites.
- **Last-touched card floats on top.** A module `zCounter` (in `CanvasCard.tsx`, shared by every canvas) hands out increasing `z` on any pointer-down (`focusCard`) and on drag/resize start (`bringToFront`), persisted into the layout — so an active card's popovers are never covered by an overlapping neighbour.
- **`.board-card`'s `motion.section` still has NO framer `layout` prop** — Framer's `layout` runs a `ResizeObserver` and applies corrective transforms to size changes it didn't initiate, which fights the manual pointer-drag move/resize (same root cause that broke the old corner-resize). Don't re-add it without re-solving this.

### Canvas settings (`CanvasToolbar.tsx` + `useCanvasSettings` + `useLocalConfig`)

Per-device knobs for the whiteboard, edited from the `CanvasToolbar` (bare icon buttons floating in the board's top-right corner; one per settings group, each opening its own `Popover` via the shared `popover-anchor` pattern — a `ToolbarGroup` helper wraps that button-plus-popover). Stored in the same `localStorage` config as the layouts (`settings: {snap, gridSize, showGrid, oneTab}`, defaulted + merged on load so a stale pre-settings config still parses). After the groups comes the **view switch**, a plain button (no popover) that flips `oneTab` — see "One tab at a time"; in that view the grid and reset groups aren't shown, having nothing to set. `App` provides them through `CanvasSettingsProvider`, so both canvases share them; the two consumers read via `useCanvasSettings` — `CanvasCard.commit()` for snap on/off + step, `BoardCanvas` for the dot-grid overlay (a `radial-gradient` background on `.board-world`, sized in world px so it scales with the zoom transform and stays aligned to where cards snap). The toolbar's **grid** group holds those three; its **reset** group runs `CardCanvas.resetPositions()`: it clears **that canvas's** saved layouts (`resetLayouts(ids)` — resetting the shop leaves the board's arrangement alone; each card falls back to `defaultLayout`, a balanced √-based grid arranged from the tab count, optionally pushed down by `topInset`) **and** bumps a `resetSignal` handed to each card in its `CardFrame`. A canvas adds its own toolbar groups through `CardCanvas`'s `toolbar` slot (`ToolbarGroup` is exported for that — the shop's "New tab"). That signal is needed because a card's position lives in framer motion values seeded once from the `layout` prop and deliberately **not** re-synced to it (so a drag isn't overridden mid-flight); an effect keyed on `resetSignal` springs the motion values to the freshly-arranged `layout`. Without the signal, clearing layouts changed the prop but moved nothing — the original "reset does nothing" bug (confirmed by the button inside the popover; device-local, never touches the server). `main` is the offset parent (`position: relative`) and the toolbar is a sibling of `.board-viewport` (not inside the scroller), so it's `position: absolute` in the corner with a `z-index` above the world and stays pinned while you pan.

### One tab at a time (`CardCanvas`'s other view + `TabDeck.tsx`)

A canvas has a second way to show its tabs: **one at a time, filling the frame**, with a deck in the corner to turn to another. It's the canvas settings' `oneTab` (per device like the rest; a **phone-sized screen starts in it**, `DEFAULT_SETTINGS` reading `PHONE_SCREEN` once at load — whatever is saved next freezes that into the device's config, so from then on it's only the owner's switch) and lives in the base, so the board and the shop both have it.

- **`CardCanvas` branches, the cards don't know.** With `oneTab` it renders no `BoardCanvas` (no camera, nothing to pan or zoom): just the card its canvas is on (`shown`, from `shownTabs[name]`; absent or since deleted ≡ the first) with `CardFrame.docked`, inside a frame that is still `.board-viewport` (+ `.one-tab`) with the canvas's `data-canvas`. Keeping that class and attribute is deliberate: every rule that hides or dims a canvas (shop mode's fade and `pointer-events`, `Poof` measuring `[data-canvas="board"] .board-card`) covers this view with no second rule. Only that one card is mounted.
- **A docked `CanvasCard`** takes its place and size from CSS (`.board-card.docked`: the frame's width up to 640px, as tall as its list up to the frame's height), renders no resize corners or move handle, sets no `x`/`y`/size style, and counts as sized for `useOverflows` — so its list scrolls inside it once it's taller than the frame. Its `footer` (the tab's add button) is rendered **outside** the scrolling body there, so a long tab's `+` isn't a scroll away; on the canvas it stays inside, as before.
- **Switching cross-fades in one grid cell.** The frame is a one-cell grid and the docked card sits in `1 / 1`, so the card leaving and the card arriving overlap during the cards' ordinary enter/exit. `AnimatePresence mode="popLayout"` would be the usual tool, but it needs a ref on its direct child, and that child is the tab kind (`SectionCard`/`ShopSectionCard`), not the motion element.
- **The points counter docks** — a tab filling the frame leaves it no gap to park in. `CardCanvas` renders the `.hud-dock` itself: always in this view, and on the canvas when asked (`dock`: the shop always, the board on a phone, where cards cover the screen too). The room it takes is `DOCK_CLEARANCE` (`canvas.ts`): the frame's top padding here, the first row's offset in the canvas's default arrangement. With the shop open over a one-tab board there are two docks in the DOM; they sit on the same spot (the shop's layer is laid exactly over the board's frame), so `useFreeSpot` taking the first changes nothing.
- **`TabDeck`** (bottom-right, where the canvas keeps its zoom controls) draws the tabs as a pile of plies: each a `motion.i` lifted along the pile's own z (`transform-style: preserve-3d` on the pile, tilted by one CSS transform), in its tab's colour, filled from its foot by the tab's `done / count` (`--fill`, a CSS-transitioned `::after`, so it moves as boxes are ticked). What a ply shows comes from the canvas's `face(card)` (`TabFace`: name, colour, count, and `done` only for a tab that starts over — one with a `period`). The pile runs from the tab on screen round through the rest (at most `MAX_PLIES`), so turning to another tab is a **cut**: a ply that moves down slides clear of the pile, drops and slides back under (keyframes on its `x`/`z` motion values, driven from an effect — not the `animate` prop, which a re-render mid-cut would retarget), while plies moving up spring. Plies are rendered bottom-first so paint order is right wherever a browser flattens the 3D. Pressing the deck opens the tabs as an ordinary `Popover` list (the Sort menu's rows: each name in its tab's colour, its count, a tick on the current one).
- **What the view can't do:** link tasks across tabs. The pick-whip hit-tests rows on screen, and here only one tab's are — a streak's tasks are linked from the canvas. Effects aimed at a row in another tab (a thaw's burst on the task's new row) find nothing and are skipped, as they are for a row scrolled out of a sized card.

### Phones and touch (`usePhoneScreen.ts` + App.css's "Phones and touch")

One breakpoint, `(max-width: 720px)` — `PHONE_SCREEN` in `usePhoneScreen.ts` and the media query in `App.css`; CSS can't read the constant, so the two are kept in step by hand. Below it the rail of places becomes a bar along the foot of the screen (`.app-nav` re-laid out in CSS; `.page`'s padding moves from the left to the bottom), the date shrinks, the canvas toolbar runs down the frame's edge (clear of the docked counter), and the board's canvas docks the counter (`usePhoneScreen` → `CardCanvas`'s `dock`). `.page` is `100dvh` (with `100vh` first for browsers without it), the screen a phone's browser really shows.

- **Nothing may make the page wider than the screen.** On a phone a document wider than the viewport grows the *layout* viewport, and everything `position: fixed` goes with it: the bottom bar slid out of view and the recap sat off-centre the moment the debug clock's badge overflowed the header. The header now wraps; check `document.documentElement.scrollWidth` against `innerWidth` when adding anything to the page's chrome.
- **`(hover: none)` — nothing points.** What a row shows only when pointed at is either always there (the row's and a group's grips, a group's ungroup button, the resize corners, a tab's `+`) or left to the press-and-hold menu (the row's trash — which, unseen at `opacity: 0`, still took a tap at the row's end). The trash **button** is hidden, not its `.remove-wrap`: the menu's Delete opens the `ConfirmPopover` that lives in that wrapper. The group handle's strip along a row's left edge is hidden too (unseen, it only swallowed the start of a pan), so new groups are made with a mouse. A tap leaves `:hover` stuck on what it touched, so the hints of chrome that takes you somewhere (the nav, the toolbar's view switch, the deck) are off; other hints still show on tap.
- **`(pointer: coarse)` — a blunter pointer.** Rows are taller, and each box, tier, tally and row grip takes a touch from around it through an invisible `::before` (the boxes stay their size: their tick is drawn in px). Toolbar, menu and nav buttons grow. Every text field is 16px: iOS zooms the page into a smaller one and stays zoomed.
- **Panels:** `.popover` is capped at the screen's width (the task form is 350px), and the viewport meta's `interactive-widget=resizes-content` makes a phone's keyboard shrink the window rather than cover it, so a panel — placed against the window every frame — moves up clear of the keys. (Chrome and Firefox on Android; iOS ignores it.) That one can't be checked in headless Chrome, which has no keyboard.
- **`useFreeSpot`** treats the bottom bar's top as the screen's foot, so what it parks (the wind-down candle; the counter where it isn't docked) never lands on the bar.
- **Checking it:** headless Chrome with `Emulation.setDeviceMetricsOverride { mobile: true }` + `setTouchEmulationEnabled`, driven by `Input.dispatchTouchEvent` — a tap, a drag (pan, a row's grip), two fingers (pinch), a hold. Both media queries above match there.

### List rows (CSS Grid + `subgrid`)

- Rows use grid + `subgrid`, not flexbox, so the `[%]` points column lines up whiteboard-style per tab. `.item-list` (the `ItemList` base) defines `grid-template-columns: minmax(24px, max-content) minmax(0, max-content) 1fr auto` (col1 / value / name / delete); `.item-row` (the `ItemRow` base) is `grid-template-columns: subgrid; grid-column: 1 / -1`. A task row's cells are checkbox / `[%]` / name / trash; a reward row's are emoji / price pill / name+note / trash.
- **Column 1** `minmax(24px, max-content)`: the 24px floor beats a single checkbox's 17px so it sits at the column start with breathing room; `max-content` lets the same column grow for tiered rows' tier-dots.
- **Column 2** `minmax(0, max-content)`, not bare `max-content`. Bare `max-content` ignored container width and blew a long tier bracket (NASA, 4 tiers) past its grid cell, spilling across tabs. `minmax(0, …)` lets it shrink under pressure. That alone wasn't enough — the fix is a **`<wbr/>` per segment in `PointsBracket.tsx`** (built from `percents.map(...)`, not a joined string), so wrapping only ever happens *between* whole percentages, never inside `2.4%`. The `<wbr/>` sits before each `/` separator, so a single-value `[0.5%]` can't split either.
- **`PointsBracket` is shared by `TaskItem` and `FlyingPoints` deliberately** — the flyer must be the row's actual bracket, not a lookalike. See the flyer section.
- Any *direct child* of `.item-row` auto-places into the next grid column in DOM order — adding/removing a real child shifts everything (the handles and the edit-popover anchor are `position: absolute`, so they take no track). Don't revert to flexbox without re-solving alignment.

### Row actions menu (`ActionMenu.tsx`, wired by `ItemRow`)

Right-click on any list row (task, streak, reward) — or a 500ms touch hold, since iOS never fires `contextmenu` — opens a menu of that row's actions. A row kind only declares `actions: RowAction[][]` (groups; separators fall between them; an action with `checked` is one of a set of choices — a `menuitemradio` ticked when current, like a task's Status; an action's `set` names the set it belongs to, captioned once above its first item, so a set reads apart from the actions beside it without a separator line; a `warning` is a red line under an action saying what it costs, a `note` a blue one saying what it gains — a thaw's "Start now for +0.5%" — and a `disabled` action shows with its warning but can't be chosen, by click, Enter or its key), **Edit first by convention** so right-click → Enter edits; the base does the gestures, placement, keyboard (arrows, Home/End, Enter, a letter shortcut, Esc/Tab closes) and closing (press elsewhere, wheel, resize, blur). Traps, each one real:

- **Portaled to `<body>`, fixed in screen space** — so the canvas zoom doesn't shrink it and neither a card's clip nor the card z-counter can hide it (z 300, above the HUD and flyers). It opens at the pointer and, measured in a layout effect before paint, flips to the pointer's other side where it would leave the window.
- **A portal still bubbles through the *React* tree.** Without the `stopPropagation` on the menu's root, a tap on an item reaches `BoardCanvas` (starting a touch pan) and a right-click inside it reaches the row's own handler (reopening the menu). Keep them.
- **The click that ends a touch hold must be swallowed natively.** React derives a checkbox's `onChange` from the same native click, so `onClickCapture`/`stopPropagation` in React can't stop the tick; `ItemRow` arms a one-shot *native* capture listener when a hold fires (`swallowLiftClick`) that kills that one click before it reaches React's root. It listens on the **document**, not the row (as it first did): on a small screen a tall menu has no side of the finger left to open on, so it opens over it, and the lift's click then landed on — and ran — whichever action sat there. The next press anywhere disarms it, for a hold whose lift brought no click (Android's); without that, the tap that picks an action would be the click swallowed. A `held` flag ignores the `contextmenu` Android fires after a hold (the menu is already open) and resets on the next press.
- **Right-click keeps its native meaning inside the row's forms and text inputs** (`NATIVE_TARGETS` — so the browser's paste menu still works in the edit form and the inline rename); a hold on the drag/group handles is a drag, not a menu.
- **A tally box's right-click stays "remove one"** — the box stops propagation, so it never reaches the row's handler.
- **Delete goes through the same confirm as the trash button**, which is why `RowRemove` is controlled (`confirming`/`onConfirmingChange` held by the row kind): the menu's Delete and the hover trash open one confirm, in one place.

### Box dots (tiered + count rows)

- Both tiered and count rows render as a strip of checkbox-styled squares (`.tier-dot`) in column 1, driven by the behaviour (`boxes`/`filled`/`levelOnClick`) — whiteboard-accurate (the physical board had a row of boxes). **Styled identically to the real checkbox** (17px, `border-radius: 5px`, white check via `.filled::after`), not small circles — a direct owner correction. Clicking dot *i* resolves a target level: tiered selects that tier (toggle off if already active), count fills to *i*+1 (clicking the topmost ticked box unticks just it); dots fill cumulatively. Each dot carries `data-box-index` (for the streak pick-whip); a tier's dot sits in a `Tooltip` saying its time (or its label, where it has none). (The timer that used to be tiered-only now lives in a generic `.task-footer` on any row when the tab's Timer toggle is on — see "Task timer".)
- The dots are the *only* tier-selection UI — the old labelled `.tier-chip` pills were removed; the label is each dot's `Tooltip`.
- **The points builder is a sentence** (`PointsBuilder.tsx`: "1h at Ugh difficulty = 3.75%") — the one place a `%` is set, in the add form, the edit form and each tier. The time and the effort are chips that open their choices under the line (`open`: one at a time): the time's presets plus a typed-time field that takes focus as it opens (`duration.ts` — `parseDuration` reads "45m", "1h30", "1:30", "1.5h", a bare number as minutes; `readDuration` adds the 2m–24h bounds and the error line; `formatMinutes` is the same writer the row's Time estimate uses), and the board's effort levels with their multipliers. The contract with its form is unchanged: `points` is the parent's, the builder writes the built `%` when a pick changes (skipping mount, so a seeded edit never clobbers) and reports `{ minutes, effort, source }`. A typed `%` that no longer matches is `by-hand`: `≠`, dashed chips, and "Or use 3.75%". Three things keep the line still, since the owner asked that typing never move it: `=`/`≠` share one width (`.sentence-sign`), "= %" wraps as one piece (`.sentence-result`), and the `%` field is never narrower than 4ch — with the two task forms at `POINTS_FORM_WIDTH` (350) so the whole sentence fits on a line. Enter in the typed time closes the choices instead of submitting the form; Esc closes them (and stops there, so the form stays open). An effort's dot and its choice are coloured by its *place* on the scale (`effortTone`), never its name; that colour stays inside the form — a row's bracket is coloured by modifiers alone. The old "?" reference in the add form is gone (the multipliers are in the effort's choices), and with it `Popover`'s `titleExtra`.
- **A task's description is folded in its forms** (`DescriptionField.tsx`, shared by the add and edit forms): a "+ Description" line (`.form-add-btn`, the same line as "+ Add tier") until clicked, then the field with the cursor in it; open from the start when the task has one. The add form re-folds it after a task is added by remounting it with the builder's `builderKey` — under its own key name, since two siblings with the same key (`0`) made React drop the click.
- **A tiered task's tiers have one editor, `TiersField` (`PointsBuilder.tsx`), in the add form and the edit form alike.** Each tier renders its own `PointsBuilder` under a "Tier N" head (its `heading`) with a remove ✕ (off on the last one — the API wants at least one tier), and "+ Add tier" sits under them. A form holds only the rows (`TierRow`, in `tierRows.ts`): the add form starts from one `newTierRow()`, the edit form from `tierRowOf(tier)` per saved tier, and both turn rows back into tiers with `tiersFromRows` — so a tier is read and written one way. A row that edits a saved tier carries it (`row.tier`): its builder is seeded with the tier's duration/effort only where the builder made its % (the same rule as a checkbox task's edit), and on save it keeps whatever the form doesn't set. Labels follow place: an auto "Tier N" label is renumbered as tiers come and go, a label with words of its own ("1hr", on boards from before the builder) is kept. Each row carries a stable `id` so its builder's `onPointsChange`/`onBuilderChange` stay stable — those are effect deps in `PointsBuilder`. Each tier's picked duration is stored as `TierDef.minutes`. **History:** the edit form first had bare %-per-tier inputs with no builder (a one-off fork), then the shared builder with the tier count fixed — each form still kept its own copy of the rows' plumbing, and only the add form's could add or remove; the owner's "why can't I add a tier?" is what folded both into `TiersField`. **What's ticked is a level** (`activeTier`, the tier's place), not a tier's identity — a `TaskEdited` that leaves fewer tiers than the one ticked brings it down to the last (the fold, next to the box count's clamp of `progress`; `App.editTask` mirrors it so the row and the counter agree at once). Covered, with rebuild parity, by `apps/api/test/tiers.test.mjs`.
- **`TaskTimer` is the one timer component, shown on any row when the tab's Timer display toggle is on** (see "Sort" / Display). It's a plain stopwatch (start/pause/reset/type-minutes, persisted via `PATCH …/timer`) for every task; passing `tiers` + `onSetTier` (only `TaskItem` does, and only for tiered tasks) additionally lights up **tier mode** — auto-advance as elapsed time crosses each tier's threshold, plus a **Submit** that locks in the reached tier. Thresholds come from **`tier.minutes`** (set via each tier's builder), falling back to scraping the tier *label* for legacy tiers; a tier with neither never auto-selects. Trap the stored minutes fix: labels are auto-generated (`"Tier 1"`), so the old label-scrape (`parseTierMinutes`) never matched and the timer never appeared. A non-tiered task passes no tiers, so it shows the stopwatch with no Submit and no scoring effect.
- **`.tier-dots` is `flex-wrap: nowrap`, not `wrap`.** With `wrap`, dots wrapped onto a second line even with room, because a wrapping container's max-content contribution to its grid column is ambiguous. `nowrap` makes it unambiguous.

### Checkboxes

Custom-styled (`appearance: none`), not native, so the tab color shows on the *unchecked* border too (native only tints `:checked` via `accent-color`). Each `TaskItem` sets `--task-color` inline; `App.css` reads it for border + checked fill + white checkmark. If checkboxes look gray, check that custom property, not `accent-color`.

### Completed styling

A done checkbox row looks **disabled**, not struck through: a gray diagonal-hatch `::after` overlay + muted text, zero transition so it snaps in. Deliberately not red/white (read as a warning) and not strikethrough-only. A **multi-box** checkbox gets the same look once every box is ticked (`task.count != null && isDone` in TaskItem's `boxes` branch; its dots dim like the checkbox). **Tiered** rows share that branch but deliberately don't — picking a tier isn't "finished", a higher one may still come.

### Drag & reorder — two separate mechanisms

- **Items within a tab:** framer-motion `Reorder.Group`/`Reorder.Item` (`⠿` handle, hover-reveal) — the `ItemList`/`ItemRow` bases, so tasks and rewards reorder identically. Persists via `PATCH /api/sections/:id/reorder` (tasks) or `PATCH /api/shop/sections/:id/reorder` (rewards).
- **Tabs themselves:** no longer *reordered* at all — they're **freely positioned** on the canvas via the header `⠿` handle (`onPointerDown={startMove}`, see "Card move & resize"), stored per-device in `localStorage`. The old native-HTML5-DnD swap was removed. `PATCH /api/sections/reorder` still exists on the server but the web client no longer calls it (a section's array order now only seeds the *default* placement of a never-moved card and its initial `z`).
- **Drag handle CSS, rule order matters.** The row handle is `position: absolute; left: -16px` on the `position: relative` `.item-row` so it overlaps the padding and never shifts the first cell from flush-left. `.section-drag-handle` overrides that back to static flow **and must appear *after* the base `.drag-handle` rule in `App.css`** (equal specificity → source order wins). If the tab handle "disappears" after touching `.drag-handle`, check rule order first.

### Sort

The Sort and Display buttons are the shared `SortMenu`/`DisplayMenu` (`TabControls.tsx`), both on one `PinnedRows` list: the pinned options up front — plus what's in use (the active sort; the toggles that were on as the menu opened, so ticking one under "Show more" doesn't jump it away under the pointer) — the rest under "Show more", each row with its pin. **What a tab offers is declared in `tabViews.ts`, and nowhere else.** Each item kind has a catalog (`TASK_SORTS`/`TASK_DISPLAYS`, the streak and reward ones), built with `catalog<…>()` so every entry is typed as an option of its menu: a sort is `SortOption<T, C> { key, label, icon, compare?: (ctx) => (a, b) => number }` (no `compare` keeps the drag order — Manual, or a sort with `parts`, below), a toggle a `DisplayOption { key, label, icon, defaultOn? }`. A tab picks from its catalog with `offer(option, { pinned, label, icon, defaultOn })` — so the Freezer's Age is the same option as Tasks' under the words "Days frozen". Board tabs are told apart by `roleOf(section)`, read off their settings, never their names: a Freezer (`freezerFor`), a to-do list (allows a type that retires when done), a routine (allows a prunable type), or habits (the rest — tiers and tallies). The card applies the chosen sort with `sortItems(items, option, ctx)` over its items in their own order (so Manual, and ties, keep it); the task sorts' context is the board clock (`{ now, settings, openDay }` — Get done quick sinks schedule-locked boxes), the rewards' each one's price now and the points. `tabView` reads the prefs against the offer: a sort the tab doesn't offer falls back to its first (Manual), and `shown(key)` is false for a toggle it doesn't offer, so a card never re-checks what its tab offers. Age sorts by `waitedMs` (`freezer.ts`), the same wait the Age chip shows in days. The time sorts key on a checkbox task's `estimateMinutes` (tasks without an estimate sink to the bottom either way; tiered tasks have no task-level estimate so they sink). The effort sorts ("Effort: lightest first" / "hardest first") rank by a level's place on the scale (`effortRank`): a task's `estimateEffort`, or a tiered task's hardest timed tier; a task with no estimate was never given an effort and sinks either way. The chosen sort is a pure client-side display transform, **persisted per tab and per device** in `tabPrefs` (see "Client vs server state") — not board truth.

Beside Sort sits a per-tab **Display** button → a `Popover` of view toggles (same reused `Popover`; the app has no `Modal`); which a tab offers is `tabViews.ts`'s (the per-tab list is in `PRODUCT.md` → "Forms & interactions"). What they do: **Time estimate** — a small clock + `Xh Ym` beside each task that has an `estimateMinutes` (the badge lives *inside* the name cell so it takes no subgrid column); **Timer** — a `TaskTimer` footer on *every* row (a stopwatch on any task; tiered tasks also get auto-advance + Submit — see "Task timer"); **Pruned tasks** (see "Prune" under Core types); **Status** — the bands (see "Status" under Core types), offered only by a to-do list; **Age** — the `AgeChip` ("today", then `5d`, `2w`, `3m`); **Completed tasks** — finished one-time tasks listed again (see the `once` note under "Core types"), in the catalog but offered by no tab; **Grouping** — every tab kind's (`GROUPING_KEY`): `ItemList`'s `grouping`, which off renders the list flat — its groups hidden (still kept, members still gathered by the fold) — with no group handle or drag-into-group; and the Freezer's line toggles — a Display option keyed by a modifier's id (`frost`, "Frost bonus") shows or hides that modifier's line under each row, `meters` ("Frost bar") the bar on it, `thaw-bonus` the thaw line (`SectionCard`'s `extraShown`: an extra a tab doesn't offer as a toggle always shows; `TaskItem`'s `lines`). For rewards: **Note**, **Times bought** (off by default), **Already bought**. Like the sort, the toggles persist per tab and per device and aren't board truth — how *this tab* is viewed — so **Timer defaults off and the Registry's tiered timer is behind it too** (it was always-on before this unification). (Tiered tasks deliberately show no time-estimate clock for now — they store minutes per-tier for the timer, not a single task estimate.) The only stored order is the manual drag order; dragging is disabled while a sort with a `compare` is active. Don't add a second persisted per-mode order — considered and rejected.

**A sort can split a list instead of ordering it.** `SortOption.parts?: (ctx) => (items) => ListPart<T>[]` (`ListPart { key, label?, color?, items }`) cuts a list into headed parts, each in the list's own order. `SectionCard.taskList` draws every non-empty part as an `ItemList` of its own under a `ListPartHead` (its words in its colour, its count, a rule) — the same narrower-list mechanism as a Status band (`inList` → `withUnlistedKept`), so a reorder inside a part keeps every other task of the tab where it was, and a row, being in another `Reorder.Group`, can't be dragged into the next part (dropped there it goes back; dropped on another *band* it still changes Status, through the band's `dropOutside`). A part without a `label` gets no header ("Priority: High only" with no High task — nothing to set apart). Such a sort has no `compare`, so the card's `ownOrder` is true: its lists stay `manual` — rows drag, and the tab's groups show where Grouping is on (a group whose tasks sit in two parts shows in both, as with bands). **Which lists split is the tab's call:** the plain list (Status off), and a band whose `STATUS_BANDS` entry `splits` (the Backlog — where tasks wait their turn); In progress and Blocked stay one list, as dragged. The two priority sorts (`TASK_SORTS.priorityHigh` / `priorityAll` in `tabViews.ts`) are the first; under High only the rest is one part labelled "Tasks". The pinned Bounty stays above the parts. The Sort popover is `fit` (`Popover`: as wide as its longest row, at least its `width`) — "Priority: High, Medium, Low" wrapped onto two lines at the fixed 212px.

### Points counter HUD (`PointsCounter.tsx` + `useFreeSpot.ts` + `useDiegeticDepth.ts`)

- Styled as a fixed-width (160px) "bracket" widget — sci-fi corner spans, no glass/blur, no idle motion. This was picked from a live 8-way comparison after two description-based attempts were rejected on sight. **Lesson: for visual-only requests here, if a described CSS change is rejected once, build a live comparison instead of guessing again.** Fixed width so digit-count changes (`9%`→`10%`) don't restretch it.
- **Count-up animation holds a fixed decimal precision for the whole tween**, computed once from the target (`decimalsNeeded`, stored in `precisionRef`), never trimmed per-frame — trimming only the final value made the digit-count change at settle-time read as a jump. A % never shows more than two decimals: `formatPercent`, `percentDecimals` and `formatPercentFixed` (`points.ts`) all round half-up to hundredths of a percent from the stored thousandths, so the count lands on exactly the digits everything else shows (`packages/contracts/test/points.test.mjs`).
- **Placement is a motion problem, not a positioning one** (this is the 4th design; step 3 was handed to another AI to get right). `.hud-anchor` is `position: fixed` but its position is *computed* by `useFreeSpot`: it measures every card, the add-tab tile, open popovers, and the date header on each layout/scroll change, then places the widget in the gap **nearest screen-centre** (candidates are obstacle edges + viewport edges/centre, not a grid). `findSpot` is exported as a pure function (boxes + viewport + size → `{x,y}`) so it's testable without a DOM. Placement is written straight to `el.style.transform` (never React state — a scroll reflow must not re-render the board); first placement runs in `useLayoutEffect` (no untranslated flash); re-placement smoothed by `transition: transform 0.55s`. Falls back to bottom-centre if there's no clear gap. **Where it docks instead of parking** (a `.hud-dock` in the DOM, rendered by `CardCanvas`): in the shop, in any canvas's one-tab view, and on a phone's board — the three places a gap can't be counted on.
- **`.hud-depth` (`useDiegeticDepth`)** owns scroll "inertia" — a damped spring kick against scroll direction, so a fixed element still *feels* like it moves when you scroll. rAF loop self-terminates when motion settles. **A previous pointer-driven 3D tilt was removed** — the owner disliked the widget tracking the mouse. Don't reintroduce cursor-following motion. That's also why the anchor no longer sets `perspective` and depth no longer sets `transform-style: preserve-3d`.
- **Keep the anchor and depth layers separate** — the static position and the animated transform would clobber each other on one element. The `MutationObserver` watches `<main>`, not `body`, so it catches tab/task/popover changes without picking up depth's per-frame transform writes (which would fire it forever).
- **Don't wrap `.hud-anchor` in anything with its own `transform`/`filter`/`perspective`/`will-change: transform`** — that becomes the containing block for `position: fixed` and the widget would scroll away. If ever needed, portal `PointsCounter` through `createPortal(…, document.body)` instead.

### Flying points (`FlyingPoints.tsx`, `flyerTiers.ts`)

Checking a box or picking a tier flies the row's `[%]` bracket into the counter, landing with a scale-pulse + particle burst. This is the app's signature "satisfying feedback" — treat it as high-stakes (see `PRODUCT.md`). There's deliberately **no origin flash** (owner found it noisy).

- **The flyer must read as the row's actual bracket detaching, not a badge appearing.** Four things carry this illusion; it breaks if any one drops: (1) it renders the same `PointsBracket` as the row (identical text incl. `<wbr/>`s); (2) it carries the row's `points-prefix` class so size/weight/figures/colour match by construction — `.flyer` sets only position/pointer-events and must not re-acquire font/colour; (3) it's pinned to the source's exact `getBoundingClientRect()` (left/top/width, not a centre point), overlaying it pixel-for-pixel at `scale: 1`; (4) the row hides its real bracket via `.points-prefix.in-flight` (`visibility: hidden`, so the points column doesn't reflow), driven by `flyingTaskIds` from `App.tsx`.
- **The flight is an arc, not a line:** `x`/`y` animate to a centre-to-centre delta with *different* easings (bends the path); `scale` keyframes `[1, 1.14, 0.72]`; `opacity` holds at 1 until 88% (fading early looked like it dissolved before arriving); `color` animates to the HUD red on a delay so it visibly stops being a board element. Framer reads the *start* colour off the DOM, so only the destination red is named.
- **Landing target is the counter's value text** (`getRect()` returns `valueRef`'s rect), not the box centre — it lands in the gap beside the number rather than merging into it. `getBoundingClientRect` composes the depth transform, so the target is always the widget's real current position mid-drift.
- **Burst particle ids are `uid()`s, never the clock** — two landings in one millisecond (a broken-down task's pieces ticked in a row) gave their particles the same React keys.
- **Finishing a broken-down task celebrates the whole task:** a flyer spawned with `finale` (the tick that finishes its last piece, or its own box) plays one tier above its gain's, never below `surge` (`tierFor(amount, finale)`).
- **Celebration scales with the *gain*, in four tiers, all defined in `flyerTiers.ts`** (`tierFor(amount)`: `spark` <1%, `charge` 1–3%, `surge` 3–10%, `overdrive` ≥10%). Nothing else holds a magnitude number — retune feel by editing that object, not animation code. For a tiered task the gain is `nextPoints − prevPoints`. Deliberately HUD-confined (no page flashes). `tierFor` collapses to `spark` under `prefers-reduced-motion`.
- **`FlyerItem` is a separate component** because per-flyer phase state (`windup` → `flight`) can't live in a `.map()` body. Phase advances in `onAnimationComplete`, which also reports landing — and that callback fires for *every* settled target including the exit fade, so it's guarded by both `useIsPresent()` and a `landed` ref (without them, unchecking mid-flight fires a burst for points being taken back).
- Ghost afterimages get `duration = flight.duration − delay` so a staggered trail lands with the leader; they render the same `PointsBracket`, carry no `exit`/`onAnimationComplete` (only the real flyer may report landing).
- Flight target is **re-measured at launch** (`getTarget` callback), not reused from spawn — a wind-up can last ~1s and the HUD moves itself.
- **Framer trap that bit this for real:** a per-value transition does *not* inherit the parent `duration` unless it opts in with `inherit: true`. `transition={{ duration: 1, x: {...} }}` gives `x` no duration and it silently falls back to the 300ms keyframe default. Every per-value transition now carries its own explicit `duration`. Also: `times` is ignored unless its length equals the keyframe count, and a literal first keyframe snaps — use `null` for "from wherever this value is." (`spark.flight.duration` in `flyerTiers.ts` is the one knob if the snappier sub-1% flight is ever wanted back.)
- Counter box-shake and corner-flare are driven imperatively (`animate()` on a ref'd node), **not** by a remount-on-`key` — remounting `.points-counter` would throw away in-flight particles/shockwaves. Don't give `.points-counter` a `key`, and don't move the anchor/depth transforms onto it.

### Tooltips & form problems (`Tooltip.tsx`, `Form.tsx`)

Nothing the browser draws by itself is used (the rule is `CONVENTIONS.md` → "Build once"; the list of what to use instead heads `COMPONENTS.md`).

- **`Tooltip` is CSS-only**: a wrapper (`.tooltip-wrap`) and a bubble shown on `:hover` / `:focus-within`. `position` is top / bottom / left / right; `align` (above or below) is start / end for a trigger at a card's edge. With no `label` it renders its children alone, so a hint that only sometimes applies needs no branch.
- **The wrapper takes focus only when asked (`focusable`).** It used to always carry `tabIndex={0}`, which gave every button inside one a second tab stop. A child that takes focus shows the bubble through `:focus-within`; `focusable` is for one that can't (the age chip's text, a locked box's disabled input) — also what makes it reachable by a tap.
- **`inline` for a trigger in a run of text.** The points bracket's values must still wrap between each other (see "List rows"); an `inline-flex` wrapper there would turn each into an unbreakable box, so `PointsBracket` wraps a modified value in an inline one.
- **The wrapper can stand in for a laid-out element** (`className` / `style`): a grid cell (`streak-best`, the locked `checkbox-cell`), a row (`cond-row`), a chip (`task-est`, `recap-tab`). Its own `display: inline-flex` loses to the element's class only because the tooltip rules come first in `App.css` — keep them there.
- **`wrap` for running text.** A bubble is one line (`white-space: nowrap`); a task's description is a paragraph, so its tooltip wraps at 220px and keeps the text's own line breaks.
- **The Status pill's buttons sit in wrappers**, so its rounded ends and dividers are selected through them (`.status-pill .tooltip-wrap:first-child button`, `… + .tooltip-wrap button`) — `button:first-child` would match all three.
- **It's clipped by a scrolling tab.** A tab's list only clips while it scrolls (`CanvasCard`'s `overflows`), so a bubble opening above the first row of a scrolling tab is cut. Known, accepted.
- **`Form` is `<form noValidate>` over the browser's own rules.** Fields keep `required` / `min` / `step` / `type="number"`; on submit it finds the first field failing them, in the form's own order (`fails` — plus one the browser lets through: a required field of only spaces), focuses it, and says what's wrong (`problemWith`: the field's own `data-missing` for being empty, else read off the failed rule) in `.form-problem` under it. Only then does it call `onSubmit` — which may return a `FormProblem { field, message }` for what only the whole form can tell (a streak with no linked task), said under the element carrying that `data-field`.
- **The problem is placed from layout offsets, not screen rects** (`placeUnder` walks `offsetParent` up to the form, which is `position: relative`): a form can be drawn scaled, and a screen measurement would be off by that scale. It clears on any edit or press inside the form.
- **One look, one rule:** `.tooltip-bubble, .form-problem` share the bubble's declarations in `App.css`. The streak form's red inline `.field-error` lines were the app's only other way to say a form problem; they went with this, so there is one.
- **What was replaced:** 16 `title` attributes (the rail, the theme switch, the debug badge, the candle, the group handle, a streak's best and its AND/OR toggle, a misfit streak condition, the estimate badge, the recap's tab chip and purchase lines, a modified bracket, Break down's tuck handle — the two link handles' titles only repeated their own words and were dropped) and the native bubbles of the add, edit, reward and streak forms. Three hints that were drawn by their own CSS in the same look went onto it too — a tier box's time and the Status pill's band names (each a `::before` reading `data-label`) and a task's description (a hidden span in its "i" button) — so every hint in the app is this one component.

### Themes (`theme.css` + `useTheme.ts` + `ThemeSwitch.tsx`)

- **Every chrome colour is a token in `theme.css`** (`--bg`, `--surface`, `--text`, `--danger-text`, `--mod-frost`, …); a theme is a `[data-theme="…"]` block giving those tokens other values, on `<html>`. `[data-theme]:not([data-theme="light"])` holds what every dark theme shares (brighter state and modifier colours, `color-scheme: dark`), so each dark theme only sets its neutrals. Adding a theme = one block there + one `THEMES` entry in `useTheme.ts`. Light's values are the original literals, so light mode is pixel-identical to before themes.
- **Theme blocks match any element with `data-theme`, not just `<html>`.** The theme menu's swatches (`.theme-swatch[data-theme=…]`) use that to draw each theme in its own colours without restating them.
- **Paper stays light.** `.recap-note` and `.booster-face` are listed with the light block, so text written on sticky notes / Booster cards keeps dark ink on pale paper under a dark app. **The tokens alone aren't enough:** a paper object also sets its own `color` (`.recap-note { color: var(--text) }`), because anything on it that names no colour inherits the *computed* colour of the dark app around it — pale ink on pale paper (the recap's streak and frost names did). A new paper object goes on that list.
- **Ink on an ink fill uses `var(--surface)`, never `#fff`** (`.btn-primary`, tooltips): `--text` turns light on a dark theme, and white text on it vanished. White stays only on a fill that's a fixed colour (red danger button, a tab-coloured checkbox).
- **Tab colours are user data, drawn through `tabInk()` (`palette.ts`)**: `oklch(from <colour> max(l, var(--ink-floor)) c h)` — `--ink-floor` is 0 on light (colour exactly as picked) and 0.72 on dark, which lifts an ink-black tab (the seeded "Tasks" is `#1e293b`) to readable while keeping its hue. Browsers without relative colours get the raw colour (`CSS.supports` check). The colour picker always shows the raw colour.
- **No flash on load:** an inline script in `index.html` resolves `board-theme` (incl. "system" via `matchMedia`) and sets `data-theme` before first paint; `useTheme` then owns it (and follows the system live while the choice is "system"). The two must agree on the key and resolution.
- **Native fields** get `:where(input, textarea, select) { background-color: var(--surface); color: var(--text) }` (`index.css`, zero specificity) so dark themes don't show the browser's own grey inputs.
- **Not themed:** shadows (ink; on dark they read as depth), the wind-down panel (already dark), and the celebration FX colours.

### Animation convention

When moving an element between screen positions, **animate transform-based `x`/`y` deltas from a static `left`/`top` anchor, not `left`/`top` directly** — learned the hard way on the flyer; framer owns the transform more reliably.

## Security architecture

Security is not a later phase. The app is destined for a shared VPS alongside the owner's other services, so **containment is the priority** and the realistic risk is supply chain, not app logic.

- **Zero outbound network calls, ideally blocked at the container level.** Never add a dependency that phones home, a CDN link, a remote font, or a telemetry/error-reporting service. Keep dependencies few and justified (`framer-motion` is the one deliberate frontend dep).
- **Validate every input at the trust boundary** (the API already does this with type guards — keep it).
- **When user-defined filters/queries arrive** (a `BACKLOG.md` item), they must be structured ASTs compiled to parameterised SQL — never string interpolation, never `eval`, bounded depth/node count.
- **No hard-coded secrets; never log credentials/tokens/key material** — log presence/type only.
- **Run non-root, unpublished DB, resource-limited, no host mounts** when the deploy story lands.
- **Auth: one shared password, no accounts** (`apps/api/src/auth.ts` / `authRoutes.ts`). There is exactly one person who opens this board, so there's no user table — just a password hash + a session secret in `apps/api/data/auth.json` (gitignored, mode `0o600`). The password is set from the terminal (`pnpm set-password`, prompts hidden input, never a CLI arg) — never through the UI, since anyone who could set it wouldn't need to be locked out. `POST /api/auth/login` checks the password (scrypt, timing-safe compare) and, on success, sets an `HttpOnly`/`SameSite=Lax` cookie good for 10 years, whose value is `HMAC-SHA256(sessionSecret, "board-session")` — stateless (no session store to clean up), and re-running `set-password` rotates `sessionSecret`, which **instantly invalidates every previously issued cookie** (the closest thing to "log out everywhere" this model needs). `requireAuth` gates every `/api` route except `/api/auth/*`; the web app's `AuthGate` (wraps `<App/>` in `main.tsx`) shows a login form until `/api/auth/status` reports `authenticated`. This is a deliberate, reviewed step toward the auth this doc used to flag as missing — the server remains the sole authority on points and time regardless. The API still **listens on `127.0.0.1` only** (`index.ts`) so nothing reaches it except through the proxy in front of it (Vite in dev, nginx in production) — the password gate is defense in depth on top of that, not a replacement for it.

The stance underneath all of this: **containment and verifiability over "just trust it."** The owner can't audit the code and self-hosts next to their other services, so the answer to "is this safe?" is architecture (isolation, no outbound, rebuildable state), never reassurance.
